# Cyberbaser TrueNAS Custom App: operator handoff

This is a local image release for `linux/amd64`, not an instruction to install without approval. Keep the desktop install and existing datasets untouched. The `cyberbaser` application is one TrueNAS-managed app with three containers. No host unit, appliance package, persistent host script, registry, engine socket, custom security profile, or published Docker port is needed.

## Read-only preflight (must pass before installing the app)

Record the results without dumping secrets or unrelated workloads. Stop and ask the owner if a gate cannot be verified. Creating the dataset or changing a host setting is separate from this inventory and requires approval.

- Verify the appliance version, idle memory/disk budget, and app-name availability. Record `sysctl -n kernel.yama.ptrace_scope` (do not change it). Verify Linux Landlock ABI 6 or newer and the renderer probe under the appliance's rootful Docker **default** seccomp and `docker-default` AppArmor; do not use an unconfined profile. Verify 4517 and 4518 are free on the server and forward ports are free on the desktop; check any configured private IPv4 is assigned. The app limits total 1888 MiB excluding host overhead; measure `memory.peak` and `memory.events` during representative rendering, not just the lab note.
- Before creating the app, run the staged release's no-network launcher probe under the same default Docker security profile. After separately authorizing the local image load, substitute its verified image ID for `<image-id>`: `sudo -n docker run --rm --pull never --network none --user 65532:65530 --cap-drop ALL --security-opt no-new-privileges --read-only --tmpfs /tmp:rw,nosuid,nodev,mode=1777,size=16m --memory 64m --cpus 1 --pids-limit 32 --entrypoint /usr/bin/timeout <image-id> 20 /usr/bin/bash -euc '/opt/cyberbaser/libexec/render-offline --landlock-abi; work=$(mktemp -d /tmp/render-probe.XXXXXXXX); mkdir "$work/build" "$work/out"; /opt/cyberbaser/libexec/render-offline "$work/build" "$work/out" -- /usr/bin/true'`. Record the ABI number (at least 6) and exit status (must be 0). The version query alone does not prove ruleset enforcement. Keep the profile unchanged if either check fails.
- Inventory host processes and all other apps, including configured start identities and effective runtime UIDs. No other process/service may use host UID 65532 or 65533; no other app may mount `/mnt/personal` or the pool root. Inspect mount source paths, not container target paths. Confirm rootful Docker uses the host UIDs in `paths.tsv`. An unknown identity, user-namespace mapping, or unresolved mount is a stop, not a pass.
- Verify that no SMB or NFS share exposes the parent of the new dataset or any ancestor. Review recursive replication and cloud-sync task settings. `/mnt/personal/cyberbaser/publisher/state` must be outside their selection or explicitly excluded. For whole-dataset replication that cannot exclude a child path, exclude the entire Cyberbaser dataset; do not omit the rule. Record the exclusion, not the credentials.
- After separately authorized dataset/path provisioning and **before** starting any app, use the TrueNAS filesystem ACL inspection for the dataset root and verify its ACL is trivial with no inherited NFSv4 entries. Verify every `paths.tsv` source is a real directory with the recorded UID, GID and octal mode and no inherited grants. Recheck share/task boundaries against the actual path. No recursive repairs, ancestor permission changes or implicit directory creation.

## Install (after separate approval)

- Create only the dataset and exact `paths.tsv` paths relative to `/mnt/personal/cyberbaser` (`.` is the dataset mount root). Use TrueNAS dataset/filesystem APIs with explicit octal modes and nonrecursive ownership changes only. `create_host_path: false` prevents Docker from filling in missing sources. The runtime creates its own app-private child directories.
- On the trusted build host, verify `sha256sum -c SHA256SUMS` and the recorded source in `build.txt`. Stream the checked archive using the existing authorized, host-key-pinned administrative SSH path into `sudo -n /usr/bin/docker load`. Verify `sudo -n /usr/bin/docker image inspect --format '{{.Id}} {{.Os}}/{{.Architecture}}' cyberbaser:<version>` reports `linux/amd64` and either the exported platform config digest (`image-id.txt`, classic image store) or the exported platform manifest digest (`build.txt`, containerd image store). The development tag's inspected index ID is recorded separately and is not the single-platform export identity. Never substitute `latest` or pull by name. Use the bundled resolved `compose.yaml`; it needs no `.env`, included file or relative mount on the appliance.
- Use the middleware schemas on the actual appliance to confirm the YAML field before writing. For SCALE 25.10 Custom Apps this is `custom_compose_config_string`: form the JSON from the file on the build host (`jq -n --rawfile yaml compose.yaml '{app_name:"cyberbaser",custom_app:true,custom_compose_config_string:$yaml}'`), pass as a single argument to `sudo -n /usr/bin/midclt call -j app.create`, and check the job result. Stream shell work via the verified admin SSH session with `bash -s`, not a multiline command interpreted by the host's default zsh. Shell-quote any payload before transmitting; don't write an installer script on the appliance.
- Verify app status through middleware and inspect only its three containers. Confirm image IDs, limits, mount allowlists, AppArmor and seccomp. The publisher must be on the Compose bridge, with no published port; only the node has host networking. Verify that the publisher's enrollment listener exists on its own loopback and is unreachable from the node's namespace, before and after setup. Do not read or print the page body. Probe the renderer launcher without added privilege. On a failure stop only this app; do not remove the dataset or weaken its protections.

## Private setup and network inventory

Use the verified Tailscale SSH port-forward path from the owner's desktop, matching local and remote `127.0.0.1:4517` (e.g. `ssh -N -o ExitOnForwardFailure=yes -L 127.0.0.1:4517:127.0.0.1:4517 <linux-user>@<tailscale-host>`). Keep that connection open through the final callback. Verify the forwarded endpoint is the expected instance before using an invitation. Use a separate browser profile/session from the desktop installation: cookies are not port-scoped. Add a same-port 4518 forward only for the authenticated private reader. Open the reader in the same browser profile after signing in to 4517; a node restart needs a fresh owner session.

Use the independent administrative channel to identify the node container by its exact Compose app and service labels. Retrieve the **latest** `Cyberbaser setup: http://127.0.0.1:4517/setup/start?token=…` line from only that node's `sudo -n /usr/bin/docker logs` in a private owner-controlled terminal or desktop flow. Filter locally rather than showing all logs. Never copy the bearer link, cookies, callback URL, pairing/recovery data, or raw logs into chat, a ticket, CI or the release bundle. Opening the link does not spend it; **Start setup** does. Normal restarts use the latest `Owner alpha bootstrap:` link from the node, with the same private terminal handling.

For the first publishing device, the server agent identifies the exact publisher container by its Compose app and service labels. With the owner present, run `sudo -n /usr/bin/docker exec -it --user 65533:65530 <publisher-container> /opt/cyberbaser/bin/cyberbaser publisher enroll-code` in a private, **unrecorded owner-controlled terminal**. Present that terminal's QR directly to the owner (or let the owner read and type the short code there). If the server agent cannot offer an unrecorded owner-only view, have the owner run the command in their own private admin terminal instead. Do not capture or relay stdout through tool transcripts, chat, logs, a ticket, clipboard sync, files or this bundle. The owner should save any recovery code independently; do not retain a copy. The setup code is one-use and expires after an hour. Publisher service logs never contain it. Do not issue codes or reset owners unattended. There is no enrollment forwarding or embedded enrollment frame in this form.

| Role and mode | Listening sockets |
|---|---|
| Node setup | TCP `127.0.0.1:4517`; Iroh starts on the phone step |
| Normal node | TCP `127.0.0.1:4517` and reader `127.0.0.1:4518`; node-private `/run/cyberbaser/review.sock` |
| Publisher (setup and normal) | TCP `127.0.0.1:4519` **inside the publisher namespace only**; shared Unix `publisher.sock.forge` and `publisher.sock.owners`; `publisher.sock` for publishing only in normal mode, all under `/run/cyberbaser-publisher` |
| Iroh, `private-address:<IPv4>` (set to the selected Tailscale address in the private bundle) | One UDP socket at the selected IPv4 and one at `[::1]`, ephemeral ports, with normal relay enabled |
| Iroh, `relay-only` | One UDP socket on `127.0.0.1` and one on `[::1]`, ephemeral, neither advertised as a direct route |
| Iroh, `direct` (broader opt-in) | Wildcard IPv4 and IPv6 UDP, ephemeral, with normal relay enabled |
| Config reconciler / render subprocesses | No network listeners. The reconciler has no network; render subprocesses cannot open network sockets, connect to named Unix sockets, or receive new socket descriptors. Landlock limits writes to that invocation's workspace/output and private scratch, and refuses cross-domain task-memory access. |

Outbound forge/relay/DNS connections and their transient source ports are not ingress listeners. Iroh ports are OS-selected; do not try to reserve fixed UDP ports. The setup-to-normal handoff can briefly retain previous sockets at the same allowed addresses. Changing the `CYBERBASER_CONTAINER_REACH` value in the node's Compose environment and applying the YAML changes setup and normal reach on restart. To use only LAN plus relay, substitute one private LAN IPv4; to use all local interfaces choose `direct`. Two explicitly selected IPv4 addresses are not available in the pinned binding; the app does not broaden a refused setting to wildcard. TrueNAS's host networking means the `direct` setting also accepts on any other host interface. Check live addresses and listeners before inviting any device.

## Upgrade and rollback

Obtain separate authorization. Retain the current resolved YAML and image tar/ID. Stop only this app, quiesce writes/jobs and take a protected dataset snapshot once stopped; include publisher state and preserve its custody. Do not treat an image rollback as a source or GitHub rollback. Check release compatibility with durable jobs, source identity, device keys and config. Load/verify the new image by ID before changing any Compose references. Use `midclt call -j app.update cyberbaser` with the new resolved YAML (confirm `custom_compose_config_string` on that version); verify all three roles moved together and use `app.redeploy` only if needed. Validate the same listener, path and profile gates, private reader, signed publisher and pending-job recovery before a real write.

If an update fails, stop only `cyberbaser`. First restore the previous resolved YAML referencing the retained compatible image and validate without touching persistent data. If incompatible migration occurred, do not restore a snapshot automatically: check for intervening approvals, pushes and source changes and obtain separate recovery approval. A failed first install can be stopped with `app.stop` while keeping all data and logs for private diagnosis. No app-delete-with-data, image prune, or blanket chmod/chown is part of rollback.
