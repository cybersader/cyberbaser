Building a contributable wiki is five kinds of work with completely different economics: solve-once software, platform integration that drifts, community-shared configuration, operations that never stop, and writing the content itself. Sorting cyberbaser's work items into those five buckets is what says which parts to build, which to hand to a community, and which anyone would ever pay for. **The short answer: the translation and validation layer is the only genuinely solve-once part, and content creation is irreducibly the user's.**

The [crosswalker project](https://cybersader.github.io/crosswalker/concepts/operational-landscape/) keeps the sibling version of this analysis.

The uncomfortable read: **the green end is nearly done and the red end never will be.** Four of the five build-once items ship today. Moderation and content are permanent, and against a measured maintainer capacity of about 4.7 days per month, that is the constraint everything else has to respect.

Read down the **Content** column: it is red for almost everyone, because content is the whole point. No amount of software removes the need to write the wiki. Cyberbaser's job is to make contributing to it cheap, not to write it.

Read across the **Host / forge** row for the uncomfortable one: it currently owns the contribution surface. Thirteen of seventeen interaction points in the shipped system are somebody else's interface. That is the finding behind [R22](/cyberbaser/reference/open-questions/) — a maintainer who has no forge has no product.

<details>
<summary>The five tiers in detail: what falls in each, and the business analogy</summary>

### Tier 1: First-principles software <span style="color:#10b981">(build once)</span>

Rooted in the nature of the problem, so it stays solved.

| Work item | Why it's resilient | Related |
|---|---|---|
| [Translation layer contract](/cyberbaser/design/translation-layer/) | Obsidian-flavored markdown is stable; the tier definitions are structural | [Principle 2](/cyberbaser/getting-started/principles/#2-obsidian-semantics-must-round-trip) |
| OFM validator (`@cyberbaser/ofm`) | Construct-damage detection is mechanical; the fixture corpus is durable | [Round-trip enforcement](/cyberbaser/agent-context/zz-challenges/translation-layer-round-trip-enforcement/) |
| Publish boundary (`@cyberbaser/publish`) | Default-deny is a permanent safety property, not a feature that ages | [Architecture](/cyberbaser/design/architecture/) |
| Link checker (`@cyberbaser/linkcheck`) | Broken-link detection is arithmetic; the budget ratchet is durable | [Architecture](/cyberbaser/design/architecture/) |
| URL continuity invariant (`cb-urlcheck`) | R23 separates durable public continuity from changeable naming and renderer choices; Cyberbase enforces the cumulative baseline before Pages publication | [Primitives: stable URLs](/cyberbaser/concepts/primitives/#stable-urls) |

**Analogy**: R&D. High upfront cost, near-zero marginal cost. This is the technical moat — restated after the July gate as *byte preservation plus mechanical validation plus governance*, rather than "the best serializer".

### Tier 2: Platform engineering <span style="color:#3b82f6">(build and refine)</span>

Built on the principles but drifts as the ecosystem does. Changes on a months-to-years cadence.

| Work item | What causes change | Related |
|---|---|---|
| Renderer spoke (pinned Quartz for the vault, Starlight for these docs) | Upstream releases; the spoke stays swappable on purpose | [Quartz spike results](/cyberbaser/research/quartz-spike-results/) |
| Splice-only edit surface | Editor tech improves ([CodeMirror](https://codemirror.net/), [Tiptap](https://tiptap.dev/)); the splice contract does not | [Translation layer](/cyberbaser/design/translation-layer/) |
| Identity and trust configuration | Auth standards move; machine identities for agent contributors are unsolved | [Contribution workflows](/cyberbaser/design/contribution-workflows/) |
| Rendering the judgements the pipeline already computes | Every validator emits JSON no human has seen rendered | [Architecture](/cyberbaser/design/architecture/) |

**Analogy**: product engineering. This is the integration work vault owners do not want to do, and therefore the plausible product.

### Tier 3: Community-maintained <span style="color:#eab308">(shared work)</span>

Per-vault or per-renderer work that is shareable: once someone solves it, everyone benefits.

| Work item | Who does it | Related |
|---|---|---|
| Vault templates and starter configs | First vault owner configures, shares a template repo | [Existing work](/cyberbaser/reference/existing-work/) |
| Renderer compatibility profiles | Community tests which spokes clear which tiers; cyberbaser validates | [Translation layer](/cyberbaser/design/translation-layer/) |
| Contribution guidelines and PR templates | Community refines, vault owner customizes | [Contribution workflows](/cyberbaser/design/contribution-workflows/) |
| Theme variants | Community contributes, cyberbaser keeps examples | [Development](/cyberbaser/development/) |

**Analogy**: a marketplace. A config registry (like [crosswalker's config browser](https://cybersader.github.io/crosswalker/features/config-system/)) is where this creates the most value: configured once, reused indefinitely.

### Tier 4: Operational maintenance <span style="color:#ef4444">(ongoing)</span>

Recurs because the outside world changes. Cannot be eliminated, only automated.

| Work item | Why it recurs | Related |
|---|---|---|
| Hosting and deployment | Static hosting (GitHub Pages now, self-hosted Forgejo preferred), edge, domain, TLS | [Architecture](/cyberbaser/design/architecture/) |
| Dependency updates | Upstream ships on its own schedule; security patches | [Development](/cyberbaser/development/) |
| Moderation | Abuse scales with openness; an open queue is an open surface | [Contribution workflows](/cyberbaser/design/contribution-workflows/) |
| Identity plumbing, if used | Token handling, secret rotation, provider API changes | [Contribution workflows](/cyberbaser/design/contribution-workflows/) |

**Analogy**: DevOps. If cyberbaser were a business this is what a subscription funds.

### Tier 5: User work <span style="color:#a855f7">(your effort)</span>

Specific to your vault. No tool eliminates it.

| Work item | Why only you can do it | Related |
|---|---|---|
| Content creation | Only you know what to write | The whole point |
| Contribution review | Only you can judge accuracy in your domain | [Contribution workflows](/cyberbaser/design/contribution-workflows/) |
| Vault organization | Only you know the right structure | [Primitives: vault](/cyberbaser/concepts/primitives/#vault) |
| Deciding who to trust | Only you set the curve | [The Problem](/cyberbaser/concepts/problem/#contribution-on-your-terms) |

**Analogy**: the customer's own work. Cyberbaser sells efficiency, not elimination.

</details>

## Where the money would come from

This is a live open question, not a settled plan. It was deleted from the roadmap by a tidy-up pass in July 2026 and restored, because it is the same question the maintainer keeps asking: *which layer creates enough value that someone would pay for it?*

The candidate answer that keeps surfacing is Tier 2 plus Tier 4 sold together — "bring your vault, get a contributable wiki" — and it is now load-bearing for a second reason. If the maintainer of a wiki must not need GitHub, somebody has to operate the pipeline for them, and that somebody is either a hosted service, a one-click self-host bundle, or a local-first app. Principle 1 constrains all three: they still need storage they control.

<details>
<summary>Tier-by-tier funding sketch, and how it compares to what exists</summary>

| Tier | Funding model | What it looks like |
|---|---|---|
| **Tier 1** (first-principles software) | Open source, grants, sponsorship | The validator and boundary packages are open. Goodwill and ecosystem gravity, not revenue. |
| **Tier 2** (platform engineering) | **Hosted service** | "Bring your vault, get a contributable wiki." The fee covers the edit surface, trust config, and deployment. |
| **Tier 3** (community) | Self-sustaining past critical mass | Templates, renderer profiles, guidelines — contributed. |
| **Tier 4** (operations) | **Included in the fee** | Hosting, updates, moderation tooling. Nobody wants to run this. |
| **Tier 5** (user work) | **The value proposition** | Efficiency, not elimination: your wiki, your content, contributions without git. |

Against what exists today:

- [Obsidian Publish](https://obsidian.md/publish) sells Tier 2+4 at $10/month with **no contribution model at all**.
- [GitBook](https://www.gitbook.com/) sells Tier 2+4 per user with **no vault fidelity**.
- [Notion](https://www.notion.so/) public pages are free to read and give you **no version-controlled source you own**, which fails [Principle 1](/cyberbaser/getting-started/principles/#1-a-single-source-of-truth-you-own).

The claimed gap is the intersection: fidelity across authoring tools, a source of truth you own, contribution without git, and someone else running the plumbing. That is a hypothesis about demand, and it has not been tested on anyone outside this project.

</details>

## What this means for sequencing

- Push work toward Tier 1, where it stays solved. Four of the five Tier 1 items already ship.
- Where that is impossible (Tiers 3-4), build the shared infrastructure so the cost is spread rather than repeated.
- Do not add Tier 4 without a reason. Every runtime is a permanent tax on a maintainer measured at ~4.7 days/month of capacity, which is why a hosted console was priced and declined for the dogfood case.
- The open fork is who operates the plumbing for a maintainer with no forge. That is a scope decision, and it belongs to the maintainer rather than to a research pass.
