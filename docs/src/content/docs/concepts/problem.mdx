A markdown knowledge base is easy to keep and hard to open up. Publish it and you either freeze it read-only or flatten its syntax into whatever a web editor understands; open it to corrections and you end up asking readers to learn git. **Cyberbaser removes both trades: the files stay yours and unflattened, and anyone can propose a change from the page they are reading.**

Obsidian is the first-class authoring surface and the [`cyberbase` vault](https://github.com/cybersader/cyberbase) is our dogfood content, not the scope.

## Three things that have to be true at once

Every existing tool gets two of these and concedes the third.

- **Markdown fidelity** — wikilinks, callouts, embeds, math, and Mermaid survive the trip to the web and back.
- **Low-friction contribution** — a reader who spots a wrong fact can fix it without git, and increasingly without any account at all.
- **No lock-in** — the content is plain files in storage you own, and it still works if cyberbaser vanishes.

<details>
<summary>The tools we checked, scored on all three</summary>

Three categories, none of which occupies the middle:

1. **Obsidian-aware publishers** ([Obsidian Publish](https://obsidian.md/publish), [Quartz](https://quartz.jzhao.xyz/), [Digital Garden](https://github.com/oleeskild/obsidian-digital-garden)). Fidelity is good. Contribution is an afterthought: at best an "Edit" link that drops a reader into a raw markdown editor with no Obsidian syntax support.
2. **Git-backed CMSes** ([Decap](https://decapcms.org/), [Sveltia](https://github.com/sveltia/sveltia-cms), Tina). Open Authoring lets anonymous readers submit PRs. But they parse to their own model and write the whole file back, so wikilinks flatten and callouts become quoted lines. [R12](/cyberbaser/research/v1-build-plan/) measured what that costs and removed this category from cyberbaser's write path entirely.
3. **Docs platforms as wikis** ([Docusaurus](https://docusaurus.io/), [Mintlify](https://mintlify.com/), [GitBook](https://www.gitbook.com/)). Polished reader and contribution UX, opinionated content schemas; forcing a vault into their shape is lossy and stays lossy.

The bet: **this is a translation-and-governance problem, not a new-SSG problem.** Renderers already publish vaults well. What is missing is a layer that guarantees what survives an edit and who is allowed to make one.

## Who it's for

- **You keep a knowledge base in markdown** and want it public without hand-running a publishing stack or moving into a walled garden.
- **A reader spots a wrong fact.** They will fix it in a few clicks; they will walk away from a CLI or a signup.
- **A developer wants to fix a typo** the normal way: edit the `.md`, open a PR, without learning anyone's markdown dialect.
- **An agent maintains content**, proposing updates through the same reviewed pipeline as a human.

And one more the project only recently admitted (R22, 2026-07-26): **the maintainer standing the wiki up should not need GitHub either.** Everything built so far assumes they have an account, a repo, and CI workflows. That is a DevOps-literate developer, a higher bar than the one Principle 3 exists to remove. The fix is an open direction, not a solved one — see [Open Questions](/cyberbaser/reference/open-questions/).

## Contribution on your terms

The deepest part of cyberbaser is not the publisher or even the translation layer. It is *how contribution is governed*, and the governing insight is that **identity gates buy almost nothing while moderation buys everything**. Requiring an email does not stop abuse (aliasing is trivial); requiring a GitHub account mainly filters out the domain expert who spotted the error. The question worth asking is not "who are you?" but "can this hurt anything before a human approves it?" — and if every contribution lands in a moderation queue, the answer is no.

So the maintainer sets the trust curve, [Discourse-style](https://blog.discourse.org/2018/06/understanding-discourse-trust-levels/), and picks how steep it is:

This is live, not aspirational: [`@cyberbaser/trust`](/cyberbaser/research/v1-build-plan/) reads `.cyberbaser/trust.yml` from the PR's base branch (so a PR cannot promote its own author) and classifies each contribution against mechanical gates. It labels a route today; it does not merge.

<details>
<summary>The rest of the governance model: surfaces, DoS, and what we compose instead of build</summary>

**Denial-of-service is a separate problem.** Content abuse is caught by the moderation queue; volumetric abuse (floods, DoS) is handled at the infrastructure edge with rate-limiting and a WAF — see [RA-01](/cyberbaser/design/reference-architectures/self-hosted-forgejo-auth/). Don't conflate the two.

**Multiple surfaces, one pipeline.** A contributor should be able to act from wherever they are:

- **In-page editing** — click edit on the rendered page and change it there. Feasible only because writes are splice-only against the raw file; a CMS that re-serializes the whole document would corrupt it ([R12](/cyberbaser/research/v1-build-plan/)).
- **Obsidian + git** and **direct forge edits**, for people who prefer them.

Every surface feeds the same pipeline: contribution → whatever trust step the maintainer set → moderation queue → merge → live. **Compose, don't build from scratch:** trust levels, moderation queues, and rate-limiting have mature implementations ([Discourse](https://www.discourse.org/)-style trust, serverless contribution bots like [Contribunator](https://github.com/Contribunator/Contribunator) and [Staticman](https://staticman.net/), edge WAFs). Wiring them into one coherent pipeline is a tech-stack design problem. This answers the two biggest [product risks](/cyberbaser/research/assumptions-and-risks/): the account wall, and moderation.

</details>

How much of that is real today: the [live vault site](https://cybersader.github.io/cyberbase/) serves 933 pages, and two rehearsed contributions have gone edit → moderation queue → merge → redeploy → verified live, measured at 3-5 minutes. The gap is item 2's "no account" — every current edit path still runs through a GitHub account. See [Direction](/cyberbaser/getting-started/direction/) for what is built versus what is still a claim.
