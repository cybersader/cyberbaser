Everything in Cyberbaser reduces to the eight ideas below, and two carry most of the weight: **one owner-controlled source** and **exact-change interoperability across replaceable surfaces**. Rendering may use parsed or structured models; accepted external proposals may not regenerate untouched source. The historical “translation layer” and “round-trip editability” names remain as anchors, but R12 changed their mechanism from whole-file conversion to exact source-bound operations.

Each entry is a one-line definition, a picture of the real thing, and a dropdown with why it matters and how cyberbaser uses it.

<details>
<summary>Why it matters, and how cyberbaser uses it</summary>

The vault is the *unit of content* cyberbaser operates on, and it is the durable half of the arrangement. Cyberbaser is delivery; the vault is the thing. If cyberbaser disappears the vault still opens and still works, which is Principle 5.

Concretely: the dogfood vault lives in its own repo, [`cybersader/cyberbase`](https://github.com/cybersader/cyberbase). Cyberbaser never edits it in place or restructures it. A publish boundary (`publish.yml`, default-deny) selects which folders are public, `@cyberbaser/projection` copies the selected files verbatim into a build tree, and a renderer turns that tree into a site. Today 933 Markdown sources are selected and projected into 931 public page URLs. Nothing in the vault is cyberbaser-shaped: no required frontmatter, no rename, no lockfile.

</details>

<details>
<summary>Why it matters, and how cyberbaser uses it</summary>

One source prevents drift between representations, makes conflict resolution tractable (one side always wins), and keeps the mental model small enough to hold.

Today that source is the vault's git repo on its default branch. The published site is rebuilt from it. The maintainer's local Obsidian folder is a working copy and direct authoring surface. An external tool submits a proposal against a known base; the owner-controlled boundary resolves and reviews the exact source operation. The eventual transport may be a commit, local candidate, or another forge-agnostic mechanism.

Git is the current *manifestation* of this primitive, not its essence. Principle 1 says "a source of truth you own", not "a git repo" — and the [source-of-truth research](/cyberbaser/research/source-of-truth/) keeps an off-ramp open, because a maintainer who does not want a forge still needs storage they control.

</details>

<details>
<summary>Why it matters, and how cyberbaser uses it</summary>

A standard markdown link (`[text](path/to/file.md)`) breaks the moment the file moves. Wikilinks reference identity, not location, so a growing knowledge base can be reorganized without turning into a graveyard of dead links.

For Cyberbaser this is the canary. If a proposal does not target `[[X]]`, those exact source bytes must remain `[[X]]`. A rich surface may render the link or represent it as a block internally, but its adapter cannot flatten untouched source to `[X](x.md)` when producing a candidate. `@cyberbaser/ofm` classifies that construct loss as `damage`; exact source operations prevent it by never rewriting the unrelated link.

</details>

<details>
<summary>Why it matters, and how cyberbaser uses it</summary>

Backlinks turn a pile of pages into a connected web. Readers find related material without searching; authors see what points at what. It is the feature that makes a wiki feel like a wiki rather than a flat docs site.

Most renderers already compute them, which is the catch: they each compute them differently, and a link Obsidian resolves is not always a link the renderer resolves. Measured on the live vault, the renderer reported zero broken links while `@cyberbaser/linkcheck` found 779 — so "backlinks work" is a claim that needs a checker, not a feature box. Keeping the graph consistent across swappable renderers is the hub's job, not any one spoke's.

<details>
<summary>Why it matters, and how cyberbaser uses it</summary>

Get this right and every contribution path composes cleanly. Get it wrong and "round-trip editability" is a slogan rather than a property, because a contributor's edit quietly damages four things they never touched.

The mechanism is the tiered feature list: Tier 1 must survive an edit, Tier 2 renders best-effort but never corrupts the source, Tier 3 is not translated and gets a documented workaround. What changed in July 2026 is *how* that is guaranteed. The original plan re-serialized the file from a parsed tree; over 1430 real vault files that reproduced the original bytes 4.6% of the time, so it was abandoned. Writes are now byte splices into the original file, and `@cyberbaser/ofm` is a validator aimed at any other tool that does re-serialize.

</details>

<summary>Why it matters, and how cyberbaser uses it</summary>

Without this, a contributor is locked into whichever surface they started on and the independent-paths idea collapses. It is also the only way the maintainer keeps Obsidian as their daily tool without dreading what a web contribution will do to a file.

It constrains every other decision: no second content authority, no source adapter that re-emits a complete file, and no external surface that bypasses owner review. `ofm-check` mechanically **classifies** each pull-request change as `clean`, `suspect`, or `damage`; it remains report-only rather than enforced (see [Q10](/cyberbaser/reference/open-questions/#q10--what-enforces-the-moderation-policy)).

Honest status: the owner-local and GitHub-backed lanes have run end to end. The single-splice correction primitive and local pilot card are mechanically rehearsed. A generalized rich/WYSIWYG adapter, multi-operation contract, and product review surface are not built.

<summary>Why it matters, how cyberbaser uses it, and the gap that is still open</summary>

This removes the biggest contribution barrier. The alternatives are giving strangers write access (a security problem) or making them fork by hand (exactly the friction being eliminated).

Cyberbaser keeps the pattern but does not prescribe one transport. The evaluated CMS products regenerated whole files, which R12 removed from the source-update path. That rejects their save adapters, not rich browser authoring. A future structured surface remains valid if it emits exact, owner-reviewable proposals. Today the forge's own web editor creates the pull request, and `@cyberbaser/trust` classifies it against mechanical gates before a human looks.

The gap, stated plainly: **the fully anonymous path and the generalized rich-authoring adapter do not exist yet.** Every shipped outside-contributor entry point still needs a GitHub account. The concierge pilot tests only a narrow correction workflow; its seven fields are not the eventual interface or proposal schema.

<details>
<summary>Why it matters, and where this actually stands</summary>

Breaking external links — from blog posts, other wikis, search indexes — is the cardinal sin of a long-lived knowledge site. The whole point of publishing is that the link keeps working.

Where it stands: R16's **verbatim path-derived URLs** remain the live convention. Folder case and natural names are preserved because lowercasing pages independently from assets would break relative references, and the 4,183-path census found zero slug collisions.

R23 separates continuity from naming. A reviewed previous sitemap is the public-address baseline. Every candidate build must retain each baseline URL as canonical or emit a direct, same-origin redirect stub to one current canonical URL. The checker validates both inventories, every candidate route file, `noindex`, the canonical target, the zero-delay refresh target, and the absence of redirect chains.

`@cyberbaser/linkcheck` implements and tests that check. The current public sitemap and a local candidate build each contained the same 931 canonical URLs, with zero failures; one real Quartz alias stub also passed separately. Live publication-workflow installation remains pending. No live URL or deployment changed when R23 was recorded.
