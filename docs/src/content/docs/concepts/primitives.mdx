Everything in cyberbaser reduces to the eight ideas below, and two of them carry the weight: **translation layer** and **round-trip editability**. Get those right and the contribution paths, stable URLs, and single source of truth compose on top for free; get them wrong and the rest is aspiration. The other six are the vocabulary the rest of these docs assume you have.

Each entry is a one-line definition, a picture of the real thing, and a dropdown with why it matters and how cyberbaser uses it.

<details>
<summary>Why it matters, and how cyberbaser uses it</summary>

The vault is the *unit of content* cyberbaser operates on, and it is the durable half of the arrangement. Cyberbaser is delivery; the vault is the thing. If cyberbaser disappears the vault still opens and still works, which is Principle 5.

Concretely: the dogfood vault lives in its own repo, [`cybersader/cyberbase`](https://github.com/cybersader/cyberbase). Cyberbaser never edits it in place or restructures it. A publish boundary (`publish.yml`, default-deny) selects which folders are public, `@cyberbaser/projection` copies the selected files verbatim into a build tree, and a renderer turns that tree into a site. 933 of the vault's pages are published this way today. Nothing in the vault is cyberbaser-shaped: no required frontmatter, no rename, no lockfile.

</details>

<details>
<summary>Why it matters, and how cyberbaser uses it</summary>

One source prevents drift between representations, makes conflict resolution tractable (one side always wins), and keeps the mental model small enough to hold.

Today that source is the vault's git repo on its default branch. The published site is rebuilt from it. The maintainer's local Obsidian folder is a working copy. A web edit is a commit against it, spliced into the existing bytes rather than re-serialized, so the repo never has to reconcile two dialects of the same file.

Git is the current *manifestation* of this primitive, not its essence. Principle 1 says "a source of truth you own", not "a git repo" — and the [source-of-truth research](/cyberbaser/research/source-of-truth/) keeps an off-ramp open, because a maintainer who does not want a forge still needs storage they control.

</details>

<p class="cb-fig-cap">Move the file? The link still works, because it never pointed at a path.</p>

<details>
<summary>Why it matters, and how cyberbaser uses it</summary>

A standard markdown link (`[text](path/to/file.md)`) breaks the moment the file moves. Wikilinks reference identity, not location, so a growing knowledge base can be reorganized without turning into a graveyard of dead links.

For cyberbaser this is the canary. `[[X]]` written from any surface must stay `[[X]]` in the file. The moment a write path flattens it to `[X](x.md)`, round-trip fidelity is gone and so is the reason the project exists — which is exactly what `@cyberbaser/ofm` calls `damage` and exits non-zero on. It is also why writes are byte splices: nothing that never reads the link can degrade it.

</details>

<details>
<summary>Why it matters, and how cyberbaser uses it</summary>

Backlinks turn a pile of pages into a connected web. Readers find related material without searching; authors see what points at what. It is the feature that makes a wiki feel like a wiki rather than a flat docs site.

Most renderers already compute them, which is the catch: they each compute them differently, and a link Obsidian resolves is not always a link the renderer resolves. Measured on the live vault, the renderer reported zero broken links while `@cyberbaser/linkcheck` found 779 — so "backlinks work" is a claim that needs a checker, not a feature box. Keeping the graph consistent across swappable renderers is the hub's job, not any one spoke's.

<details>
<summary>Why it matters, and how cyberbaser uses it</summary>

Get this right and every contribution path composes cleanly. Get it wrong and "round-trip editability" is a slogan rather than a property, because a contributor's edit quietly damages four things they never touched.

The mechanism is the tiered feature list: Tier 1 must survive an edit, Tier 2 renders best-effort but never corrupts the source, Tier 3 is not translated and gets a documented workaround. What changed in July 2026 is *how* that is guaranteed. The original plan re-serialized the file from a parsed tree; over 1430 real vault files that reproduced the original bytes 4.6% of the time, so it was abandoned. Writes are now byte splices into the original file, and `@cyberbaser/ofm` is a validator aimed at any other tool that does re-serialize.

</details>

<summary>Why it matters, and how cyberbaser uses it</summary>

Without this, a contributor is locked into whichever surface they started on and the independent-paths idea collapses. It is also the only way the maintainer keeps Obsidian as their daily tool without dreading what a web contribution will do to a file.

It constrains every other decision: no lossy transform, no CMS-specific schema that differs from the vault's, no write path that re-emits a file it did not need to change. It is enforced mechanically rather than by review — `ofm-check` runs on every pull request and classifies the change as `clean`, `suspect`, or `damage`.

Honest status: proven for the paths that exist. Two live contributions have gone edit → queue → merge → redeploy → verified live. The in-page WYSIWYG surface, which is the hardest case, is not built.

<summary>Why it matters, how cyberbaser uses it, and the gap that is still open</summary>

This removes the biggest contribution barrier. The alternatives are giving strangers write access (a security problem) or making them fork by hand (exactly the friction being eliminated).

Cyberbaser takes the *pattern* but not the products. The CMS category that popularized it re-serializes whole files, which is what R12 measured and removed from the write path, so today the fork-and-PR dance is done by the forge's own web editor and the review happens in the pull request. `@cyberbaser/trust` classifies each one against mechanical gates before a human looks.

The gap, stated plainly: **the fully anonymous path does not exist yet.** Every current entry point still needs a GitHub account, which means the persona Principle 3 was written for has no working route. That is tracked as an open question, not a shipped feature.

<details>
<summary>Why it matters, and where this actually stands</summary>

Breaking external links — from blog posts, other wikis, search indexes — is the cardinal sin of a long-lived knowledge site. The whole point of publishing is that the link keeps working.

Where it stands: the site ships **verbatim paths** today. The URL is the vault path as written, folder case and all, because lowercasing pages while assets keep their natural case breaks relative references. That is a deliberate v0 choice, safe only because a census of 4,183 paths found zero slug collisions.

What is undecided is the durable scheme: a frontmatter slug, a permanent hash, or a title-slug with redirects generated on rename. Until that is chosen there is no **URL freeze**, so a reorganization today still moves URLs. A slug-diff gate that fails the build on an unintended URL change is the next step. Tracked in [Open Questions](/cyberbaser/reference/open-questions/) and [the renderer/URL proposal](/cyberbaser/research/proposal-renderer-urls/).

</details>
