Design principles are constraints on future decisions. Each principle below:

1. **States a rule** (what it forbids or requires)
2. **Justifies it** with a reason grounded in prior art or a specific failure mode
3. **Says what it rules out**, so it's falsifiable: if future evidence overturns the reason, the principle goes too

These are the current working constraints for the v1 Build phase. Evidence can sharpen or replace them, but implementation must respect them until a decision record says otherwise.

---

## 1. A single source of truth you own

**Rule:** One authoritative copy of the content, in a version-controlled vault the maintainer owns. In the current manifestation that is a git repo (`cybersader/cyberbase` on GitHub today). Accepted changes must return to that source as byte-preserving edits; no contribution surface becomes a second authority. No sidecar content database, parallel source store, or vendor-proprietary format may replace it. Git-backed is how version control happens today, not the essence, and the general product must not require contributors or maintainers to operate GitHub.

**Why:** Every Obsidian-publishing tool that's taken off has one failure mode in common: they store content in a place the user doesn't own (Notion workspaces, Publish's proprietary CDN, CMS databases). When the tool goes away or changes pricing, the content is trapped. A user-owned, version-controlled source of truth means cyberbaser can disappear tomorrow and the vault still works perfectly on its own.

**Rules out:**
- Sidecar databases for "enriched" content
- A CMS or sidecar database that becomes a second content authority
- An adapter that synchronizes by regenerating the authoritative source
- Content that only exists in a CDN or rendered-HTML form
- Any solution where the vault is not a self-sufficient Obsidian vault in isolation

## 2. Authoring semantics and untouched bytes must survive edits

**Rule:** Any authoring-tool feature that renders in the vault and on the web must remain functionally intact after an accepted edit (Obsidian is the first-class case). R12 makes the external-proposal mechanism non-negotiable: every Cyberbaser-mediated application operates on exact source bytes, and **no adapter may regenerate the untouched remainder of the file**. `@cyberbaser/ofm` validates changes; it never rewrites the file. Cyberbaser does not replace or mediate the owner's primary local editor.

**Why:** The 1,430-file gate measured only **4.6% exact byte identity** after whole-file AST serialization. The failure was architectural formatting normalization, not a tuning problem. Preserving untouched bytes by construction prevents a small correction from flattening wikilinks, callouts, block references, spacing, line endings, or unrelated author choices.

**Rules out:**
- Lossy transforms (e.g., `[[Page]]` → `[Page](page.md)` on save)
- "Simplified" markdown dialects that drop Obsidian extensions
- CMS save adapters that strip unknown syntax or regenerate the whole file
- Publishing pipelines that render-then-edit instead of edit-then-render
- Any "safe" writer whose correctness depends on serializing the untouched remainder of a document

**Load-bearing evidence:** the [R12 gate measurement](/cyberbaser/research/v1-build-plan/#gate-result-run-2026-07-25) and the [translation layer](/cyberbaser/design/translation-layer/). Future rich, raw, WYSIWYG, CMS-like, forge, or agent surfaces remain allowed, but their adapters must emit exact source-bound proposals rather than reopen the serializer question.

## 3. Contributors shouldn't need git or a forced account

**Rule:** At least one contribution path must work for a domain expert who has never used git, cloned a repo, understood branching, or created an account merely to report a correction. Accounts may supply trust signals later; they are not the safety mechanism.

**Current state:** this product path has **not shipped**. The live site's edit link opens GitHub and therefore requires a GitHub account. [Q09 remains open](/cyberbaser/reference/open-questions/#q09--what-is-the-contribution-path-for-someone-with-no-account). [`OD-01`](/cyberbaser/research/owner-self-dogfood/) exercised the correction boundary once with the maintainer switching reader and owner contexts; it is operational evidence, not an endpoint, editor, writer, independent human result, or proof that the rule is satisfied. The larger reader pilot remains available later before stronger usability claims.

**Why:** The biggest barrier to community contribution on existing markdown wikis is not only git fluency, but the platform wall around it. Domain experts, subject-matter writers, and students may be able to improve a page yet reasonably refuse a forge account. The contribution must still arrive as a bounded proposal that the owner can review safely.

**Rules out:**
- "Just send a PR" as the only contribution path
- A GitHub or forge account as the only way to report a useful correction
- Required CLI tools for contributors
- Documentation that assumes git knowledge
- Merge conflict resolution that requires a terminal

## 4. Every offered contribution path must work independently

**Rule:** Any contribution path Cyberbaser offers must work end-to-end without being a client of another contribution surface. This principle does **not** require three named paths, a Web CMS, or a particular interface. Direct owner authoring and external proposals are distinct lanes; independence does not require them to share an editor, moderation UI, or source-application mechanism. Today the owner-local Obsidian+Git lane and GitHub's account-required external proposal are operational; the account-free path is still under experiment.

**Why:** A reader-facing intake must not depend on a live Obsidian instance, and a local authoring path must not depend on an intake service being deployed. Independence keeps one surface's outage, retirement, or replacement from blocking the others.

**Rules out:**
- Architectures where one path is a privileged client of another
- Shared session state between paths
- Preview pipelines that can only render through one surface

## 5. The vault is primary; cyberbaser is derivative

**Rule:** If cyberbaser disappears tomorrow, the underlying knowledge base must remain fully functional in its native authoring tool (Obsidian, in our case) on its own. No cyberbaser-specific files should be required to use it.

**Why:** This is the vendor-lock-in escape hatch. It also forces good architectural hygiene. If you find yourself adding a build artifact to the vault, or requiring cyberbaser-side tooling to use the vault locally, you've violated separation of concerns. The vault is the durable artifact; cyberbaser is the delivery mechanism.

**Rules out:**
- Vault-side plugins that cyberbaser requires to be enabled
- Frontmatter fields that cyberbaser writes back to files
- Build artifacts committed to the vault repo
- Any coupling where "cyberbaser is broken" implies "vault is broken"

## 6. Research before implementation

**Rule:** No feature ships without a corresponding principle (or explicit trade-off entry) that justifies it. If you find yourself writing code for something that isn't grounded in the concepts / prior art / principles pages, stop and write the justification first.

**Why:** The old approach (jumping from "it would be cool if..." to `git commit`) is exactly how the previous iteration ended up with a parked Phase-0 prototype that doesn't answer the hard questions. The reinit inverted the order. Writing the reason takes less time than undoing a misguided implementation.

**Rules out:**
- Speculative refactors without a written motivation
- "Let me just try it and see" commits on the critical path
- Adding dependencies without a documented trade-off
- Promoting an experiment into product work before its precommitted decision rule has evidence
