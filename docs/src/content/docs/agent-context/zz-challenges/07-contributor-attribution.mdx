**Status:** R24 completed investigation item 1 for the current dogfood path. A genuine cross-repository PR from a second account carried one contributor-authored commit. After the owner performed a normal squash merge, authoritative `main` commit `4a40055` retained the contributor's GitHub-mapped name, noreply address, and account as author; GitHub was the committer and the owner was recorded separately as the PR merger. The live publication passed. [Q08 is closed](/cyberbaser/reference/open-questions/#q08--does-the-fork-flow-actually-attribute-the-contributor).

That result repairs the legal dependency for this one measured path. It does not complete this brief: visible page credit, contributor profiles, trust-history computation, anonymous and pseudonymous attribution, multi-commit squash behavior, and other forges remain unresolved. The second account was controlled by the maintainer, so this is operational evidence rather than independent-contributor usability evidence.

**What exists today, against this brief's own deliverable table:**

| Path | How identified | What a reader sees |
|---|---|---|
| Obsidian + Git push | commit author | nothing |
| Web CMS PR | n/a — no CMS in the write path (R12) | n/a |
| GitHub "Edit this page" | contributor remains the authoritative squash-commit author for the measured one-commit fork path | nothing |
| Anonymous | proposal is anonymous at the trust floor; no public credit mechanism exists | nothing |

The live site's layout is breadcrumbs, title, date and reading time, tags, and an edit link. There is no author component, no contributor list, no avatar, and no contributors page. The one person-shaped element points *outward* to GitHub: it invites contribution, it does not credit it.

**Why this still matters beyond UX.** [Legal & Governance](/cyberbaser/design/legal-and-governance/) can now point at measured Git history for the current GitHub path, but every other accepted path needs an explicit attribution rule. Item 2 (pseudonymous identity) has one design fragment in the [hub BOM](/cyberbaser/research/proposal-hub-bom/): a fixed bot identity plus a stable pseudonymous submission ID, and never a network identifier in a commit, since git history is permanent. The implemented proposal contract keeps identity claims inert and preserves the anonymous trust floor; neither mechanism supplies visible credit.
:::

## The assignment

The [vault vision](/cyberbaser/agent-context/zz-log/2026-04-13-vault-vision-mining/) includes **"show contributors at the top of each page with pic and contributors page."** Contributions come from 3+ surfaces: Obsidian+Git push, Web CMS PR (fork-and-PR via Decap), and GitHub direct edit. **Your job: design a unified attribution model that works across all paths.**

This isn't just a UI question — it's a data-model question. Where does contributor identity live? How does it survive the translation layer? What about anonymous contributors?

## What to investigate

1. **Does git blame work across all paths?** When a contributor edits via Decap's Open Authoring (fork → branch → PR → merge), does `git blame` correctly attribute the lines to the contributor's GitHub account? Or does it show the merge commit author (the vault owner)? Test with a real Decap Open Authoring workflow.

2. **Anonymous / pseudonymous contributors.** The vault vision mentions "anonymous secure editing sessions." If a contributor doesn't have a GitHub account, how are they attributed? Options: anonymous with session ID, email-based identity, OAuth with non-GitHub providers. What's the CLA implication — can you accept anonymous contributions under [AGPL + CLA](/cyberbaser/)?

3. **Contributor profiles.** The dream: photos, contributor pages, edit history, contribution stats. Where does this data come from? GitHub API (avatar, profile link)? A custom contributor database? What about contributors who use different identities across paths (GitHub account for PRs, different name in Obsidian commits)?

4. **Attribution in the published UI.** How do existing wikis show contributors? [Wikipedia's history tab](https://en.wikipedia.org/wiki/Special:RecentChanges), [GitBook's page history](https://docs.gitbook.com/), [Notion's page analytics](https://www.notion.so/). What UX patterns work for a reader who wants to know "who wrote this"? Where does it go — page header, footer, sidebar, dedicated tab?

5. **Attribution through the translation layer.** If contributor info is stored in git history, does the Astro build extract it? Starlight has `lastUpdated: true` (git-based). Can it also extract contributor LIST per page? Does [astro-loader-obsidian](https://github.com/aitorllj93/astro-loader-obsidian) support this?

6. **The CLA + attribution interaction.** The [CLA](/cyberbaser/) grants the maintainer sublicensing rights. Does attribution need to be legally preserved (like Creative Commons BY), or is it purely a UX/community feature? What does the AGPL require regarding contributor acknowledgment?

## What success looks like

- **Attribution data model**: where contributor identity is stored (git, CMS metadata, external DB), how it's extracted at build time, how it's displayed
- **Path-specific attribution table**: for each contribution path (Obsidian+Git, Web CMS, GitHub direct, anonymous), how the contributor is identified, what data is available, what's lost
- **UI mockup or reference**: sketch of how contributor info appears on a published page (can be ASCII or a reference to an existing implementation)
- **CLA/legal summary**: what's required vs optional for attribution
- **Validity**: holds until the CMS choice is finalized (attribution implementation depends on CMS capabilities)
