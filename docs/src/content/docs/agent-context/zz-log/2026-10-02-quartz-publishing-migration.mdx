## Decision and rationale

After read-only inventory and bounded public comparison, the owner explicitly chose: **“Yes, use Quartz and preserve the content and existing URLs.”** This selects a new presentation for Cyberbase rather than pixel parity with Obsidian Publish. Reuse the existing Quartz route where it meets the preservation requirements; do not build a broader publishing system by momentum.

Preserve intended public content/assets and existing publicly used URLs on `cybersader.com`, including `/README`, relevant deep links, exact case, and encoded paths. Never expand publication to all repository/vault content or republish deliberately excluded/private notes for parity. Newly discovered exposure conflicts require owner resolution.

Cyberbase is the owner's desktop Obsidian vault. GitHub holds content, but desktop freshness is unverified. No new management integration or source authority follows. Quartz remains a replaceable renderer, not a global Cyberbaser requirement; authoring and source backends remain replaceable.

## Implementation and acceptance gates

The [canonical practical plan](/cyberbaser/development/quartz-publishing-migration/) records five stages, none completed by this entry:

1. **Pin and inventory:** verify saved desktop changes and writers/sync, choose the source baseline, inventory actual Publish pages/assets/URLs and current Quartz routes, then classify direct pages, equivalent redirects, fragment/assets, and unresolved mappings. No complete manifest exists yet; authentication-blocked evidence stays unknown without bypass.
2. **Minimum corrections:** let the manifest determine README handling, links/assets, path/base-URL differences, and relevant asset-only trigger behavior. Preserve untouched source bytes, no whole-file serialization or mass renames.
3. **Contained preview acceptance:** separately authorize a disposable renderer preview with pinned inputs, machine-check selected content and every known old URL, anchors and assets, then obtain representative owner browser acceptance with explicit coverage limits. Normal owner-alpha startup can start intake and recover jobs; it is not passive preview.
4. **Production cutover:** obtain explicit owner approval for the production pins/configuration and domain routing only after evidence passes. Retain source/build/output identities, and establish separately verifiable recovery procedures for source, site, and DNS. Exact DNS commands await actual setup. Verify production content and old URLs before declaring replacement accepted.
5. **Cancel last:** retain Publish until owner acceptance of production and old-URL verification. Cancellation needs independent authorization; subscription/service retention and recovery implications remain uncertain.
