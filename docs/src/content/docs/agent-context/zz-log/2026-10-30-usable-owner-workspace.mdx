## The next milestone is routine use

The immediate integration milestone is a usable private workspace for maintaining an existing public site: open an already-public page, edit it, check the result, publish through an approved route, and confirm the intended public URL changed. Ordinary owner authoring is distinct from reviewing and applying external proposals.

This clarifies the operational priority, not a new product identity or editor selection. The chosen operating-home and renderer direction remains in the [publishing migration plan](/cyberbaser/development/quartz-publishing-migration/). Cyberbaser stays independent of a particular host, transport or renderer.

## Separate built components from a connected workflow

The owner-local editing and publishing pipeline was built and previously exercised. An available browser editing surface, existing source copies, a saved configuration and earlier publishing evidence do not establish that the current integration is ready for routine use.

Before activation, identify the editable source, its active writers, the publishing input and the intended public endpoint. A room's backing folder is not automatically the owner-approved publishing authority. A working renderer target is not automatically the existing public site. Starting a writer with recovery behavior is not a read-only readiness check.

The next planning work is the smallest source-and-publication connection that makes the owner loop usable, not another editor project or a larger host test framework. No source cutover, config activation, live write, publication, domain change or subscription cancellation is authorized by this priority clarification. Snapshot expansion and the proposed bounded export experiment remain held.

## Implementation approved, live publication still gated

The owner selected the existing Quartz site for the first usable loop. The current main website stays unchanged until a separately reviewed cutover. The approved implementation is limited to body-text changes on one explicitly mapped, already-public page: edit in the chosen workspace, prepare an exact private review, deliberately Publish, and follow the existing publisher through live confirmation.

A fresh isolated publishing checkout was prepared without changing existing working copies. It is a delivery mechanism, not another authoring location. The optional source-input foundation is implemented against synthetic reader evidence; independent static review identified three validation repairs, which the builder has now implemented. They cover unexpected edit-session metadata, unsanitized cloning errors and a filename-extension edge case. The reviewed byte-binding logic had no identified defect in the inspected scope; independent verification subsequently confirmed the repairs and found no verified defect in the bounded foundation/controller scope. The foundation validates one policy-bound mapping, exact UTF-8 bytes, positive source version, byte count and digest, then reuses the existing exact-operation primitives without writing source or starting a job. The authenticated panel and runtime connection have since been implemented and are undergoing independent verification. The real workspace connection, normal workspace entry and live activation remain incomplete; routine use is not yet established. The integration will reuse the existing exact-operation and durable publication pipeline rather than introduce another writer or deployment mode.

Activation also depends on a coherent single-note read: returned text must match the declared source version and digest. A stable filesystem read alone cannot establish this when the host writes files in place. A narrow generic read-integrity repair is being coordinated separately; this does not resume snapshot expansion or the held export experiment.

Implementation approval covers scoped code, isolated preparation and synthetic verification. It does not authorize real source reconciliation, access grants, production startup, a content commit or push, publication, or a domain change. Before the first real publication, review the complete selected-content difference from the last deployed revision, not merely the one new edit or the workflow's trigger paths.

### Connected synthetic browser rehearsal passed

A subsequent actual-loopback HTTP reproduction returned correctly framed, valid preparation JSON. That verifies that transport case; it does not recover the first browser run's discarded response. The browser test was then changed to keep actual HTTP status checks while deriving the draft identity from the real review navigation and checking its immutable stored evidence. This avoids navigation-sensitive response-body retrieval without intercepting requests, changing the application or dropping exact-byte, source-version, mapping or job-identity assertions.

The resulting single corrected run passed: one browser test, 49 assertions, 3.26 seconds. It exercised normal authentication, preparation (HTTP 201), all four review modes, explicit Publish (HTTP 202), the actual completed job page and a later replay (HTTP 202). Immediate double activation sent one client Publish request. The replay returned the same deterministic job. The fixture recorded exactly one publication source application, one commit and one local-bare push beyond its baseline setup, and confirmed the exact candidate bytes and matching local/remote commit. Private source references remained absent from responses. The owned browser and temporary root were removed.

Renderer/pre-apply rendering, deployment observation, live confirmation and local rebuilding were explicitly simulated. The coordinator inspected the final JSON receipt and both review/completion screenshots, including their visible simulation notice; the coordinator did not rerun the browser. Earlier failed receipts are preserved, not replaced. This is connected synthetic acceptance, not a real-site publication, live host compatibility, human usability acceptance or a full recovery/renderer certification.

The [canonical rehearsal guide](/cyberbaser/development/owner-publication-rehearsal/) now supplies one command from the repository root: `bun run --cwd docs review:owner-publication`. The guide explains the isolated browser, cleanup, real local effects and simulated stages. Its package-script value and JSON syntax were checked; no docs build or human-invoked headed-launcher acceptance occurred. The remaining real-use gates are the coherent supported source read, private connector, single-page enrollment, normal workspace navigation and separately approved activation/publication. The main website remains untouched.

## Human review rejected the interface

After the successful synthetic run, the maintainer rejected the interface as unusable because of its poor UX/UI design. Mechanical acceptance remains valid at its measured scope, but the owner-facing usability checkpoint failed. Offering the fixture before establishing a designed baseline shifted basic design work onto the maintainer.

The next work starts with the owner's task, information hierarchy, reading flow, actions and states, then a coherent visual system in the actual publication screens. It is not a cosmetic pass or another disconnected mockup. The verified publishing engine and safety boundaries remain underneath; internal machinery should not dictate the interface. Internal desktop/mobile visual critique must precede another owner invitation. The maintainer's time should test product fit, not whether basic design work was done.

The maintainer supplied [Impeccable](https://github.com/pbakaus/impeccable), [taste-skill](https://github.com/Leonxlnx/taste-skill) and [Interfaces](https://interfaces.dev/) as references. A bounded source/design review is underway; no claims about their contents or visual examples precede that inspection. No source-access, activation or publication gate changes follow from the redesign direction.

## Human involvement belongs at useful checkpoints

Required sign-in and scoped access approvals remain owner actions. Technical verification and routine debugging remain agent work. The owner should evaluate a coherent workflow when it can demonstrate the actual task, not a disconnected mockup or isolated infrastructure test.

Progress updates should state what is built, what is actually connected, what can be used now and the next missing connection before discussing implementation details.

## Supporting reload probe stopped with a limitation

Following the [byte-preservation regression checks](/cyberbaser/agent-context/zz-log/2026-10-29-byte-preservation-regression/), two bounded local runs exercised modification of existing synthetic notes and attempted a receiving-client reload check. Writer-side before/after/final-byte checks passed, and relay observations attributed the target writes only to the writer.

The first receiving-client assertion failed because it inferred its role before a startup marker was available. A narrow correction passed four focused deterministic groups, but the second run failed because the target note was not yet in the receiving file index during plugin startup. Both runs exited nonzero and recorded cleanup. These are failed probe acceptance results, not demonstrated byte loss and not successful post-reload acceptance. No further probe expansion is selected.

Private reports preserve the exact evidence and personal integration details. No production build, service activation or publication was performed for this record.
