## Maintainer direction

Three things from the maintainer in this session, recorded rather than inferred:

- The core shape of the [Owner application event](/cyberbaser/design/owner-application-event/) proposal is accepted: a second explicit owner act, the existing Save pipeline as the only writer, create-once events, no auto-apply.
- "Nobody will ever be running commands." The act belongs in the UI. The backend under it must stay resilient and machine-callable. So the first-draft answer of a terminal script was wrong for this product, and the act is a button on the approved receipt with the same privileged API behind it.
- Questions to the maintainer must run as an upside-down funnel, high level first, for someone who holds the vision but is not in the weeds. The earlier question set was too abstract and referential. On the three follow-up questions (aim, deliberateness, limits) the maintainer stated no preference, so the recommended answers were taken and are recorded on the design page.

## What was built

- `apps/owner-alpha/src/proposal-application.js`: the event artifact and its closed validator; a read-only status (`not-decided`, `rejected`, `stale`, `unapplicable`, `eligible`, `applied`); derivation of the pipeline's edit session and source operation from the prepared input and the exact blob, with the owner pipeline's own rules applied first; the rendered-site slug resolver that reads the owner edit link back from the built site; and the act itself, which prepares the input if missing, re-checks everything, requires a clean checkout at the checked tip, records the event, and starts the job.
- The review service gained `applicationStatus` and `apply`; the handler gained `POST /api/review/<queueId>/apply`; the receipt gained the application step in four states with one sheet; `public/apply.js` drives it and hands the owner to the job page. The real server wires the pipeline's Save entry, the site root, and the owner origin into the service. The checkpoint fixture shows "not available in this setup".
- Two source helpers (`liveUrlForSlug`, `pathMatchesPolicy`) and two input-adapter helpers (`decisionDigest`, `readApprovedProposalInput`) are now exported.

Canonical guide: [Applying an approved suggestion](/cyberbaser/development/applying-approved-suggestion/).

## Design changes from the draft

- The proposed off-by-default `applications.enabled` config block was dropped. The act already runs only under the durable policy that lets a Save commit and push; a second switch for the same effect would be a knob without a boundary behind it.
- The proposed provenance trailer in the commit message was deferred. The pipeline reconstructs the expected message from policy when it reconciles a commit after a crash, so a custom message would break that path. Provenance is durable in the event and in the job's session `origin`.
- Inputs are prepared as part of the act, so no one has to run the input script first.
