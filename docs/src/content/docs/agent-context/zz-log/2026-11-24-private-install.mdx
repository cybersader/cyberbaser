## Why

Owner decision (relayed by the Cyberchief project lead): for the next step, "Real install, private (Recommended)": two private GitHub repositories, Cyberbaser installed on the owner's machine with the phone paired, nothing public, cyberchief.me untouched, the 17 sample pages kept out. Three things blocked that install: the installer could only use the bundled renderer, every publish waited on a GitHub Pages deployment that a private site never has, and nobody had run the flow through the installed, hardened services with a real renderer.

## What now works

**Install with the site's own renderer.** `cyberbaser install --renderer <dir> --renderer-name <name> --renderer-quartz-commit <sha> --renderer-fingerprint <a,b,c | @file>` checks the assembled renderer (one real directory, an executable `build`, no link that leaves it, every fingerprinted entry present, a Quartz checkout on the pinned commit), copies it to `/var/lib/cyberbaser/renderers/<name>`, gives it to the node account and removes every group and other write bit. It is outside every checkout and the program, and the publisher account cannot read it. The layout file carries the renderer section, so setup writes it into the node config. A bad renderer stops install before anything changes.

**The node may build offline in the hardened service.** The node unit now allows only user and network namespaces (`RestrictNamespaces=user net`), which the renderer slot needs for its no-network build (`unshare --user --net`). The publisher keeps `RestrictNamespaces=yes`. `patch` and `unshare` are checked at install when a renderer is given. The Cyberchief renderer's `build` (bash, `node` as the program's own runtime, `patch`) ran inside the service with no network.

**Private-only publication.** `workflow.provider: "private-site"` (with only `branch`). The repository stays a GitHub repository and the GitHub App still holds the push credential. After the publisher pushes, the deployment is the node rebuilding its private site from that exact commit (`provider: private-site`, `publication.site: private`), and the live check reads the page from the node's own reader on its private address. The evidence keeps its usual shape and is marked `evidence: private-site-live`. `live.baseUrl` is the page identity only (the vault's declared `site.baseUrl` when it has one, so link checks and addresses agree with the renderer). Nothing calls a Pages, Actions or deployment API.

**Setup offers it.** With `install --site private`, the website step says the site stays on this machine, shows the private address, and offers **Keep it private** first, with "Use a public website instead" beside it. The finished config has no Pages workflow.

**The plugin says so.** A bundle's progress carries `site: "private"` and the node's private link; the checklist's last step and the Live notice read "Live on your private site", and View on site opens the private address.

## Found on the way

- The phone works out new public pages from its own vault's `publish.yml` and `.cyberbaser/site.yml`. Without them it refuses to approve a new post (`approval-public-unknown`), so the phone vault must hold those two files.
- This worktree's `apps/owner-alpha/node_modules` held a stale copy of `@cyberbaser/proposal` (no `page-bundle.js`); `bun install --frozen-lockfile` fixed it. The install script runs it before building.
- The container harness did not copy the plugin's `js-yaml`, so its headless phone could not start; fixed in `run.sh` (this also affects `setup-e2e.sh`).
- Covers are not shown on the Cyberchief post page (feed cards only), so the check is the image itself, confirmed byte for byte by the live check.
