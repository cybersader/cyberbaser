## Why

The [owner review port](/cyberbaser/agent-context/zz-log/2026-08-22-owner-review-port/) left four questions for the maintainer: default mode, whether R1 semi-rendering reads well enough, dock prominence, and whether Compare earns its place. The [cloud review handoff](/cyberbaser/agent-context/zz-log/2026-09-24-cloud-review-handoff/) asked for a bounded session that prepares that checkpoint without running or passing it. This is that session.

## What changed

**Canonical pack.** [Owner review maintainer checkpoint](/cyberbaser/development/owner-review-checkpoint/) is new. It gives the launch command and ports, the seven proposals and what each exercises, a suggested order, five cold comprehension questions and four direction questions, explicit pass and fail conditions for reading modes, semi-rendering limits, the decision dock, Compare, and the decision-only meaning of Approve, a recording template, and what a pass does and does not unlock. Approve being understood as decision-only is a hard gate that cannot be traded against the presentation areas.

**Realistic corpus in the real launcher.** `bun run --cwd docs review:owner-alpha` no longer seeds three `teh` typo proposals on a one-line page. It now seeds seven pages and submits seven proposals through the real account-free intake: a long paragraph rewrite, a sourced number and date correction with a reference link, a link destination inside an ordered list, a pure deletion of a blockquote notice, a YAML frontmatter value, one paragraph in a five-section page, and a sentence on a page holding a callout, a table, a task list, a wikilink, and inline code. The corpus and the shared owner configuration live in `apps/owner-alpha/bin/review-checkpoint-corpus.js`. The page text is adapted from the executable fixtures in `@cyberbaser/proposal-fixtures` so the two research surfaces show comparable material, without adding that package to the owner-alpha dependency closure.

**Fixture helper.** The intake test helper's `createFixture` accepts an optional `pages` list and exposes `pageIdFor(path)`, `checkout`, and `revision`. Its default is unchanged, so every existing intake and acceptance test keeps its one-page fixture.

**Guarding the claims.** `apps/owner-alpha/test/review-checkpoint-corpus.test.js` submits every corpus proposal through the real intake, loads it with the same field selection the private review socket sends, revalidates it with real Git through `validateOwnerReviewEvidence`, builds the same projection the review page builds, and asserts the `expects` block on each proposal: block kinds present, constructs degraded to exact source, inline token types, removal and addition segments, the changed block's kind for the frontmatter case, and the heading count for the long page. The docs table cannot claim something the projection does not do.

**Stale flow corrected.** The [owner proposal UI review](/cyberbaser/development/owner-proposal-ui-review/) page still described a three-view surface that opened in Proposed with an Exact tab. It now describes the four server-rendered modes with Changes as the current default, the 256 KiB reading bound, and the seven-proposal launcher, and it points at the pack.

## Boundaries

The checkpoint was not run. No area is marked pass or fail. No roadmap decision changed. Nothing merged, deployed, or exposed an intake lane, and approval still records intent only. The corpus is synthetic-mechanical research data, and a green corpus test is not maintainer comprehension.
