The earlier [owner-first publisher step](/cyberbaser/agent-context/zz-log/2026-11-21-owner-first-publisher/) remains necessary, but its browser-first acceptance example was not the owner's ordinary writing workflow. The owner usually writes in a workspace or Obsidian mobile, often with agent assistance. The [editing and trust roadmap](/cyberbaser/design/editing-and-trust-roadmap/#publish-from-where-you-write) now treats these tools as first-class clients and the website editor primarily as a contribution client.

The design distinguishes three events: save a private draft, authorize one selected version for publication, and confirm that version on the public page. Agent work stays attributable where evidence permits and otherwise unattributed; running inside an owner's tool never transfers owner authority. Iroh can carry commands but cannot select the canonical source or reconcile independent copies.

The revised phase gates include a phone app interrupted immediately after Publish: resume from the same request without a second job. Making a previously private note public has its own selection preview and owner decision, separate from editing an already-public page. Any future agent authority to publish on behalf of the owner requires a separate scoped, revocable grant and an audit record, not just a higher contribution tier. These are acceptance conditions, not implemented client capabilities.

A source review of the workspace software (relayed, not verified live) found no route from a workspace to Git and no export of changes against a base revision; the workspace's converged text is authoritative for its own content and identifies Markdown by text digest, not Git bytes. The roadmap records the resulting binding rule (workspace text digest plus Git base, refuse non-round-trippable files) and three candidate seams, none selected.

Later the same day the owner named the clients (agents and Obsidian mobile, both through the sync workspace) and decided that **the Git vault is the authoritative copy**. The roadmap gained two node-side refusals (a vault-held retired list; no publishing from an unbound or diverged workspace) and a draft source-snapshot contract, sent to the workspace project for a gap check. The workspace project is willing to consider a server-side read adapter outside its core, as a separately granted capability with its own security review; that is a milestone, not a patch, and is not selected.

## Built the same day (three bounded workers, synthetic fixtures)

- **Workspace checks on the owner node.** A mapping declared `source.kind: "workspace"` must be bound to a vault commit before it can publish. Binding and staleness use a *folded* text digest on both sides (strict UTF-8, leading BOM stripped, CRLF and lone CR to LF); the Git operation is derived against exact vault bytes, so untouched lines keep their own terminators and a vault file is never normalized by publishing. Refused: unbound, diverged at bind, delivery moved since baseline, invalid UTF-8, a vault file with a lone CR, text that is the vault text repeated (`workspace-text-repeated`, after a real duplication defect was found in a workspace), a second or unclosed leading frontmatter block, and anything matching the private retired list, which fails closed when unreadable. The baseline advances only after verified-live evidence. CR acceptance is opt-in for this path; raw edit, owner-direct Save and proposal application still refuse CR.
- **Device and agent identity.** An Ed25519 signed-request adapter beside the bootstrap session: each request binds audience, key, command, input digest, nonce, time and an optional channel binding. All refusals look identical to the caller; reasons go to an audit sink. An agent key can never hold a publish, apply or approve grant and cannot read publication status.
- **Publisher-owned repository.** The separate publisher no longer runs Git in the app's checkout. It copies only object bytes for the bound commit into its own bare repository, validates them, verifies the exact commit there and pushes to the policy URL as an argument. Hostile hooks, config, alternates, URL rewrites, extra refs and tampered evidence all failed to change what was published.

**Live rehearsal, owner-approved, read-only.** Six `read_note` calls to two synthetic notes in the workspace project's designated test room, at three versions. Every returned text hashed to the digest the workspace reported; CRLF and a deliberately mixed note came back byte-exact. Fed to `apps/owner-alpha/test/workspace-capture-rehearsal.js`, the first edit (a property change) was refused with `frontmatter-edit-rejected`, the existing rule that owner publication never alters frontmatter. The body-only edit bound, published one exact commit to a disposable local remote and preserved the mixed file's terminators (14 CRLF, 1 LF before and after). Build, deployment, live check and rebuild were simulated and labelled so.

**Evidence and its limits.** Focused suites: workspace 217/217, identity 43/43, publisher 48/48. Full owner-alpha suite on the combined work: 707 passed, 4 opt-in skips, 2 failed, both timeouts on a heavily loaded machine: a hook timeout in `proposal-review-client.test.js` (third occurrence today; 9/9 alone, five runs) and the four-case classification test in `pipeline.test.js` at the 5 s limit (8/8 alone, three runs). Neither is fixed; treat the suite as not clean until those tests are made robust. One publisher fixture's first run made a read-only `ls-remote` to the vault's public GitHub URL taken from the example config; nothing was written, and both fixtures now refuse any non-local destination. Same OS user throughout, so credential isolation is still unproven.

**Open after this:** whether to adopt the [property-change proposal](/cyberbaser/design/property-policy/) (the owner asked for a principled structure, not a special case); a command for agents to submit proposals (none exists, so an agent key can authenticate but do nothing); loading device keys and the retired list from private node state; the carrier; container isolation; and, in the workspace project, an exact-path read grant, a vault-to-workspace refresh, and an audit reference for agent writes.

The source topology for the first real note is still an open input. Until it is known, make no workspace-wide export, assume no Git synchronization, and select no new public notes. The existing workspace publication rehearsal is synthetic; it is not evidence that a live workspace plugin works. No plugin, live inspection, vault change or deployment was part of this documentation change.
