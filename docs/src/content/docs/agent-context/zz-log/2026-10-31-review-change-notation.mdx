## The owner's question opens research, not a new selection

After the [full-page document-first review](/cyberbaser/agent-context/zz-log/2026-10-31-document-first-publication-review/), the owner asked whether familiar Microsoft Word Track Changes or CriticMarkup had been researched as a primitive. This follow-up does not establish human acceptance of the replacement, select canonical notation, or authorize per-change accept/reject.

The canonical synthesis is [Review change notation](/cyberbaser/research/review-change-notation/). It separates three layers: editorial presentation, suggestion notation/interchange, and exact source-bound application with owner authority. Neither reference needs to replace the whole safety architecture to be useful.

## Historical evidence recovered and qualified

The July [Option 4 proposal](/cyberbaser/research/option-space/#option-4-change-the-unit-of-contribution-from-file-and-pr-to-a-suggestion) considered CriticMarkup, reject-all invariance and a 21-fixture go/no-go. No execution or result was found in the bounded searched tracked documentation, orientation, application and package scope. Private execution is not ruled out. Later proposal-review research surveyed Google Docs, Notion and components, then used block-granular exact-source reveal instead of rendered-inline mapping. An evaluated inline tracked-change notation for owner Publish was not found in that scope.

The gap is an unresolved research gate disconnected from subsequent UI direction, not a claim of no prior research. The historical proposal body is preserved with a dated qualification: tested reject-all reversibility would not prove absence of semantic conflicts, harmful acceptance or attribution abuse.

## Primary-source evidence and limits

The synthesis cites Microsoft's support guidance for display modes, inline/balloon placement, navigation, hidden-versus-resolved revisions and per-change/bulk resolution. These are paraphrases from previously summarized retrieval, not claims about OOXML, stable IDs or concurrency.

The already-downloaded CriticMarkup README was inspected directly for all five constructs, Markdown-boundary caveats and newline warnings. Its omissions are scoped to that document, not generalized to every tool. The inspected MultiMarkdown maintainer page documents accept-all, reject-all and imperfect highlighting, but is revised in 2014 and is not a current benchmark. No parser or round-trip evaluation ran here. Owner-authored CriticMarkup is not categorically banned; display-only use, import/export and canonical embedding remain different workflow choices.

## Recommendation and unrun gate

The recommendation, not a locked selection, is to retain document-first review and the existing exact-authority contract, then evaluate familiar tracked-change presentation with a bounded source-to-rendered mapping proof. Authoritative UTF-8 byte offsets, projection string offsets and inline tokens without source spans are not interchangeable. Existing line-LCS display refinement does not supply that missing mapping. No parser or editor is selected, and feasibility is unmeasured.

The planned gate uses the same substantive full-page workload for tiny/dispersed edits and broad rewrites, plus literal markers, Markdown boundaries, Unicode/graphemes, supported LF/refusal of unsupported CRLF and stale/ambiguous bases. It requires exact mapping or explicit fallback, untouched unchanged blocks, hiding without candidate mutation, unambiguous whole-version consent and no fabricated author history. Any evaluated CriticMarkup adapter must reproduce exact base/candidate bytes through reject-all/accept-all without serializer regeneration. **This gate has not run; neither has this wave closed the historical 21-fixture gate.**
