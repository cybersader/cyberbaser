## Why this entry exists

The maintainer opened the canonical docs site to review the new owner proposal UI and found no review entry point there. Both observations were correct. Current-state documents had been maintained, but the chronological knowledge-ops layer had drifted. The project could tell a new agent what is true now, but not provide a clean dated trail of how the intervening evidence changed the design.

## UI review delivery correction

A coherent interface review should not require the maintainer to infer which unrelated port contains the product surface. It must arrive through one of the normal project paths:

1. a deployed surface, when deployment is separately authorized;
2. a review entry point documented in the canonical docs; or
3. one explicit command that launches the complete authenticated local fixture.

The owner-review checkpoint now uses the third path. From `docs/`, run:

```bash
bun run review:owner-alpha
```

The command starts the real live queue writer, private Unix-socket review seam, independent owner validation, immutable decision store, privileged HTTP routes, and three disposable proposals. It opens an authenticated loopback browser automatically, keeps every proposal decision effect-free, and removes the temporary fixture on `Ctrl-C`. The docs page [Owner proposal UI review](/cyberbaser/development/owner-proposal-ui-review/) provides the durable entry point and review questions.

The Starlight docs site remains the canonical knowledge base, not the product authority surface. The privileged owner UI intentionally stays on its separate exact origin. The correction is to coordinate the experience through docs and one command, not to weaken the origin boundary by embedding privileged controls into Starlight.

## Restored guardrail

The docs preflight now compares `.claude/FOCUS.md`'s `Last updated` date with the newest dated `zz-log` filename. If current project orientation advances beyond the chronological log, local docs development and builds fail with an explicit knowledge-ops error.

This check is intentionally narrow. It cannot prove that every entry is good, but it prevents another months-long silent gap while the current-state layer continues moving.

Going forward, every meaningful research, architecture, product-direction, real acceptance, or implementation wave must leave all three layers aligned in the same session:

- canonical explanation in the relevant docs page;
- current orientation in `.claude/`; and
- chronology, dead ends, evidence, and handoff in one dated `zz-log` entry.

## First maintainer reaction

The maintainer's immediate assessment was that the owner-alpha interface is very ugly. After the functional test, they clarified that the problem should have been obvious: it does not feel like a normal authoring or editorial approval experience for a content-focused person. It exposes far too much information, is not beautiful, and the review treatment reads as AI-generated dashboard slop. That is accepted as direct product feedback, not a request for minor styling polish. The current surface is a backend-functional alpha with minimum security structure, not a visual target or a product-quality interface.

The functional behavior passed, but the presentation needs a first-principles redesign informed by content authoring, wiki moderation, and editorial approval products. The target is not a prettier engineering dashboard. The primary interface should foreground the proposed wording and owner decision, use progressive disclosure for integrity evidence, and feel calm and familiar to someone focused on content rather than implementation.

The maintainer then completed two actions in the real local fixture: one rejection and one approval intent. The runtime retained two immutable decision-only artifacts, both with every effect-boundary field false. The source checkout remained clean, checkout `HEAD` exactly matched the bare remote's `main`, the queue remained retained, and the owner store had no job directory or durable delta outside `proposal-review/`. This is genuine maintainer interaction with synthetic disposable proposals. It is not a real contributor rejection, independent-owner evidence, or contributor-to-live proof.

## Current next step
