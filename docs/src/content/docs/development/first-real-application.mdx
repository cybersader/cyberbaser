This is the sheet for the first time a suggestion goes all the way to the live Cyberbase through the owner's own app: submitted from a page, reviewed, approved, applied, published, confirmed. It is the first contributor-to-live evidence. The maintainer runs it; nothing here is automated on their behalf.

:::caution[Prepared, not run]
Since 2026-09-30 every link this run needs exists and is proven on a throwaway vault. The run itself is the maintainer's; nothing here is automated on their behalf.
:::

## What the owner turns on first

The apply step, the receipt, the job page, and the Decided list are built and proven on a throwaway repository. So is the way a suggestion about a real page reaches the owner's queue without commands, described on [Suggestions on the private site](/cyberbaser/development/suggestions-on-the-private-site/). Before the run, in the owner app's config:

1. **Turn proposal review on** with a private socket path, if it is not already on.
2. **Turn the form on**: `"suggestions": { "form": { "enabled": true }, "forge": { "enabled": false } }`.

That is all. The owner's private site then shows **Suggest a correction** on every published page, the site build writes the binding the intake needs, and the owner app starts the intake beside itself. The public site keeps no form, nothing is exposed, and the owner app stays the only writer.

## The run, once those exist

Budget half an hour. Have the job page open on the server machine and the receipt on whichever device you approve from.

1. **Start the owner app** the usual way. It starts the local intake beside it. Note the commit your vault is at.
2. **Pick one small change** on a published Cyberbase page: a typo, a date, a sentence. Not frontmatter, not a page you intend to edit today.
3. **Suggest it from the page**, in your local site, as a reader would: select the text, write the replacement and a one-line reason, submit. You get a receipt with a queue ID.
4. **Open Proposals** in the owner app. The suggestion is in Needs review. Open it, read it in whichever mode you like, and **Approve** with a note. The receipt says Source unchanged.
5. **Tap Apply to page** on that receipt and confirm. You land on the job page. Watch the six steps: checking, changing the page, pushing, site build, live check, local refresh.
6. **Wait for Live on the page.** Three to five minutes for the GitHub build and deploy. Open the public page and see the change.
7. **Go back to Proposals.** The row reads Live.

## What gets recorded

Copy this into a dated entry under `docs/src/content/docs/agent-context/zz-log/` and fill it in:

```text
First real application run
Date · vault commit before · page · queue ID

Approve: receipt read Source unchanged (yes/no) · anything unclear:
Apply: time from confirm to Live on the page · anything that stalled:
Commit · pushed commit on origin/main · Actions run · public page confirmed at (time)
Decided list read Live (yes/no)

Friction noticed, in order of annoyance:
Anything you would not want a contributor to see:
```

Then update the result section on [Applying an approved suggestion](/cyberbaser/development/applying-approved-suggestion/), the roadmap line about the connected slice, and `.claude/FOCUS.md` in the same session.

## What this run does and does not prove

It proves that one real suggestion can travel the whole boundary: proposal-only intake, owner review, decision-only approval, a separate owner act, the owner pipeline, and a live witness. It is maintainer-operated evidence: the maintainer wrote the suggestion and the maintainer applied it. It does not prove that a stranger can use the form, that the public site should carry the form, or that any lane is offered. Those stay separate decisions with their own evidence.
