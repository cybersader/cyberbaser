Try the complete suggestion loop in your own browser without changing your real vault or opening your owner configuration. By default, the launcher creates three short security notes, a fresh Git vault, a local bare remote, and a private owner workspace. You can instead rehearse on a read-only committed folder copy, described below. All three HTTP listeners bind **127.0.0.1 by default**; `--host PRIVATE_IPV4` selects one private address for a separate-device rehearsal. Nothing is deployed.

This is a hands-on companion to [Suggestions on the private site](/cyberbaser/development/suggestions-on-the-private-site/), not the [first real application run](/cyberbaser/development/first-real-application/). To see a signed workspace edit in the same owner inbox, [try an agent proposal on a throwaway vault](/cyberbaser/development/agent-proposal-rehearsal/).

## Launch

From the repository root:

```bash
bun run --cwd docs try:suggestions
```

Keep that terminal open. The launcher prints the **site home first**, a short list of canonically encoded page links, the owned temporary directory, **Proposals**, a one-time sign-in URL, and the six steps below. It does not launch or attach to a browser. Open the printed one-time bootstrap URL in your own browser to sign in; it lands on the site home. **Start from the site home** and follow its page links, then use Proposals in that same browser. You do not need to type a page URL. The reader repairs a missing home slash and can redirect one extra percent-encoding layer added by a chat app, but only for an existing safe site path. Missing pages show a home link in the browser.

Enter **b** then Enter in the terminal for a fresh sign-in link if the first expires or you switch browsers. Without terminal input, run the exact short **`kill -USR1 <launcher-pid>`** command printed by this run, from another local shell or your coding session. This signals only that launcher and prints a fresh link to its original output; it does not return a link over HTTP or launch a browser. It replaces any unused link, keeps existing signed-in sessions, and preserves the one-time, loopback, separate-owner-origin sign-in boundary. Only signal the PID printed by your current run. Do not share the sign-in link or terminal output.

### Prepare once if asked

You need Bun, Git, Node.js/npm, rsync, Linux `flock`, `sha256sum`, and the `build-contained` helper installed on this development machine. The launcher checks its app dependencies and pinned Quartz renderer before creating a vault. If they are missing, it prints this exact preparation command:

```bash
bun run --cwd docs try:suggestions --prepare
```

Preparation runs inside `build-contained`. It installs the two apps' frozen dependency closures without install scripts, then downloads the pinned Quartz checkout and installs its pinned npm dependencies. It does not update project lockfiles. Internet access is needed for preparation. Its reusable renderer seed lives at `.workspace/suggestions-rehearsal-renderer`; it is not part of the disposable vault. The normal launcher never downloads dependencies or a browser. The first real site build can take a minute.

## Use a copy of real content

To rehearse with a folder from your vault instead of the three sample notes:

```bash
bun run --cwd docs try:suggestions --from "/path/to/your/vault" --folder "📁 03 - Curations, Stacks"
```

The source vault is **read-only**. The launcher reads committed objects from **`origin/main` by default**, not the desktop working tree or an extra unpushed commit. It does not fetch, checkout, change the index, or update refs. Use `--ref <commit-ish>` to select another already-local commit. A missing ref or folder is refused. The launcher refuses the project's own docs and previous rehearsal directories as sources.

Only that folder's Markdown is copied, preserving exact paths and bytes, plus referenced files under the vault-root `_attachments/` directory. Attachment references use the existing Markdown reference extractor, with exact-path/relative-path lookup and filename fallback for embeds, wikilinks and Markdown links. Ambiguous attachment filenames are refused. Only references from publishable pages bring attachments into the copy. Unreferenced attachments, other folders, vault configuration, Git history, and working-tree changes are not copied. A generated `index.md` lists the publishable copied pages.

The throwaway publication allowlist selects the chosen folder and generated front page. The real owner publication selector and projection still enforce **`publish: false` and `cb-publish: false`**; denied notes are copied into the disposable vault but are absent from the site and front-page listing. The normal projection independently determines which copied attachments reach the site. Markdown and referenced attachments each have a **50 MiB total cap**. The folder may contain at most **400 Markdown pages**, including denied notes; raise only that page-count cap with `--max-pages 800`, or choose a smaller folder. Symlinks and unsafe paths are refused.

Start from the printed **site home** and choose a published page from its list. Follow the six steps below, but choose a short ordinary sentence and your own small correction instead of the synthetic MFA sentence. **Every edit, commit and push goes only to the throwaway copy and its local bare remote, never your source vault.** Private-address listeners, Ctrl-C cleanup, `--keep`, `--port` and optional `--challenge` modes work as before.

This is a partial copy: links and embeds into other folders will not resolve, and source pages are never rewritten to repair them. Existing content errors can still block projection or application. The current application route requires LF-only source and the normal 64 KiB source-edit limit; CRLF or larger notes retain their exact bytes in the copy but cannot be applied through this rehearsal. No Excalidraw exports, Canvas rendering or Dataview execution is added.

## Try the six steps

1. **Sign in and start from the site home.** Open the bootstrap URL, which lands on the private site home, then choose **MFA methods**. You should see a short page containing the deliberately wrong sentence **SMS codes are phishing-resistant.**
2. **Suggest the correction.** Choose the **Edit button**, tap into the rendered text and type, then choose **Send · N** and **Send suggestion**. For the sample MFA page, change **SMS codes are phishing-resistant.** to **SMS codes are not phishing-resistant.** Add a short explanation when asked. You should get a receipt. This creates a proposal, not a source edit.
3. **Deliberately hit the page limit before applying.** Send two more distinct suggestions about that same page, with different explanations or replacements. The second attempt should get a receipt; the third should show the rate-limit message and create no additional proposal. The page budget is two attempts, including replays or later source-validation failures, not two successful edits. Do this before applying: the rebuild creates a new publication-bound page ID. The sender also has a three-attempt budget, so do not spend attempts on other pages first.
4. **Review and Approve.** Open the printed **Proposals** URL. Open your first correction, inspect the before/after change, and choose **Approve**. The page is still unchanged; approval records the owner's decision only.
5. **Apply to page.** On the approved receipt choose **Apply to page**, confirm, and follow the job. You should reach **Local rehearsal complete**. The exact splice, commit, push to the local bare remote, and private-site rebuild are real. Deployment and live confirmation are explicitly simulated.
6. **Reload the private page.** Reload MFA methods. It should now say **SMS codes are not phishing-resistant.** Recovery codes and the other unchanged source bytes should stay unchanged. The second proposal may now be stale because it was bound to the old revision; it is not silently rebased.

## Edit as the owner

After signing in, use the small **Edit link** above the visitor **Edit button**. Both paths use the same rendered-page editor, with tracked changes, Undo/Redo, per-block Markdown and per-change Remove. The owner variant finishes with **Save · N**; the visitor variant finishes with **Send · N**. The private link checks the owner session before returning to the page editor. Public builds have no owner link.

1. Make a rendered-text correction. For a different block, place the caret and choose the **Markdown** control to edit that block's exact source. Rendered and Markdown edits cannot mix within one block.
2. Choose **Save · N**, inspect the contextual changes, then **Continue to Save**. This navigates to a separate owner-origin confirmation; it does not send a suggestion.
3. Choose **Save** on that confirmation. One owner-direct authorization starts the ordinary exact-change job, commit, local push and rebuild. Visitor intake limits and bot checks do not apply to owner Save. Deployment and live verification remain simulated in this rehearsal.

The **X** control exits immediately when there are no changes. Otherwise it offers **Discard**, **Save draft**, and **Keep editing**. Drafts stay in this tab's browser session, bound to the original source, not in the vault or a server inbox. Reopen Edit in that same tab to restore a draft. Closing the tab or changing the source can make it unavailable. A short expired or stale owner handoff must be reopened from the page editor.

The finish controls sit at the bottom-right normally. While a touch editing surface has focus, they move to the visible viewport's top-right and the active line gets clearance below them. This does not depend on Safari reporting a smaller keyboard viewport. Chromium phone emulation and deterministic viewport shrink are tested; real iOS Safari keyboard acceptance is still required.

**Edit whole file as Markdown** remains an advanced owner fallback in this suggestions-enabled rehearsal, not the default Edit destination. Private sites built without suggestions or without page provenance retain the working raw Edit destination; an independently enabled owner-only rendered editor is not implemented in this wave. Its Save and X controls stay fixed at the bottom-right rather than below the textarea. It retains the existing single-change validation limits.

Reader scripts cannot read the HttpOnly owner session cookie, obtain its CSRF token or authorize a source write. Its top-level form POST stages only a bounded, expiring draft. The separate owner origin renders escaped text, requires its own session and CSRF for Save, and records the exact base, policy and operation digests. Recovery checks that immutable owner-direct record; visitor approval rules are unchanged.

## Optional bot-check rehearsal

These variants use only Cloudflare's **published Turnstile test keys**, never a production credential:

```bash
bun run --cwd docs try:suggestions --challenge pass
```

The visible test widget passes. Try the same six steps. The browser and local intake need internet access to `challenges.cloudflare.com` for the widget and verification request. Test responses use `example.com`, so the generated config pins `expectedHostnames: ["example.com"]`, not the loopback browser hostname.

```bash
bun run --cwd docs try:suggestions --challenge fail
```

The widget and test secret deliberately fail. You should get no receipt and no new proposal. This mode cannot continue through approval and application.

```bash
bun run --cwd docs try:suggestions --challenge spent
```

The visible test widget passes, but verification uses Cloudflare's already-spent-token test secret. Expect refusal and no new proposal. Failed challenges still consume sender attempts. Restart in ordinary or **pass** mode to try the full loop.

The launcher writes the test secret into a mode-0600 file inside its owned temporary directory and points the optional owner `suggestions.form.challenge` block at it. It never reads your production secret or real owner config. These tests check the integration shape, not resistance to actual bots or a production Cloudflare configuration.

## Stop and clean up

Press **Ctrl-C**, **q** then Enter, or send SIGTERM to the launcher. It stops its owner and reader listeners and the owner-supervised intake, waits for any active local source-writing job, and removes the owned throwaway directory. If cleanup cannot finish, it reports the retained path rather than claiming success.

To keep the throwaway files after stopping:

```bash
bun run --cwd docs try:suggestions --keep
```

The printed directory contains the disposable vault, local remote, owner config and private runtime evidence. `--keep` retains test secrets too when combined with a challenge mode. Delete only that exact printed directory after all owned services and jobs stop. The reusable Quartz seed remains after normal cleanup; a later run creates a fresh vault and empty queue. A kept directory is evidence for inspection, not a resumable launcher state.

## Troubleshooting

- **Missing dependencies or Quartz seed:** run the printed `--prepare` command. Preparation uses the existing pinned renderer setup and may need npm/Git network access. The launcher does not silently install anything.
- **A port is occupied:** stop the other rehearsal, or choose another three consecutive ports, for example `bun run --cwd docs try:suggestions --port 46537`. Use `--host PRIVATE_IPV4` when another device needs access; public and wildcard addresses are refused.
- **Proposals asks you to sign in:** use the bootstrap link in the same browser. The private reader page being accessible does not authenticate the separate owner origin. Enter **b** for a fresh one-time link, or run this launcher's printed `kill -USR1 <launcher-pid>` command and read its original output.
- **A copied page link does not open from chat:** open the printed site home and use its page list. The reader repairs one extra encoding layer only, not repeated encoding or links outside this partial copy.
- **The third suggestion is not accepted:** that is the intended page-limit check. Restart for a clean queue and limit state. Replays and malformed source-bound requests can use the budget too.
- **No widget or challenge refusal:** check access to `challenges.cloudflare.com`, browser blocking extensions and the selected test mode. A disconnected widget fails closed. If this checkout does not yet accept the optional challenge block, use ordinary mode until the matching owner configuration change is present.
- **The page has not updated:** approval alone never applies. Use **Apply to page**, wait for the local job to finish, then reload the private site, not a public site. The terminal remains open throughout.

## What this proves, and what it does not

The rehearsal uses the real private-site Quartz form, retained source binding, separate intake process, queue, authenticated Proposals review, immutable owner decision and separate application act. Rendering, exact source checks, source application, commit, local push and private-site rebuild run against disposable data. A fixture-local Git seam verifies the local bare remote before presenting the policy's synthetic HTTPS repository identity. That identity is not a network destination.

It does **not** deploy, contact GitHub Actions, verify a public page, write to your real vault, offer public contribution access, establish usability acceptance, or settle Q09. Only `--from` reads a real vault, using committed objects without opening its working-tree content. Deployment discovery, deployment success and live confirmation are explicitly simulated and labelled on the owner screens. The optional bot-check modes contact Cloudflare but do not validate production keys or real abuse handling. Actual browser selection, the visual widget and the owner's experience still require the human walkthrough above; an HTTP test is not a browser acceptance result.
