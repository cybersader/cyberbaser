**Status: implemented and mechanically tested, off by default, not offered publicly.** WP4 Lane B now has a strict correction-intent contract, exact retained-source derivation, a local durable proposal queue, an optional HTTP intake app, a Quartz form that public builds leave absent, and local-only OCI/Compose packaging. Its same-host review seam and owner-alpha decision-only consumer are also implemented and mechanically accepted. Since 2026-09-30 the owner can turn the form on for their own private local site from one `suggestions` section of the owner app's config; the owner app then derives the intake's settings and starts and stops it beside itself ([Suggestions on the private site](/cyberbaser/development/suggestions-on-the-private-site/)). Repository CI is read-only and exercises the package, app, renderer, deployment-structure, image-build, and isolated runtime-acceptance paths.

This is implementation evidence, not product or human evidence. No public endpoint is deployed. No ordinary reader or independent owner has used the path. No running reverse proxy, TLS endpoint, edge DDoS control, service installation, image publication, hosted console, source writer, merge path, approval-to-application authority, or production authority exists. Since 2026-11-16 the [public-readiness protections](#public-readiness-protections-off-by-default) are built and tested but not deployed. Q09 remains open.

## The implemented path

```text
published source-backed page
  → optional Quartz correction form
  → strict credential-free correction intent
  → retained publication binding + exact historical Git objects
  → canonical @cyberbaser/proposal
  → anonymous / full-review classification
  → owner-local durable proposal queue
  → private same-host read-only review snapshots
  → independently validated owner decision-only record
```

The implemented same-host path stops at retained owner decision evidence. Approval records intent only, and rejection is terminal only in the owner decision layer. It cannot apply, commit, push, merge, deploy, rebuild, publish, or authorize source writing.

## WP4 implementation amendment: local queue and sibling service

This is a **no-R-number implementation amendment** to the already ordered WP4 work. It records two version-1 choices without closing Q09 or selecting a permanent product surface.

1. **Use a local filesystem proposal queue, not bot pull requests, for Lane B v1.** `@cyberbaser/proposal-queue` stores exact canonical proposal bytes plus bounded receipt, carrier, trust-classification, and lifecycle artifacts in one private owner-controlled directory. The queue has finite entry, byte, per-source, and retention bounds. Its only lifecycle states are `pending-review` and `expired`. It has no accepted, rejected, merged, applied, or published state.
2. **Run public intake as a sibling service, not inside owner-alpha.** `apps/account-free-intake` is a separate process and deployment image. Its container receives only credential-free config, retained source-binding manifests, a read-only bare Git object store, and one dedicated writable queue volume. It does not mount the owner-alpha app, vault worktree, owner state, credential socket, renderer output, or publication output.

These choices keep unauthenticated traffic and queue writes outside the owner-authority process. They do not make the local filesystem queue a permanent cross-maintainer protocol, and they do not authorize public exposure. Owner-alpha now inspects the same canonical queue evidence through the private read-only socket and retains decision-only records. Any broader WP5 console must preserve that boundary and must not turn the queue or decision store into a second source authority.

## Components and boundaries

### `@cyberbaser/account-free-intake`

The package accepts a strict, credential-free correction intent containing only an opaque retained-publication binding digest, opaque page ID, exact quote plus optional context, replacement, rationale, inert HTTPS evidence URLs, and an optional high-entropy idempotency key.

The receiver resolves the exact retained binding and historical Markdown blob from owner-controlled local inputs. It reads `.cyberbaser/trust.yml` from the same source revision, derives one canonical quote-bound `@cyberbaser/proposal`, reapplies it in memory, and requires anonymous `full-review` routing. It performs no HTTP, network fetch, queue write, checkout, ref mutation, source write, identity verification, owner decision, or publication action.

### `@cyberbaser/proposal-queue`

The carrier-neutral queue accepts canonical proposals from Lane A or Lane B. It retains exact proposal bytes, validates all metadata, uses a Linux kernel lock, writes through private staging plus `fsync` and atomic rename, and re-verifies retained source and trust-policy evidence on open and load.

Lane B raw idempotency keys are never retained. Anonymous Lane B entries cannot supply a verified subject. Capacity and retention are finite, and recovery fails closed on substituted files, ambiguous locations, duplicate IDs or replay scopes, stale source, policy disagreement, proposal-application failure, or trust-classification disagreement.

### `apps/account-free-intake`

The optional Bun app refuses to start unless its exact configuration sets `enabled: true`. It exposes only:

- `POST /v1/corrections` for the strict JSON intent;
- `OPTIONS /v1/corrections` for non-credentialed CORS from exact configured form origins; and
- loopback-only `GET /healthz` for the container health check.

The app rejects credentials, treats forwarded headers as non-authoritative, enforces an exact public Host and Origin, bounds the body, shares one five-second deadline across body read and derivation, and applies process-wide token and concurrency limits. Those limits are origin protection only, not edge DDoS protection.

The bundled `list` and `show` commands render bounded text or static escaped HTML. They use a nonmutating queue inspector that revalidates exact source and policy evidence but performs no recovery, retention, expiry, purge, temporary cleanup, or state write. The service must be stopped because the inspector's shared lock conflicts with the service's lifetime exclusive lock; a queue that requires recovery fails inspection until normal service startup repairs it. The commands expose no accept, reject, apply, write, or publication operation. They remain offline diagnostic instruments, not the live owner decision surface or a hosted review product.

When explicitly enabled, the intake process instead serves bounded read-only `list` and `load` snapshots from its already-open queue over one private same-host Unix socket. The writer keeps its lifetime exclusive lock. The socket exposes no enqueue, expiry, purge, decision, or source operation. Owner-alpha is a separate consumer: it imports neither the intake app nor queue files, independently validates the advertised evidence, and records decisions only in its own private store.

For the owner's own private site, `publicOrigin` and `allowedFormOrigins` may instead be exact private numeric IPv4 HTTP origins with explicit ports (the same ranges the owner app binds), and `listen` must then bind exactly that address and port. The owner app writes such a config itself and supervises the process; no one edits it. Every public deployment shape keeps the HTTPS-only rule and the `0.0.0.0` listener behind a proxy.

### The forge watcher (Lane A into the same queue)

Since 2026-09-30 the same service can watch one Forgejo repository for open pull requests and enqueue each new head as a Lane A entry, read-only towards the forge. The `forgejo` config block is optional; when it is enabled the public form may be off (`listen`, `publicOrigin` null, `allowedFormOrigins` empty), so the service can run for the review socket and the watcher alone. The watcher keeps a private clone, retains each base commit it enqueued, and proves Lane A entries from that clone on recovery. Design and evidence: [Pull requests in the inbox](/cyberbaser/design/pull-requests-in-the-inbox/).

```json
"forgejo": {
  "enabled": true,
  "apiBaseUrl": "https://forge.home.arpa:8443/api/v1",
  "repository": { "url": "https://forge.home.arpa:8443/owner/cyberbase.git", "owner": "owner", "name": "cyberbase", "baseBranch": "main" },
  "cloneDir": "/srv/cyberbaser/forge-clone",
  "pollIntervalMs": 60000,
  "tokenFile": null
}
```

### Quartz renderer integration

`renderers/quartz-cyberbase` contains a source-backed **Suggest a correction** component and browser client. The component is absent unless build-time configuration explicitly sets `CYBERBASER_ACCOUNT_FREE_INTAKE=enabled` and supplies every retained-publication input. Normal and current public builds leave it disabled. The owner site build supplies those inputs itself when the owner's `suggestions.form` is on; the intake origin may then be a private-network IPv4 HTTP origin.

When enabled, the browser receives only the public intake action, retained binding digest, and opaque page ID. Repository identity, source revision, source path, owner origin, private-network details, identity, contact, and account fields are not rendered into the form or posted by the client.

### Local-only OCI deployment

`deploy/account-free-intake` packages the sibling service as one Linux/amd64 image and an off-by-default Compose profile. A plain `docker compose up` starts nothing. The service has a read-only image root, runs as `65532:65532`, drops all capabilities, uses `no-new-privileges`, publishes no host port, joins only a dedicated internal bridge, mounts source evidence read-only, and writes only one dedicated proposal-queue volume.

The repository provides no reverse proxy. Joining one to the internal network, terminating TLS, exposing `/v1/corrections`, preserving the exact Host, and adding edge DDoS controls are separate design and authorization steps.

## Public-readiness protections (off by default)

Built 2026-11-16 by maintainer direction (see [access tiers](/cyberbaser/design/contribution-trust-and-access/#access-tiers-abuse-protection-without-a-forced-account)). Everything below is disabled unless explicitly configured; existing configs and builds behave as before. Nothing is deployed and no Cloudflare account, tunnel or key was used.

| Layer | Where | Behavior |
|---|---|---|
| Edge rate limit and TLS | Cloudflare, configured by the operator | Documented in the deploy README; not automated. |
| Bot check | `apps/account-free-intake/src/bot-check.js`; renderer `suggestCorrectionChallenge.ts` | Optional `botCheck` config (Cloudflare Turnstile). The page sends the token only in header `Cyberbaser-Challenge-Token`. The server verifies success, hostname and action on every submission before source lookup and fails closed: `challenge-failed` (403) or `challenge-unavailable` (503). The secret is read from a file and never logged or queued. |
| Real client address | `apps/account-free-intake/src/client-address.js` | Optional `clientAddress` honors `cf-connecting-ip` only from configured trusted peers; anything malformed falls back to the socket address. |
| Per-sender, per-network and per-page limits | `apps/account-free-intake/src/abuse.js` | Defaults: 3 per sender (refill 3/hour), 10 per IPv4 /24 or IPv6 /64 (refill 10/day), 2 per page (refill 2/day). Keys are HMAC values with a per-process random salt; raw addresses are never stored or logged. Maps hold at most 10,000 keys with oldest-first eviction. Exceeding returns `rate-limited` (429). |
| Inbox cap | Existing queue capacity | A full queue returns `queue-capacity` (503); the form says suggestions are paused. Suggestions still never write to the vault. |
| Public entry | `deploy/account-free-intake/compose.public.yaml` | Opt-in overlay adding a Cloudflare Tunnel connector (no inbound ports), a pinned internal subnet trusted for the client-address header, separate egress for Turnstile verification, file-mounted secrets, and a required operator-supplied connector image digest. |

**Adding your own provider.** Each control is a registry of providers rather than vendor code in the service. Server side: challenge providers in `apps/account-free-intake/src/challenge/` (contract: `validateOptions`, `create` → `verify` returning `pass`, `fail` or `unavailable`), client-address sources in `src/client-address/`, and limit stores in `src/limit-store/` (injectable; no config switch yet). Browser side: widget providers in `renderers/quartz-cyberbase/components/challenge/` (contract: `scriptUrl`, `validateSiteKey`, `mount` → `reset`/`remove`). A new provider is one module, one registry line and one test that runs the shared conformance suite in `test/conformance/`. The core owns the token header, deadlines, CORS and fail-closed mapping: any provider error, timeout or unexpected result is refused, never passed. Both READMEs give the exact steps. Turnstile is the first and only provider so far.

Known limits: rate limits reset on restart, and key eviction lets a high-churn attacker forget old quotas (the inbox cap still bounds the outcome). Per-page counts include replays and failed attempts that passed the bot check. Cloudflare terminates browser TLS, so it can see submitted corrections; the deploy README states this. Turning on Turnstile requires outbound HTTPS from the intake, which relaxes outbound isolation in the public overlay only.

Since the same day, the owner app can also turn the bot check on for the private site through an optional `suggestions.form.challenge` block, and [Try suggestions on a throwaway vault](/cyberbaser/development/try-suggestions/) exercises it with Cloudflare's published test keys. Not done: enabling the form in the public Cyberbase build, a receipt status page, contributor accounts, and any live Turnstile or tunnel test.

Evidence after the provider refactor: intake app 160/160 including the conformance suites; deploy structure 20 pass, 1 opt-in skip; `packages/account-free-intake` 24/24; renderer suite including Turnstile provider conformance passed. Earlier evidence before the refactor: intake app 125/125 tests; `packages/account-free-intake` plus `packages/proposal-queue` 51/51; deploy structure 20 pass and 1 opt-in image test skipped; renderer suite passed. One existing review-socket test was updated because it submits three corrections to one page and now meets the per-page limit. An independent static security review found no defects in the scoped changes; it did not execute tests or exercise live services.

## Mechanical evidence

Focused deterministic suites cover:

- strict correction-intent and retained-binding contracts;
- real local historical Git object resolution without fetch or mutation;
- canonical proposal derivation and anonymous trust routing;
- durable queue writes, locking, crash recovery, capacity, retention, idempotency, and evidence revalidation;
- exact HTTP Host, Origin, CORS, credential, body, deadline, rate, concurrency, and receipt behavior;
- private Unix-socket ownership, modes, schemas, pagination snapshots, concurrency, deadlines, response bounds, cleanup, and nonmutating live queue access;
- safe text and static-HTML offline inspection rendering;
- disabled-by-default Quartz configuration, opaque page IDs, strict browser payloads, response bounds, and retry idempotency;
- local OCI allowlists, pinned bases and packages, off-by-default Compose, internal-only networking, read-only inputs, dedicated queue storage, and explicit owner-authority exclusions; and
- an opt-in Docker runtime acceptance that builds one local image, starts one isolated internal-only service, enqueues one real anonymous proposal, verifies durable queue artifacts and unchanged inputs, and cleans up its temporary resources.

`.github/workflows/proposal-queue.yml`, `.github/workflows/account-free-intake.yml`, and `.github/workflows/account-free-intake-container.yml` have only `contents: read`, immutable action pins, credential-free checkout, no secrets, and no artifact publication, deployment, release, registry push, or repository mutation step. The first two run package/app/renderer checks; the container workflow builds only a local image and runs isolated acceptance. Structural tests fail if those properties regress.

## Evidence boundary

The implemented mechanics support these claims only:

- the package, app, queue, and disabled renderer integration exist;
- deterministic local tests exercise their stated contracts;
- the deployment bundle is structurally tested and has an opt-in isolated Docker acceptance path; and
- CI is designed to run that complete acceptance without publishing or modifying the repository.

They do **not** support these claims:

- publicly deployed or reachable;
- human-tested or usable by an unfamiliar reader;
- offered as a contribution path;
- protected by a production reverse proxy, TLS, WAF, or DDoS service;
- an identity verifier or anything above the anonymous trust floor;
- a publicly deployed, offered, or independently operated owner-review product;
- a watched live forge (the watcher is proven hermetically only);
- a source writer, merge mechanism, or publication authority (approval-to-source application exists separately as the owner's own Apply act); or
- closure of Q09.

## Run the focused checks

```bash
bun test packages/proposal-queue/test
bun test packages/account-free-intake/test
bun test packages/forgejo-intake/test
bun test apps/account-free-intake/test
bash renderers/quartz-cyberbase/tests/run.sh
bun test deploy/account-free-intake/test
```

The final deployment command reports the Docker runtime acceptance as skipped unless Docker is available and `ACCOUNT_FREE_INTAKE_CONTAINER_IMAGE` names an immutable local image ID. See `deploy/account-free-intake/README.md` for the local-only build and acceptance procedure.
