## Open

### Q08 — Does the fork flow actually attribute the contributor?

**Asked:** 2026-04-11 as [challenge brief 07](/cyberbaser/agent-context/zz-challenges/07-contributor-attribution/); reopened as a numbered question 2026-07-26.
**Why it matters:** [Legal & Governance](/cyberbaser/design/legal-and-governance/) makes commit history the attribution record the content license points at. If the merge commit, rather than the contributor's account, ends up as the author on a fork-and-PR contribution, that record does not say what the license needs it to say.
**Blocks:** the licensing argument, and any contributor-facing credit UI.
**Status:** 🔴 **unverified.** [Contribution Workflows](/cyberbaser/design/contribution-workflows/#attribution) asserted it works "without any special handling" from 2026-04 until this rewrite; nobody ever checked. The two live contribution PRs in R17 were authored by the maintainer's own account and so could not test it. The check is about ten minutes: `git log --format='%an %ae'` over the merged contribution PRs, plus one PR opened from a second account.

### Q09 — What is the contribution path for someone with no account?

**Asked:** 2026-07-26 (the honest replacement for Q07).
**Why it matters:** [Principle 3](/cyberbaser/getting-started/principles/) says contributors shouldn't need to learn git and shouldn't be forced into an account. Half of that is met. The other half has no implementation: GitHub's web editor, the only path open to an outside contributor, requires a GitHub account.
**Blocks:** Principle 3's core persona, and any claim that "accounts are optional."
**Status:** 🔴 **open, rated critical** in the [risk register](/cyberbaser/research/assumptions-and-risks/#the-real-gating-risks-ranked). A design exists — the `cb-intake` anonymous submission endpoint in the [hub BOM](/cyberbaser/research/proposal-hub-bom/) — and nothing is built. The abuse controls (rate limiting, first-time-contributor holds) belong to the same design, not to a separate CMS or proxy.

### Q10 — What enforces the moderation policy?

**Asked:** 2026-07-26.
**Why it matters:** the trust classifier computes routes and `ofm-check` classifies damage, but `ofm-check.yml` is `continue-on-error: true`, `trust-gate.yml`'s auto-merge step is commented out, and `main` carries no branch protection and no rulesets. **No check can block any merge.** Every gate in the written policy is currently a human reading a diff.
**Blocks:** the auto-merge route (it can never fire without a required check), and any claim that the pipeline enforces anything.
**Status:** 🔴 **open, and constrained.** The obvious fix, branch protection with required checks, collides with a hard constraint: the maintainer pushes to `main` directly from Obsidian Git, and a PR-for-everything rule would break daily authoring. The question is what enforcement looks like that survives that constraint, not whether to turn protection on.

### Q06 — Content addressability: slugs, hashes, or title-based with redirects?

**Asked:** 2026-04-11
**Source:** [Primitives · Content-Addressable URLs](/cyberbaser/concepts/primitives/#stable-urls)
**Why it matters:** breaking external URLs when the vault is reorganized is unacceptable for a wiki; links must survive reorganization.
**Blocks:** it no longer blocks the deploy (the vault is live), which makes it worse rather than better: **933 pages now have URLs derived from their current file paths**, so every deferral increases the cost of choosing a convention later.
**Status:** 🔴 **open, and the oldest genuinely unresolved question on this page.** R16 shipped verbatim paths as a v0 default and R16/R19 declined the folder renames, but no `permalink` convention, alias handling, or redirect table was ever decided. [Renderer URLs](/cyberbaser/research/proposal-renderer-urls/) argues for path-slug plus `aliases`; [dissent §1.3](/cyberbaser/research/dissent/) calls it a half-day convention decision with no owner. Still no owner.

## Answered, with a named residue

### Q04 — How do we guarantee no lossy round-trip in practice?

**Asked:** 2026-04-11 · **Answered:** 2026-07-25 by [R12](/cyberbaser/research/v1-build-plan/#gate-result-run-2026-07-25), empirically.
**The answer, and the redefinition it required:** the gate ran the round-trip over all 1430 real vault files and returned **4.6% byte-identity, zero mask leaks, zero parse errors**. Whole-file re-serialization cannot preserve real files, so it is banned from every write path. Enforcement was re-scoped from "does the file survive re-serialization" to **"no construct damage in a change,"** which is what `@cyberbaser/ofm`'s `clean | suspect | damage` classifier computes.
**Residue, and it is real:** the check runs report-only (see Q10), and the per-feature equivalence rules the original question implied — is `[[Foo]]` ≡ `[[Foo|Foo]]`, does `![[img.png|200]]` have to survive — were never written down. They live in the classifier's code, not in a document. That half sits with [challenge 05](/cyberbaser/agent-context/zz-challenges/05-translation-equivalence/).

### Q05 — What's the incremental build story for a vault of thousands of pages?

**Asked:** 2026-04-11 · **Closed on scale:** R12, then measured again in R14 and R16.
**What was measured:** the full OFM corpus pass over 1430 files takes **7.3 s** on ext4 (R12); Quartz builds the 1420-page vault in **1:55** locally (R14) and **160 s** in CI (R16). Scale was never the problem. Note the ~780x penalty measured for many-small-file reads on a 9p mount, which is why benchmarks run on ext4.
**Residue:** there is still no incremental build. Every push to `main` triggers a full rebuild, and the measured end-to-end deploys ran **3m07s to 4m52s** across five successful runs. That is tolerable at 933 pages and is the number to watch, not the theoretical ceiling.

### Q03 — Should the Web CMS show rendered Obsidian preview, or raw markdown?

**Closed as moot**, 2026-07-25 by **R12**. There is no web CMS. Decap, Sveltia, TinaCMS, EmDash and Pages CMS were all disqualified for re-serializing the file on save ([write-path proposal](/cyberbaser/research/proposal-write-path/)). The surviving form of the question — should a contributor see a rendered view of their change before it merges — is the per-PR preview, which is [designed and unbuilt](/cyberbaser/research/proposal-hub-bom/#per-pr-rendered-previews).

## How to resolve a question

1. Spend the research time (could be a session, could be a sprint)
2. Write the answer and rationale in [Trade-offs](/cyberbaser/reference/tradeoffs/) or in the relevant design page
3. Mark the entry here closed, with the deciding R-number and a one-line residue if anything survives. Keep the heading and the number so inbound links don't break
4. If the answer reveals deeper questions, those become new entries here

A good answer usually creates two new questions, and that's fine. Better to have precise questions than vague confidence. What is not fine is what happened to Q01-Q07: answered in a decision record and never marked here, so the page kept asserting for months that settled things were open.
