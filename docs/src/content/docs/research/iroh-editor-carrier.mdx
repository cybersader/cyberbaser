**Iroh is a viable candidate for reaching the owner editor without opening a home-network port. It is not selected for deployment.** The local fixture demonstrates real browser-to-owner traffic and a passkey proof bound to the actual Iroh connection. A real editor still needs the same command core and local account custody as private HTTPS, a separate trusted editor origin, and production browser, relay, and security tests. Keep private HTTPS first in the [editing roadmap](/cyberbaser/design/editing-and-trust-roadmap/). The [earlier Iroh fixture](/cyberbaser/research/local-first-protocol-options/#2-iroh-proposal-transfer-fixture--completed-locally) moved immutable proposals; it did not test a browser, identity or commands.

## A. Only the relay is reachable from outside

**Documented.** A [browser Iroh build](https://docs.iroh.computer/deployment/wasm-browser-support) uses WebAssembly and the relay, not direct UDP. The [N-API bindings](https://docs.iroh.computer/languages/javascript) wrap native Iroh for Node.js; they are not a browser build. The [self-hosted relay guide](https://docs.iroh.computer/iroh-services/relays/self-hosted) covers TLS and `/healthz`; verify exact flags against the pinned release. [Iroh's security and privacy notes](https://docs.iroh.computer/concepts/security-privacy) describe the distinction between encrypted payloads and routing metadata.

**Proposed topology.** The native owner endpoint (Rust for this experiment) opens an outbound persistent connection to an owner-operated relay on a separate reachable host. Disable IP transports, public discovery/publication, default relays, and automatic port mapping; give the browser only the owner endpoint ID and explicit relay URL, with the owner ID pinned from a trusted setup. The browser starts a WebSocket to the same relay and dials that ID and editor ALPN. Nothing binds a home-network listener or requires an inbound rule; the owner’s native process accepts Iroh streams over that outbound connection. Use a DNS-only relay hostname, valid certificate and TLS/WSS, with no public relay fallback. The relay host holds no vault, credential verifier, application sessions, or Git credential. A Rust sidecar, if needed, should feed only bounded commands and verified context through an owner-local authenticated interface, not expose the publisher directly.

**Visibility.** The relay necessarily sees connected endpoint IDs, which endpoints exchange traffic, public-facing socket addresses (including the owner's), timing and sizes or volume; its WebSocket frontend also sees handshake metadata such as Origin. A relay can deny, delay or observe traffic. It terminates outer WebSocket TLS in production, but it cannot authenticate as either Iroh peer or decrypt the inner authenticated QUIC/TLS traffic to read command bodies, passkey assertions, file names or source. This is transport privacy, not anonymity or availability. The fixture observes the path, not a ciphertext inspection. Minimizing relay logs and disabling discovery keep the owner's address out of published routing records; they do not hide it from the relay operator.

**Observed locally.** Rust Iroh 1.0.3 and a real `iroh-relay` library instance ran with relay HTTP/WS bound to IPv4 loopback. Chromium loaded the `wasm-bindgen` Iroh build (no native client shim), opened only the configured local WebSocket, and the owner reported a selected relay path and zero direct IP addresses. A new dial failed when only the relay stopped. This tests forced relay routing in one host, not off-site reach, a firewall configuration, WSS, or NAT behavior.

## B. The editor origin runs trusted code only

**Proposed.** Ship a small static application at a dedicated origin under owner control, for example `https://edit-relay.cybersader.com` if private HTTPS keeps `https://edit.cybersader.com`. The reader site may render vault HTML; the editor origin must never serve or execute vault HTML, SVG, scripts, plugins, or user-uploaded static assets. A reader Edit link opens the editor top-level without an opener. A public route ID is an untrusted locator, never an authorization or a command; resolve and scope it on the owner node. Any reader-origin draft transfer remains inert and requires a separate owner confirmation before submission. Show source and diffs as text using safe DOM APIs. Do not embed the privileged editor on reader pages or accept privileged requests from reader windows. If rich preview is later necessary, render it on a separate origin with a sandbox, no shared state, and no privileged message bridge.

Use exact restrictive CSP (own build scripts and WASM, exact relay in `connect-src`, no frames/ancestors, forms, base overrides, or arbitrary third-party code), deny cross-origin opener access, and avoid cross-origin cookie scope, credentialed fetch, or secrets in URLs. Do not split the *same* editor origin between a private cookie-setting server and a public static host: a host-only cookie can still be sent to either server when they share a hostname. Use distinct hostnames and RP-specific credentials if both carriers run side by side. Treat static asset delivery and update integrity as security-critical: whoever serves trusted scripts can act within an authenticated editor session. A Worker can reduce accidental key exposure but is not a boundary against scripts already trusted by the editor origin.

**Key storage.** Generate a fresh browser Iroh Ed25519 endpoint key in WASM memory for the session and discard it on close or reload. Do not persist it in IndexedDB or `localStorage`. The passkey private key instead stays in the authenticator/passkey provider. The [Iroh `SecretKey` API](https://docs.rs/iroh/1.0.3/iroh/struct.SecretKey.html) takes key bytes; the spike does not establish that a non-extractable WebCrypto `CryptoKey` can be used by Iroh's TLS stack. IndexedDB is origin-scoped storage, not protection against compromised same-origin code. Any future durable device key needs explicit policy, storage and revocation review. The owner endpoint key is stable and separate from passkeys and the Git credential; store it owner-locally, restrict access, and re-pin it through the trusted setup if rotated. The fixture uses fresh keys and local origins, not production isolation headers or hardware-backed key storage.

## C. Authenticate the person on this connection

**Observed mechanism.** After the full QUIC/TLS handshake the owner issues a random 32-byte session ID and per-attempt 32-byte nonce. Each side reads the authenticated owner/browser endpoint IDs from Iroh, never from request JSON. Both independently derive 32 challenge bytes from the **inner** TLS exporter, with an application-specific label and context containing the versioned ALPN, owner ID, browser ID, session ID, and nonce in a fixed role order. This is an application use of [TLS 1.3 exporters](https://www.rfc-editor.org/rfc/rfc8446.html#section-7.5) through [Iroh's connection API](https://docs.rs/iroh/1.0.3/iroh/endpoint/struct.Connection.html#method.export_keying_material), not a new credential or the generic `tls-exporter` binding type. The browser compares with its own derivation before calling `navigator.credentials.get`. The assertion signs authenticator data and the hash of `clientDataJSON`, which contains the challenge and browser origin. The owner consumes the challenge on the first verification attempt, valid or not; the challenge expires, belongs to that connection, and never becomes a bearer token. Reconnect requires a new challenge. Ignore 0-RTT for authentication and commands.

**Proposed production verification.** On the owner host, use the narrow local account adapter to invoke a maintained server library that implements [WebAuthn assertion verification](https://www.w3.org/TR/webauthn-3/#sctn-verifying-assertion). Require exact origin `https://edit-relay.cybersader.com` and RP ID `edit-relay.cybersader.com` in the example topology (the editor hostname, not the URL or a parent domain), same-origin top-level ceremony, enrolled active credential bound to this owner's account, the exact one-use challenge, `webauthn.get`, RP ID hash, user presence and verification, and valid signature, algorithm, user-handle, counter and backup-state handling per the verifier and policy. Counters do not replace nonce consumption, and synchronized passkeys may have no useful counter. The fixture verifies ES256, origin, RP hash, user flags, signature and the bound challenge for a virtual authenticator; it is not a complete verifier or evidence that Better Auth accepts carrier-supplied challenges. Do not copy the verifier into production.

The account adapter opens a short, revocable connection session and hands the core `{id, method, sessionId, authenticatedAt}`. `id` is the deployment-local owner account, not an endpoint ID or credential ID; `method` is `webauthn`; session and timestamp are server-issued. No browser-supplied principal or relay assertion is trusted. The carrier owns connection bindings; layer 3 owns session authority. Layer 2 checks current grants and freshness before commands or effect admission. Nothing about the handshake grants Save, Decide, Apply or Publish.

**Proposed enrollment and revocation.** Bootstrap from the host console or existing authorized private owner setup. It issues a one-use short-lived registration grant for the same stable owner account, at the same exact editor origin; that grant may traverse an unauthenticated but pinned Iroh channel solely to complete registration. There is no public signup or email reset. New credentials require fresh owner proof plus explicit approval; two independent authenticators (one offline recovery key) and a console recovery procedure cover loss. Store public credential bindings and session/recovery state solely in the enabled owner account adapter. On revocation, invalidate enrollment/credential records and their sessions; disconnect connections and also check revocation at the core/effect boundary to cover races. A lost device using a synced credential cannot be uniquely revoked by credential ID: revoke that credential for all copies or require distinct hardware credentials or an explicitly enrolled per-device key. Never let the relay's admission list become the account store.

## D. Small frames, durable command semantics

**Observed fixture.** One bidirectional QUIC stream per request, EOF as the boundary in each direction, versioned JSON with `{v, id, body}` and echoed IDs, bounded reads of 4,096 bytes per frame, five-second owner stream deadline, session and request limits. Both fake commands require the verified owner principal. Malformed or oversize frames return an error code and a null request ID; duplicate IDs in one connection are rejected. The fixture never writes source and has no durable job or command ledger.

**Proposed common contract.** Both carriers translate into the same command types: `read-source`, `submit-change-set`, `decide`, `apply`, and `job-status`, plus the owner-direct Save command when extracted. Every request has version, request ID and validated command-specific body; an application response echoes the ID with a result or stable error code. Unknown fields, ambiguous encodings, unsupported versions and malformed paths fail closed. Start with carrier-independent per-command body and response caps, for example 256 KiB encoded per command as a bounded first target, and finite connection, in-flight stream, request and idle limits; measure real page sizes before freezing caps. Cap before allocation or parse, impose read/write deadlines, and close on abusive framing. Limit larger reads to an explicit later byte-range protocol if needed. Do not blindly raise bounds or split one exact change into silent writes.

Authorization, source selection, pinned base/policy, and operation digests remain the core's concern. Submitting or deciding does not apply. Use a stable mutation key scoped to the principal and command plus the canonical request digest; record it with the receipt/job admission so a lost response or retry after reconnect (even on HTTPS) returns the same receipt or a conflict if the payload changed. Connection request IDs are only short-lived correlation and replay guards. Never auto-resubmit a mutation on a new session or interpret a timeout as a failed write; resolve through a receipt or authorized job-status query. At most one admitted effect ultimately reaches the isolated publisher. An unauthorized or revoked caller cannot use replay to retrieve a previous receipt.

## E. One conformance suite, plus carrier-specific checks

**Proposed shared tests.** Run the same fixture command traces through HTTPS and Iroh and compare authorized results, refusals, and eventual durable effect state. Exclude carrier diagnostics and generated opaque IDs from equality checks.

| Case | Required result on either carrier |
|---|---|
| Forged client principal, wrong account, missing proof, expired or revoked session, stale step-up | No private read, action or receipt. Authorization uses live policy, not network location or carrier. |
| Wrong origin or attempted cross-context submission | No privileged effect. HTTPS proves exact Origin and CSRF; Iroh proves the exact WebAuthn origin on the active peer-bound session, with no ambient cookie or reader bridge. |
| Proof replay/across connections, duplicate request, changed-body mutation key | No reauthentication or extra job. A valid exact retry, after a fresh session if necessary, resolves to the existing result only after authority is checked. |
| Unsupported version, bad encoding, truncated/oversize frames or slow stream | Bounded processing, cancellation or typed refusal, no dispatch of a partial frame, no mutation. |
| Private or excluded path, stale base or policy, ambiguous operation, manipulated bytes | Fail closed; do not change undeclared source bytes. |
| Submit, Decide, Apply, direct Save and job status | Correct owner and scope on each. Decide is not Apply; one exact authorized action creates at most one job and status is scoped to the caller. |
| Disconnect around admission, restart after admission, relay or HTTPS outage | No duplicate write or privilege downgrade. Report unavailable/unknown accurately; known jobs recover and resolve through the same status interface. |

Carrier-specific gates include making sure HTTPS rejects forged forwarding/Origin/CSRF, and Iroh rejects wrong peer/ALPN, another channel's challenge and relay fallback. Verify shared semantics against the actual command core before treating the carrier as interchangeable.

## Result, remaining gates, and layer impacts

**Observed (Chromium 147, Linux, loopback, debug build).** Nine test groups passed in each of two runs. Cold dials were **160.4 and 167.6 ms**; warm round trips were **1.45 and 1.60 ms median**, **7.0 and 2.5 ms p95**, respectively (50 sequential browser echo requests per run). Across both runs the minimum was 0.8 ms and the maximum was 30.0 ms. Warm timings include one QUIC bidirectional stream, WASM and owner fixture framing for each request, not page/WASM load, passkey touch, disk, Git or publication. Cold dial includes endpoint bind and connection setup, not passkey authentication. This is a local smoke measurement, not remote latency or a mobile performance claim. Re-run from the repository root with `build-contained -- bash spikes/iroh-editor-carrier/run.sh` (docs Playwright/Chromium, Rust and WASM-capable Clang required). There is no deployed editor or vault in the fixture.

**Unverified deployment gates.** Test valid WSS and exact hosted CSP with desktop Chromium/Firefox/Safari and iOS, including real passkeys, networks blocking WebSockets, suspension/reconnect, key rotation, recovery and revocation. Rehearse a relay outage and the explicit private HTTPS fallback (never auto-downgrade). Verify the home deployment opens no inbound socket and publishes no route, the owner platform restarts and recovers after reboot, backups are restorable, and the isolated publisher holds the only reusable push credential. The [relay's data rate limits](https://docs.iroh.computer/relays/rate-limiting) are not a complete connection admission policy: test bounded per-source and aggregate connection/bandwidth/handshake limits separately, including exhaustion with ephemeral browser IDs. Any browser-visible token or check of the WebSocket Origin is not authorization; do not bake relay secrets into static assets. Confirm a usable relay admission policy and minimize metadata retention. Before activation, perform an independent defensive review of origin isolation, exact source binding, privilege bypass prevention, assertion and mutation replay, revoked sessions, host recovery and abuse controls. No public relay was used.

**Layer 2:** no Iroh type, node ID or relay field should enter commands or policy. If the extracted core cannot recover a mutation by a carrier-neutral key across reconnects or cannot recheck authorization before an effect, fix that shared contract before either carrier is eligible; this is not Iroh-specific logic.

**Layer 3:** Iroh needs a headless verifier entry that accepts server-issued connection-bound challenge state and returns a revocable session without relying on HTTP cookies. If the chosen Better Auth integration cannot do this, add or replace the adapter under the existing custody limit; do not move its authority into the relay or layer 4. Side-by-side private HTTPS and the static Iroh client require a separate exact origin/RP pairing under the same local owner principal. Reliable revocation of one device that shares a synced passkey would require a distinct credential or an explicit device-binding design.

**Layer 5:** the static editor origin, WASM `Transport`, passkey handshake and clear reconnect/unknown-result UX are new client work. Same-origin fetch or a privileged editor scripted by rendered vault content cannot be used unchanged. The editing experience can share the exact-change client model and retain the existing separate confirmation boundary; it does not make reader scripts privileged.
