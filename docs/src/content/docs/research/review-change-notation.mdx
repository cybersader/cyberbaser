## Three layers, not competing complete architectures

| Layer | Useful reference or candidate | What remains separate |
|---|---|---|
| Editorial presentation | Word's inline insertions/deletions, margin indicators, optional detail and change navigation | How Cyberbaser derives trustworthy marks from pinned source |
| Suggestion notation or interchange | CriticMarkup's readable plain-text constructs | Whether it is display-only, imported/exported, or deliberately authored in canonical Markdown |
| Application and owner authority | Cyberbaser's existing pinned base, exact operations, byte preservation and owner-controlled route | Neither a familiar display nor notation replaces this contract |

Word and CriticMarkup need not supply the entire publishing safety architecture to be useful. Conversely, visual familiarity does not grant their resolution semantics: **Publish still approves the whole reviewed version**, not selected words or passages. Per-change accept/reject would be distinct product and schema work, not visual parity.

## Word contributes a review vocabulary

Microsoft's [Track changes](https://support.microsoft.com/en-us/word/training/track-changes-in-word) and [accept/reject guidance](https://support.microsoft.com/en-us/word/accept-or-reject-tracked-changes-in-word) document several separable conventions:

- Simple Markup, All Markup, No Markup and Original offer different lenses over revisions.
- Inline marks and balloons put detail in different places; next/previous navigation is separate from resolution.
- Hiding markup does not accept or reject changes.
- Per-change and bulk resolution are distinct actions.

These are useful presentation references, not a requirement to reproduce Word. The cited support pages were inspected through summarized retrieval; these are paraphrases, not verbatim quotations. They do not establish revision IDs, OOXML representation, concurrency or rebasing behavior. No claims about those internals follow here.

Reviewer names and colors must reflect real provenance. A comparison of two versions is **not authoring history**: Cyberbaser must not invent reviewers, authors or attribution from a diff.

## What CriticMarkup offers, and what is unproven

The [toolkit README](https://github.com/CriticMarkup/CriticMarkup-toolkit/blob/master/README.md) defines five constructs. These examples use ASCII syntax, not typographical hyphens found in some upstream examples:

```text
Addition:     {++new++}
Deletion:     {--old--}
Substitution: {~~old~>new~~}
Comment:      {>>note<<}
Highlight:    {==text==}
```

The README permits standalone highlights while recommending an accompanying comment. It describes comments as free-form metadata, including notes, initials or timestamps. That is not verified identity. Its caveats advise avoiding newlines inside tags and completely enclosing Markdown delimiters rather than crossing a substitution boundary.

In the inspected README, stable change IDs, pinned base anchors, escaping and nesting rules are not specified. This is scoped evidence about that document, not proof that every CriticMarkup tool lacks them.

The [MultiMarkdown maintainer page](https://fletcher.github.io/MultiMarkdown-5/criticmarkup.html) explicitly documents accept-all, reject-all and attempted HTML highlighting. It treats CriticMarkup as a layer processed before Markdown and explains how cross-layer spans create edge cases. It warns that highlighting does not always work or produce valid HTML. The page is revised **2014-01-24**, for MultiMarkdown 5.1.0: useful historical implementation evidence, not a current 2026 benchmark. No parser, code or round trip was tested in this wave.

There is **no blanket ban on owner-authored CriticMarkup in canonical Markdown**. Embedding review markup changes source and requires an explicit workflow choice, but the exact-byte rule does not inherently forbid that format. Display-only marks, an external import/export adapter and canonical authoring are different roles with different obligations.

Reject-all returning the exact base would establish reversibility under the tested parser and fixtures. It would not prove absence of semantic conflicts, harmful acceptance or attribution abuse. Option 4's historical claims about eliminating conflicts and proving nothing destroyed remain proposals, not established safety results.

## Precise source mapping remains unproven

The present offset spaces differ: authoritative operations use **UTF-8 byte offsets**; projection segments and blocks use **JavaScript string offsets**. The inline token representation has no source spans and is built from derived strings that join source lines. Existing byte-to-character conversion is therefore not a rendered-inline mapping.

The publication display already uses line LCS to refine a single authoritative splice envelope. Precise byte-span-to-inline claims would need evaluated mapping from exact source to rendered text, including Markdown boundaries and Unicode. That gate remains unproven. This is not merely CSS, and adopting CriticMarkup does not automatically solve it. No new parser/editor is selected.

The [projection authority model](/cyberbaser/design/review-projection-model/) remains intact: display is downstream of exact source and never becomes an application input. Unsupported or underivable detail needs an explicit exact-source or coarse fallback, not confident approximate marks.

## Alternative endpoint reconstruction, bounded synthetic proof 2026-11-02

The approved implementation compares the existing, already source-replay-verified base and candidate block projections. Bounded source-slice block LCS anchors unchanged blocks, positional compatible pairs receive full-token identity LCS, and compatible plain-text replacements may receive word refinement. Token identity includes all actual enumerable metadata, including link targets; structural block metadata is compared separately. Grapheme boundaries are checked with `Intl.Segmenter`, including whitespace followed by combining marks. Without segmentation support, refinement declines to whole text tokens.

Before any inline result is rendered, dropping removed runs must reconstruct the exact **candidate token stream**, and dropping added runs the exact **base token stream**, including metadata. This is a guarantee about the derived, lossy projection, not exact byte rendering or unique authoring history. The unchanged replay gate separately governs source bytes. Source slices that differ while their comparable projections match retain an explicit navigable source/formatting marker and exact previous/source disclosure. Unsupported syntax, incompatible structure, authority-region disagreement and exceeded bounds have labelled block/exact/coarse fallbacks rather than guessed inline locations.

Display-only limits are **2,000,000 block-LCS cells**, **20,000 token-LCS cells per group**, **40,000 word-LCS cells per replacement**, **400 eligible blocks**, **2,000 inline marks**, and **2,000,000 cumulative cells**, including block/token/word comparisons. These do not change authoring policy, preparation limits or the existing display decomposition limits. Broad changes can start clean with a Show changes eye toggle and a short Whole-document review status. The later quiet refinement removes category tallies and keeps the fallback explanation inside Details; this does not promise inline detail for fallback blocks.

Source-marker repairs give every row a candidate-coordinate position before numbering and suppress a deletion marker only when same-operation base spans are fully represented by deleted blocks plus actual gaps. Gap-only or ambiguous coverage retains an honest exact-previous marker. Clean reading hides marker-only wrappers, not candidate prose. These repairs do not introduce precise inline source spans.

## Recommendation and open choices

**Recommendation, not a locked format selection:** retain document-first review, the evaluated endpoint-reconstruction strategy and the existing exact-authority contract while responding narrowly to actual owner feedback. Bounded synthetic acceptance and independent evidence inspection permit a synthetic review checkpoint, not real-host readiness or human acceptance. Keep CriticMarkup available as an optional notation or adapter candidate, without selecting canonical storage now.

Open choices include inline versus margin detail, useful navigation and hiding controls, mapping strategy, and whether any CriticMarkup role is justified. Whole-version Publish remains unchanged. Neither this research nor the earlier mechanical readiness verdict establishes human acceptance.

## Prior mapping and notation gates remain open

Use the same substantive full-page fixtures for each presentation candidate: tiny edits, dispersed changes and broad rewrites. Add literal CriticMarkup tokens in inline/fenced code, Markdown-boundary crossovers, Unicode/graphemes, supported LF and refusal of unsupported CRLF, and stale or ambiguous bases.

Pass criteria are:

1. Exact source-to-rendered mapping, or an explicit honest fallback; unchanged blocks remain untouched.
2. Hiding marks changes no candidate; whole-version consent stays unambiguous; no fabricated author history.
3. Stale or ambiguous binding refuses rather than guessing, without weakening existing authority checks.
4. If a CriticMarkup adapter is evaluated, reject-all reproduces the exact base and accept-all the exact intended candidate, without serializer regeneration; literal markers have unambiguous handling.

Failure blocks that adapter or presentation candidate, not familiar editorial UX as a category. **The precise source-mapping and CriticMarkup-adapter gates have not run.** The November endpoint reconstruction tests above partially evaluate a different presentation strategy and do not silently complete either gate. The original 21-fixture CriticMarkup gate remains **UNRUN**, historical and unresolved.
