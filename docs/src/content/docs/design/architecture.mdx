Cyberbaser, as built, is **ten no-authority boundary packages, an append-only decision-ledger package, a private owner-alpha authority application, a separate optional account-free intake application, local-only OCI deployment bundles, two deployment-observation providers, and read-only repository CI around an owner-controlled Markdown source**. The ten boundary packages select what may publish, project disposable copies, prepare exact candidate splices and canonical proposals, reconstruct narrow Forgejo and account-free carriers, classify integrity and trust, retain bounded proposal evidence, inspect rendered links, and enforce emitted-site URL continuity. The Forgejo intake adapter is effectful but read-only and no-authority; it is hermetically tested against injected Forgejo metadata and real local Git objects, not a live or offered lane. The account-free adapter resolves retained publication bindings and exact local Git objects, while the carrier-neutral proposal queue writes only private review evidence. The separate Lane B app and disabled Quartz form are mechanically tested but not publicly deployed, human-tested, or offered. The ledger now has an implemented and hermetically tested two-stage GitHub adapter: an unprivileged capture uploads only a routing hint, while a trusted `workflow_run` recorder reconstructs authority and may append only the governance JSONL record through exact non-force publication. Those workflows are not installed in the live vault, no real fork run has occurred, and there are zero live observations. The separately selected owner-alpha route may write one declared exact operation because the owner's Save activates a precise durable policy for that edit. WP2 gives that same route an owner-operated container home without changing its authority, exact-change, or recovery rules. WP3 phase one adds a strict Forgejo 16 Actions observation adapter and disposable acceptance fixture behind the same provider seam. The original same-UID host-runner design failed adversarial review and was replaced by unprivileged run-scoped job containers with an exact two-source mount allowlist and no engine socket. On 2026-08-10 the real Forgejo 16.0.2 fixture gate passed isolation, controlled PR, exact owner-alpha Save, fixed run/job binding, HTTPS witness, storage, unchanged-seed, and exact-cleanup checks. Production authority remains unchanged. The current GitHub, Actions, Pages, and Quartz arrangement is dogfood infrastructure, not the architecture's essence.

R23 adds no new authority-bearing component. `@cyberbaser/linkcheck` checks both rendered internal links and canonical-URL continuity from previous and candidate sitemap inventories plus emitted files. The continuity path is package-tested and reproduced all 931 current public URLs in a read-only local pinned-Quartz rehearsal, with one real alias stub separately covering one simulated removal. It is not installed in the live publication workflow and caused no deployment or public URL change.

The stable model is broader than today's interfaces. Local editors, forge editors, reader-correction controls, rich browser or CMS-like tools, and agents may all be authoring spokes. External spokes must emit bounded proposals against a pinned source base and converge on owner-controlled review or delegated policy; they cannot write canonical source directly. The owner may continue authoring in a preferred local tool or use the private owner-alpha wiki as a direct-authority lane. Renderers remain independently replaceable output spokes.

Deployment observation is now explicitly provider-shaped without becoming a generalized deployment receipt. Owner-alpha dispatches on one strict provider field. GitHub retains its exact Actions/Pages/environment contract. Forgejo binds an exact 16.x instance, repository, run, job attempts, handles, and terminal deployment-job dependencies, then leaves publication proof to the existing live witness. Both providers remain opaque evidence to the unchanged durable pipeline. See [Forgejo Actions phase one](/cyberbaser/development/forgejo-phase-1/).

### The private owner-alpha lane

The owner now has a second direct-authority route for dogfood: **their machine runs the wiki as a small personal server, and every device they trust is just a browser**. Spot a typo while reading on the phone, tap Edit, fix it, tap Save once; the server machine (which alone holds the vault, Git, and credentials) verifies, applies, publishes, and confirms the change live. Both origins bind one owner-chosen private numeric IPv4 address: loopback by default for single-machine use, or an RFC 1918 / RFC 6598 address so an encrypted overlay or trusted LAN carries the wiki to the owner's other devices (the app is transport-neutral and never coupled to one overlay vendor). Pinned Quartz runs on the unprivileged reader origin. Its absolute Edit links cross to the separate privileged origin, where a one-time bootstrap establishes a per-device owner session; the server console can mint a fresh one-time sign-in link for each additional device. One **Save and publish** action durably records the source session, exact UTF-8 operation, pinned base, policy revision, and live target before the browser receives acceptance.

After acceptance, the policy runs the bounded mechanics without routine approval screens: pre-apply source, OFM, trust, publication, projection, render, and link checks; exact atomic source application; one-parent, one-path commit; normal non-force push to the bound destination; exact Actions run and Pages deployment monitoring; visible live-text verification; and local Quartz rebuild. Startup recovery resumes only states whose durable classification is safe. Ambiguous application state stops for manual intervention rather than replaying an effect.

This does not make an external proposal adapter a writer. It is the owner's own local authority route, restricted to existing tracked UTF-8 LF Markdown body edits and one contiguous exact operation. The hermetic browser acceptance test proves the composition with a temporary checkout and local bare remote; it is mechanical evidence, not unfamiliar-reader or independent-owner usability evidence. The first real policy-activated Cyberbase Save completed on 2026-08-02 through the bare-metal route.

WP2 packages the same server as one Linux/amd64 OCI image with two explicit Docker Engine profiles. Rootless mode runs container `0:0` inside the user namespace that maps to the unprivileged vault owner; rootful mode runs the main process as the vault owner's exact nonzero UID/GID. Linux host networking is mandatory, no `ports:` bridge exists, and the configured numeric private address must be assigned in the Linux namespace Bun joins. The image root is read-only, `/vault` is the only writable host bind, config is staged into private tmpfs, durable state lives in a profile-bound named volume, and HTTPS credentials cross only an operator-supplied Unix socket. The image contains a verified offline Quartz seed, but production Git, deployment observation, and live verification still require outbound access.

Deployment shape: the server machine holds the vault, credentials, and policy; trusted devices hold only a browser session; the public site still changes only through the pushed commit and the vault's own CI. The full operator path, including bootstrap attachment, restart recovery, upgrades, evidence, and deliberate limits, is on [Owner-alpha container deployment](/cyberbaser/development/owner-alpha-container-deployment/). The user journey remains on [Contribution workflows](/cyberbaser/design/contribution-workflows/#the-deployment-story-what-runs-where).

## The verdict

**Cyberbaser, as built, is ten no-authority boundary packages, an append-only decision-ledger package, a private owner-alpha authority application, a separate optional account-free intake application, local-only OCI deployment bundles, and repository CI that governs or verifies parts of a Markdown knowledge base:** what may publish, how disposable copies are projected, how external lanes represent and retain one exact proposal, whether a change damaged the content, which trust route applies, whether links resolve, whether every previously published canonical URL remains canonical or directly redirect-covered, how governance outcomes are recorded, and how one exact operation reaches a verified live page under owner authority. The ten boundary packages do not write authoritative source. The proposal queue writes only bounded review evidence. The ledger CLI writes only its governance JSONL record; its two-stage capture/record adapter is implemented and hermetically tested but not installed in the live vault. The owner-alpha application writes source only as a direct owner-local route after one Save activates a precise durable policy. Its Linux/amd64 image changes deployment mechanics, not authority. The sibling account-free service has no owner authority and writes only its dedicated queue.

The broader architecture is a stable owner-controlled hub between replaceable authoring and rendering spokes. A conforming external rich editor or CMS-like surface may model content however it chooses, but its durable output is now the implemented canonical [`@cyberbaser/proposal`](/cyberbaser/design/proposal-contract/) artifact: one existing Markdown source, one pinned base, and one exact quote- or offset-bound splice. It cannot directly regenerate the source, become a second authority, or bypass owner-controlled review or delegated policy. The shared contract, narrow Forgejo pull-request adapter, local queue, account-free derivation/app, and disabled Quartz form are built. Lane A is not live, linked, installed, or offered. Lane B is local-only, off by default, unexposed, and human-untested. Rich-editor operations and external source application remain separate and unbuilt.

The current interfaces remain narrower than the vision. The private owner-alpha source editor and job page are built for owner dogfood, while GitHub still owns the external contribution editor, identity, PR review, and merge surfaces. The private correction pilot remains a study instrument, and the GitHub path still scatters governance evidence across a raw diff, labels, and logs.

:::caution[What this page does not claim]
No account-free contribution product, public auth service, product moderation UI, preview deployment, offered or installed intake lane, or hosted Cyberbaser server is shipped. Lane B's local queue, disabled form, sibling app, and internal-only deployment bundle are implementation mechanics, not a public service. ## Boundaries: what each part must not do

The separations that keep the system honest, with how each one is currently held. "By code" means something fails if you violate it; "by convention" means nothing stops you.

| Part | Must **not** | Held by |
|---|---|---|
| **Vault (source of truth)** | hold build artifacts · depend on cyberbaser plugins to open in Obsidian · let its file layout be dictated by the URL scheme | **Convention.** R16 shipped verbatim paths partly to keep this true |
| **Publish boundary** | publish by default · trust the plan instead of the result · let a published page inline a private one | **Code.** Fail-closed config, post-hoc leak test, cross-boundary embed check, all fail the build |
| **Hub packages** | apply lossy transforms · regenerate untouched source · be coupled to one renderer or authoring UI · take the owner's editorial authority | **Code and decision.** [R12](/cyberbaser/research/v1-build-plan/#gate-result-run-2026-07-25) removed whole-file re-serialization after measuring 4.6% byte identity over 1,430 real files. ## Open architectural questions

The full list lives in [Open Questions](/cyberbaser/reference/open-questions/). These are the architecturally significant ones, with what is now settled marked as settled.

### Partly answered: where does the hub runtime live?

**The owner dogfood runtime lives on the owner's machine; the offered external product runtime is still unselected.** The ten no-authority boundary packages and the decision-ledger package run in CI, CLIs, injected adapter hosts, the private owner-alpha process, or the separate optional Lane B sibling process. Owner-alpha has two owner-operated packaging shapes: the established bare-metal launcher and WP2's Linux/amd64 OCI image. Both bind two origins on one owner-chosen private numeric IPv4 address (loopback default): an unprivileged Quartz reader and a privileged editor/API protected by one-time bootstraps, per-device sessions and CSRF tokens, and exact Host/Origin policy. The container requires Linux host networking so Bun still owns the exact bind decision; it does not add bridge publishing or a wildcard. On a non-loopback address, transport confidentiality comes from the chosen network (an encrypted private overlay or trusted LAN), not from the app. Durable runtime state remains owner-operated and derivative, not a second content authority.

WP4 now implements a distinct local-only Lane B runtime shape: one off-by-default sibling service on a dedicated internal bridge, with read-only retained bindings and bare Git objects plus one writable proposal-queue volume. It receives no owner credentials and has no source worktree or publication output. A real public deployment still needs a separately selected reverse proxy/TLS/edge-abuse boundary and explicit exposure authorization; none is provided or running. A trusted rich editor used inside an owner's existing environment may have a different deployment shape, but an external spoke still cannot bypass the exact-proposal and owner-controlled application boundary.

The private owner-alpha decision answers where **this dogfood writer** runs. It does not choose the general maintainer or outside-contributor operating model.

### Open: the console fork

The system computes decisions no human sees — the step-3 card at the top of this page. Two designs were priced against a measured budget of roughly **4.7 maintainer-days per month** (96 commits across 11 calendar days in 219 days, tripled to allow for uncommitted effort).

| Option | Build | Ongoing | What it buys |
|---|---:|---:|---|
| **Hosted console** (auth, queue view, preview service, write-back, deploy, abuse handling) | **13.5 d** | **~1 d/month, forever** | One screen where the route, the fidelity verdict, the link delta and a render are the same object. Replayable policy: the trust classifier is pure, so any proposed setting can be re-run against real history |
| **Static generation plus CI annotation** (decision ledger, sticky PR comment, static status page, contributors page from git history, linkcheck on a second renderer) | **4.5 to 6.75 d** | ~0 | Satisfies every non-real-time promise in the vision without a runtime. Loses full-fidelity previews unless the 3-day artifact-preview pattern is also built |

The hosted option costs about three months of everything and then takes a permanent 21% of annual capacity. The static option is 2 to 3 times cheaper to build and has no maintenance tail. **Neither pass recommended a hosted application**, and the anti-console argument is strongest on the narrow claim: never ship a thing that holds moderation, identity or session state, because that is content state outside the commit it produces, which the boundaries table forbids.

The [decision ledger](/cyberbaser/design/decision-ledger/) package and selected two-stage adapter are implemented and hermetically tested. An unprivileged `pull_request: closed` capture uploads only a non-authoritative routing hint; a privileged `workflow_run` recorder binds the exact run and artifact, reconstructs every authority field from GitHub APIs and exact inert Git objects, then publishes one ledger-only commit through bounded normal-push checks. GitHub's [`workflow_run` documentation](https://docs.github.com/en/actions/reference/workflows-and-actions/events-that-trigger-workflows#workflow_run) is the governing trust boundary. The record template contains a deliberate non-runnable immutable-tooling placeholder, so live installation remains a separate explicit authorization step. No real fork run or live append has occurred. The ledger still belongs in commits rather than a hosted database, and it remains the only path to the first of the six auto-merge preconditions ("at least 20 PRs classified with the maintainer's own decision recorded"). Zero live entries have been recorded.

### Open: the missing enforcement

Every validator is advisory. Concretely: `ofm-check` is `continue-on-error`, `linkcheck` is in no workflow at all, the trust gate never merges and never blocks, and the vault's `main` has no protection and no rulesets. The projection is the single exception, and it only fails the build after a merge has already happened.

The constraint that shapes the fix: **the maintainer pushes to `main` directly from Obsidian Git**, so any proposal that requires PRs for all changes breaks daily authoring. The open question is which subset can become required without that collision, and the likely answer is a push-triggered reporting job plus required checks on PRs only.

Thirteen of the seventeen are not a cyberbaser surface, and the four that are consist of one hyperlink, two terminal commands, and a website about the project. Meanwhile `report.denied` (every file with the rule that denied it), `report.strippedLinks` (every boundary-crossing link with line numbers), `report.crossBoundaryEmbeds` and the full asset reachability chain all exist as JSON in a CI artifact nobody downloads.

### Open: assets and block IDs in a web edit

Reframed rather than answered. [R12](/cyberbaser/research/v1-build-plan/#gate-result-run-2026-07-25) removed the whole-file round-trip, so the question is no longer "how does the AST survive re-serialization" but "what does a raw-text splice do when the spliced region contains an embed or a block reference". Still the one genuinely unsolved Tier-1 item in the [translation layer](/cyberbaser/design/translation-layer/).

### Open: incremental builds, and what federation adds

Partly measured, not solved. All 933 selected Markdown sources rebuild into 931 public page URLs in 3m07s to 4m52s in CI, and the artifact sits at roughly a quarter of the 1 GB Pages cap. Nothing incremental exists: every push rebuilds everything.

Federation does not turn that pipeline into one multi-vault build or shared database. Each base keeps its own source of truth and publishes its own public pages, descriptor, inventory, outbound relationships and change information. Other bases and meta-wikis discover those publications from user-chosen seeds and ordinary links.

<p class="cb-fig-note"><span class="cb-chip cb-chip-mute">level zero</span>The direct owner link is the architecture's failure floor. Optional Webmention can notify the target, but neither navigation nor authority depends on it. The active <a href="/cyberbaser/research/federation/#measured-local-fixture-the-narrow-claim-passed">fixture prototype</a> expands this to three subject bases and two competing meta-wikis with peer-published descriptors, inventories and Linksets.</p>

A meta-wiki is an ordinary base, not a central graph service. It publishes its own collections, mappings, annotations, mirrors and indexes as source-qualified claims. Many can disagree or fork. None can overwrite the owner records of another base.

Every crawler, local graph cache, graph database, search engine, ranking model and public index is a **swappable spoke** around those publications. Each stores issuer and retrieval provenance, returns direct owner URLs, and can be deleted and rebuilt from chosen seeds. If losing one of those stores loses knowledge, naming, moderation state or basic navigation, it was not a spoke; it had quietly become the hub.

The bounded test runs with controlled local origins instead of waiting for an outside operator. It makes no interoperability claim: an independently implemented producer or consumer remains the later proof that the published profile travels between implementations.
