Cyberbaser, as built, is **six small packages and three vault-side dogfood CI jobs around an owner-controlled Markdown source**. The packages select what may publish, project disposable copies, prepare one exact candidate splice in memory, classify integrity and trust, and inspect rendered links. None writes the owner's authoritative source. The current GitHub and Quartz screens prove one arrangement; they are replaceable spokes, not the architecture's essence.

The stable model is broader than today's interfaces. Local editors, forge editors, reader-correction controls, rich browser or CMS-like tools, and agents may all be authoring spokes. External spokes must emit bounded proposals against a pinned source base and converge on owner review. The owner continues to author the source directly in their preferred local tool. Renderers remain independently replaceable output spokes.

:::danger[The maintainer's own path has fewer checks than a stranger's]
An honest typo that deletes a callout is caught in the contribution journey and missed in the authoring one. Both validators are wired to `pull_request` only, and direct pushes to `main` are not merely allowed, they are the maintainer's daily authoring path. That constraint is real (requiring PRs for everything would break Obsidian Git authoring), so the fix is not "turn on branch protection", it is **a `push`-triggered validation job that reports rather than blocks**. It has not been built.
:::

## The verdict

**Cyberbaser, as built, is six small packages and three vault-side dogfood CI jobs that govern parts of a Markdown knowledge base:** what may publish, how disposable copies are projected, whether a proposed change damaged the content, which review route applies, whether links resolve, and how one exact candidate splice can be prepared in memory. None writes the owner's authoritative source.

The broader architecture is a stable owner-controlled hub between replaceable authoring and rendering spokes. A conforming rich editor or CMS-like surface may model content however it chooses, but its durable output is a bounded proposal against a pinned base. It cannot directly regenerate the source, become a second authority, or bypass owner review. This adapter contract is an architectural invariant, not a shipped generalized API.

The current interfaces remain much narrower. GitHub and Quartz own nearly every shipped screen. The private pilot kit renders one local exact-correction review artifact, while the GitHub path still scatters governance evidence across a raw diff, labels, and logs.

:::caution[What this page does not claim]
No browser/CMS authoring spoke, auth component, product moderation UI, preview deployment, generalized adapter API, or Cyberbaser server is shipped. A serializer-backed CMS writer is architecturally inadmissible; rich presentation itself is not. `main` on the vault repo has **no branch protection and no rulesets** (verified 2026-07-26: `branches/main/protection` returns 404, `rulesets` returns `[]`), `ofm-check.yml` is `continue-on-error: true`, and the auto-merge step in `trust-gate.yml` is commented out behind six named preconditions. **Nothing in this system can currently block a merge.**
:::

The two lanes that run alongside the build are deliberately decoupled: `ofm-check` asks "is this change safe for Obsidian syntax", `trust-gate` asks "who has to look at it", and neither knows about the other. That decoupling is correct engineering and it is also why there is no single place a maintainer can look.

## Component reference

Two things worth knowing before the table. The renderer spoke has **zero tests** while the six packages have 187, and `encodeRepoPath` in `EditThisPage.tsx` is exported specifically to be testable and has no test. And `agents: []` means the entire agent branch of the trust classifier, the most elaborate logic in that package, is unreachable in production today: every real PR takes the trusted-human branch or the terminal fallback.

## Boundaries: what each part must not do

The separations that keep the system honest, with how each one is currently held. "By code" means something fails if you violate it; "by convention" means nothing stops you.

| Part | Must **not** | Held by |
|---|---|---|
| **Vault (source of truth)** | hold build artifacts · depend on cyberbaser plugins to open in Obsidian · let its file layout be dictated by the URL scheme | **Convention.** R16 shipped verbatim paths partly to keep this true |
| **Publish boundary** | publish by default · trust the plan instead of the result · let a published page inline a private one | **Code.** Fail-closed config, post-hoc leak test, cross-boundary embed check, all fail the build |
| **Hub (the packages)** | apply lossy transforms · regenerate untouched source · be coupled to one renderer or authoring UI · take the owner's editorial authority | **Code and decision.** [R12](/cyberbaser/research/v1-build-plan/#gate-result-run-2026-07-25) removed whole-file re-serialization after measuring 4.6% byte identity over 1,430 real files. Packages may select, project disposable copies, classify, inspect, or prepare candidate bytes; none writes the owner's authoritative source |
| **Authoring adapter** | write canonical files directly · become a second content authority · authorize itself · hide stale or ambiguous source mapping | **Architectural contract, generalized adapter unbuilt.** A conforming local, browser, CMS-like, forge, or agent spoke binds to a pinned base and emits a bounded proposal. Its UI and internal model are replaceable; its source application rules are not |
| **Spoke renderer** | be treated as permanent or unique · hold contribution or auth state · be forked | **Convention, with one crack.** Quartz is pinned and unforked, but the folder-link fix landed as a Quartz plugin rather than in the projection. Worth watching |
| **Federation spokes** | become naming, merge, moderation or navigation authority · flatten conflicting issuers · hold the only copy of knowledge | **Research invariant, not built.** Every crawler, graph store, cache, search provider and ranking model is replaceable, exportable and rebuildable from peer publications and chosen seeds |
| **Owner-local editor** | be replaced or required to act as a client of an external contribution surface | **Principle and current practice.** The owner edits the authoritative source directly in their preferred tool; external proposal rules do not force the owner through a Cyberbaser editor |
| **Governance** | let a change promote its own author · decide from a policy the change itself supplied | **Code.** The policy is read from the base ref, and the classifier fails closed on unknown author types |

## Open architectural questions

The full list lives in [Open Questions](/cyberbaser/reference/open-questions/). These are the architecturally significant ones, with what is now settled marked as settled.

### Answered: where does the hub runtime live?

**It does not. The hub is libraries plus CI jobs.** Every capability runs either on a GitHub-hosted runner (`publish`, `projection`, `ofm`, `trust`, Quartz) or on a developer's machine (`linkcheck`, the CLIs). Nothing of ours runs in a reader's browser and nothing of ours runs on a server, because there is no server.

Any public account-free intake needs a trusted execution point for credentials, abuse controls, and durable intake state. That could be hosted, self-hosted, or part of another explicitly chosen operating model; none is built. A trusted rich editor used inside an owner's existing environment may have a different deployment shape, but it still cannot bypass the exact-proposal and owner-review boundary.

This replaces the question that stood on this page from 2026-06-21 to 2026-07-26, when the honest answer was that nobody had checked.

### Open: the console fork

The system computes decisions no human sees — the step-3 card at the top of this page. Two designs were priced against a measured budget of roughly **4.7 maintainer-days per month** (96 commits across 11 calendar days in 219 days, tripled to allow for uncommitted effort).

| Option | Build | Ongoing | What it buys |
|---|---:|---:|---|
| **Hosted console** (auth, queue view, preview service, write-back, deploy, abuse handling) | **13.5 d** | **~1 d/month, forever** | One screen where the route, the fidelity verdict, the link delta and a render are the same object. Replayable policy: the trust classifier is pure, so any proposed setting can be re-run against real history |
| **Static generation plus CI annotation** (decision ledger, sticky PR comment, static status page, contributors page from git history, linkcheck on a second renderer) | **4.5 to 6.75 d** | ~0 | Satisfies every non-real-time promise in the vision without a runtime. Loses full-fidelity previews unless the 3-day artifact-preview pattern is also built |

The hosted option costs about three months of everything and then takes a permanent 21% of annual capacity. The static option is 2 to 3 times cheaper to build and has no maintenance tail. **Neither pass recommended a hosted application**, and the anti-console argument is strongest on the narrow claim: never ship a thing that holds moderation, identity or session state, because that is content state outside the commit it produces, which the boundaries table forbids.

The genuinely open part is the **decision ledger**: a `pull_request: closed` job appending one line per PR (route, verdict, checks, the maintainer's actual outcome) to a file in the vault. It is a day of work, it lives in a commit so it breaks no boundary, and it is the only path to the first of the six auto-merge preconditions ("at least 20 PRs classified with the maintainer's own decision recorded"). Nobody is keeping that record, so the agent lane can never be enabled on the project's own terms.

### Open: the missing enforcement

Every validator is advisory. Concretely: `ofm-check` is `continue-on-error`, `linkcheck` is in no workflow at all, the trust gate never merges and never blocks, and the vault's `main` has no protection and no rulesets. The projection is the single exception, and it only fails the build after a merge has already happened.

The constraint that shapes the fix: **the maintainer pushes to `main` directly from Obsidian Git**, so any proposal that requires PRs for all changes breaks daily authoring. The open question is which subset can become required without that collision, and the likely answer is a push-triggered reporting job plus required checks on PRs only.

### Open: 17 interaction points, 4 of them ours

Every place a human touches this system today, and whose product they are actually using.

| Whose UI | Count | Which interactions |
|---|---:|---|
| GitHub | 9 | Editing, authenticating, submitting, the OFM annotation, the trust label, the trust rationale, moderating and merging, downloading `projection-report.json`, build health |
| Quartz | 2 | Reading a page; search, graph, explorer, dark mode, backlinks, table of contents |
| A plain text editor | 2 | Hand-editing `publish.yml`; hand-editing `.cyberbaser/trust.yml`. R15 records that the maintainer does not hand-author YAML, so in practice this is an agent session |
| **Ours** | **4** | The "Edit this page" anchor (87 lines of TSX that render one `<a>`) · `cb-linkcheck` · `ofm-check` · this docs site |

Thirteen of the seventeen are not a cyberbaser surface, and the four that are consist of one hyperlink, two terminal commands, and a website about the project. Meanwhile `report.denied` (every file with the rule that denied it), `report.strippedLinks` (every boundary-crossing link with line numbers), `report.crossBoundaryEmbeds` and the full asset reachability chain all exist as JSON in a CI artifact nobody downloads.

### Open: assets and block IDs in a web edit

Reframed rather than answered. [R12](/cyberbaser/research/v1-build-plan/#gate-result-run-2026-07-25) removed the whole-file round-trip, so the question is no longer "how does the AST survive re-serialization" but "what does a raw-text splice do when the spliced region contains an embed or a block reference". Still the one genuinely unsolved Tier-1 item in the [translation layer](/cyberbaser/design/translation-layer/).

### Open: incremental builds, and what federation adds

Partly measured, not solved. All 933 selected Markdown sources rebuild into 931 public page URLs in 3m07s to 4m52s in CI, and the artifact sits at roughly a quarter of the 1 GB Pages cap. Nothing incremental exists: every push rebuilds everything.

Federation does not turn that pipeline into one multi-vault build or shared database. Each base keeps its own source of truth and publishes its own public pages, descriptor, inventory, outbound relationships and change information. Other bases and meta-wikis discover those publications from user-chosen seeds and ordinary links.

<p class="cb-fig-note"><span class="cb-chip cb-chip-mute">level zero</span>The direct owner link is the architecture's failure floor. Optional Webmention can notify the target, but neither navigation nor authority depends on it. The active <a href="/cyberbaser/research/federation/#active-local-prototype-prove-the-shape-with-fixtures">fixture prototype</a> expands this to three subject bases and two competing meta-wikis with peer-published descriptors, inventories and Linksets.</p>

A meta-wiki is an ordinary base, not a central graph service. It publishes its own collections, mappings, annotations, mirrors and indexes as source-qualified claims. Many can disagree or fork. None can overwrite the owner records of another base.

Every crawler, local graph cache, graph database, search engine, ranking model and public index is a **swappable spoke** around those publications. Each stores issuer and retrieval provenance, returns direct owner URLs, and can be deleted and rebuilt from chosen seeds. If losing one of those stores loses knowledge, naming, moderation state or basic navigation, it was not a spoke; it had quietly become the hub.

The bounded test runs with controlled local origins instead of waiting for an outside operator. It makes no interoperability claim: an independently implemented producer or consumer remains the later proof that the published profile travels between implementations.
