The maintainer decided on 2026-09-30 that a pull request opened on their own Forgejo should reach them the same way a form suggestion does: in **Proposals**, read in place, decided with Approve or Reject, put on the page with Apply. No second review surface, no commands. This page records the accepted design and what was built.

:::note[Accepted and built]
The maintainer accepted the core shape, the repository alias list, and the rule that the first version never writes to the forge, and asked for it to be built tests first. It is built and proven hermetically. No live forge has been watched yet; that waits on the maintainer's Forgejo and is recorded separately.
:::

## The shape in one paragraph

The service that already receives form suggestions, and already holds the queue's only writer lock, has a second ear: it watches the forge for open pull requests on the vault copy. When it sees a head it has not seen, it reads it through the existing adapter, exactly as the live check does, and puts the resulting exact suggestion into the same queue as a Lane A entry with the author's forge identity attached. From there nothing is new: the owner app validates it, lists it in Proposals with a line saying it came from a pull request, and the same Approve and Apply steps follow. The watcher never writes to the forge, never merges, never comments, and never touches source.

## What the owner sees

1. **Someone opens a pull request** on the vault copy in Forgejo, in Forgejo's own editor. Only accounts the owner created can do this; registration is off.
2. **Within a minute it is in Proposals**, in Needs review, reading like any other suggestion, with one extra line: *From pull request #42 on your forge*, linking to the request. The review page adds the forge account number.
3. **Review, Approve or Reject, Apply.** Identical. The trust route comes from the trust policy naming that forge account, or full review for an account the policy does not name.
4. **After Apply, the receipt says one more thing:** the pull request on the forge is still open, and the owner closes it there. This first version never writes to the forge.
5. **If the author pushes again**, the newer version of the request is the row in Proposals and earlier versions fold under it as links. If the request is closed on the forge, the suggestion stays until it expires, and the owner can reject it; the first version does not learn about closures.

## Where the watcher lives, and why

The queue has one writer: the intake service takes an exclusive lifetime lock when it opens the queue, and the owner app only ever reads through the private socket. So the watcher is a second input inside the intake service, beside the form endpoint. Two consequences, both built:

- The service can run **with the public form endpoint off**: `listen`, `publicOrigin`, and `allowedFormOrigins` may be null and empty when the `forgejo` block is enabled. The launcher reports which inputs are on.
- The service's recovery check accepts Lane A entries and proves them from the watcher's own clone, from retained objects only, before the queue opens to callers.

## What the watcher does, exactly

Every poll, default once a minute:

1. One read-only request to list open pull requests on the configured repository, after the version preflight.
2. For each open, non-draft request whose number and head commit it has not seen in the queue: the adapter's four reads (version, repository, request, author), the exact base and head commits fetched into private temporary refs of the watcher's own clone, the one changed Markdown file, one splice proven to reproduce the head, and the trust policy at the base commit.
3. The base commit is fetched again into a retained ref under `refs/cyberbaser/lane-a/retained/`, so recovery can prove the entry after the adapter's temporary refs are gone. Automatic garbage collection is off in the clone.
4. One enqueue: the canonical proposal, the base bytes, the policy evidence, the verified subject `forgejo:<origin>#user=<id>`, and a Lane A carrier naming repository, request number, and head commit. The queue derives replay identity from those three, so re-polling can never enqueue the same head twice.
5. Anything the adapter refuses (a draft, two files, a bot account, a request that no longer descends from its base) is skipped, logged, and not asked about again until its head changes.

The watcher keeps its clone under `forgejo.cloneDir`, created on first use with the remote fixed to the configured repository. A token, if the repository is private, comes from a mode-0600 file named by `forgejo.tokenFile`, read per request and never logged.

## The repository identity problem, and the alias list

The adapter binds each proposal to the repository it read from: the Forgejo copy's URL. The owner app compares that against its own remote, which is GitHub, at review and again at Apply, and refuses on mismatch.

Built answer: the owner's durable policy may list a few repository identities that count as the same vault, in `repository.aliases`. Review and Apply accept a proposal bound to any listed identity, and everything else stays exact: the base commit must still be reachable from the owner's branch, and the page's blob must still be the exact object reviewed. That holds because the copy was migrated from GitHub with identical commit history. It stops holding the day something is merged on the forge, so the rule for the copy is: **never merge there**; suggestions are consumed by the inbox and requests are closed by the owner. An empty alias list leaves the pinned GitHub policy revision unchanged.

## What stays out of this version

- No writes to the forge: no comments, labels, closes, or merges.
- No mirroring or syncing between GitHub and the forge; the copy drifts and is only for suggestions.
- No accounts created by the watcher, no open registration.
- No public exposure of the forge or the intake service.
- No change to what a suggestion may be: one existing Markdown file, one splice.

## Evidence

Hermetic, recorded on 2026-09-30:

- `apps/account-free-intake/test/forgejo-watcher.test.js`: the real service with the form off and the watcher on, against the adapter package's fake Forgejo and a real local Git fixture. One request enqueues once and only once across polls with the base retained and no temporary refs left; a draft is ignored; a new head of the same request enqueues a second entry; a two-file request is skipped with the adapter's code and not re-read; the service restarts and recovers both Lane A entries by re-proving them from the clone; the runtime starts without a public listener and stops the watcher on close; the forge's own refs are untouched and the token never appears in the queue or the log.
- `apps/owner-alpha/test/config.test.js`: the alias list is accepted, normalized, and refused when malformed, duplicated, longer than eight, or naming the remote itself; an empty list keeps the pinned revision.
- `apps/owner-alpha/test/server.test.js`: a forge request reads as one suggestion, with the forge line on the row and the header, earlier heads folded, the waiting count counting requests not heads, and the close reminder on the applied receipt.
- `packages/forgejo-intake/test/api.test.js`: the open pull request listing is one bounded read-only page after the version preflight.

Not yet: a live forge watched, or a real pull request seen in Proposals. That is the [Lane A live validation](/cyberbaser/development/forgejo-lane-a-live-validation/), now runnable from the inbox itself once the maintainer's forge is up.
