:::caution[Corrected 2026-07-29. The earlier version confused a rejected writer with an entire interface category.]
The old plan specified a Decap-based web CMS path, per-PR preview deployments, and a CI gate that blocks merges. None exists. [R12](/cyberbaser/research/v1-build-plan/#gate-result-run-2026-07-25) permanently rejected the evaluated CMS products' whole-file save behavior; it did **not** reject rich browser or CMS-shaped authoring as a replaceable interface. The preview and gate remain designed but unbuilt. Every claim below is labelled **built**, **borrowed**, **pilot**, or **designed, unbuilt**.
:::

Cyberbaser does not prescribe one authoring interface. Reader correction tools, rich browser editors, CMS-like front ends, forge editors, local Markdown tools, and agents may all be replaceable spokes. External spokes submit bounded proposals through the owner-controlled exact-change boundary; they do not directly rewrite or become a second authority for the Markdown source. The owner's local editor remains a distinct direct-authoring lane.

Every contribution path the product offers must still work **independently**; this does not require three named paths or a Web CMS (see [Principle 4](/cyberbaser/getting-started/principles/#4-every-offered-contribution-path-must-work-independently)). This page states the mechanisms that exist, preserves the withdrawn serializer-backed CMS proposal as history, and separates shipped mechanics from intended but unbuilt authoring spokes.

## Historical proposal: serializer-backed CMS writer — withdrawn

**Status: that writer design is withdrawn, not deferred.** It specified Decap with Open Authoring: a rich web interface that would render Markdown, offer wikilink and callout widgets, show a live preview, then save by regenerating the complete file and opening a fork-and-PR invisibly.

It was ruled out on measurement, not taste. The [write-path proposal](/cyberbaser/research/proposal-write-path/) evaluated Decap, Sveltia, TinaCMS, EmDash, and Pages CMS in their available save configurations. Every one re-serialized the whole file. [R12](/cyberbaser/research/v1-build-plan/#gate-result-run-2026-07-25) then measured only **4.6% byte identity** across all 1,430 real vault files and permanently prohibited that source-write mechanism.

That result closes arbitrary whole-file save adapters, not rich authoring as an interface category. A browser editor may parse content, use blocks, render WYSIWYG, or keep transient UI state. To conform, its adapter must bind to a pinned source base, emit a bounded proposal, preserve every untouched byte, and leave owner-controlled application outside the editor. An arbitrary CMS cannot become plug-and-play with zero integration because its document model still has to map deliberately onto that proposal boundary.

**Why the old three-path framing ended.** The principle is path independence, not a mandatory count or a commitment to three specific surfaces. In practice there are **three source-change lanes** today, two of them owner-only:

- direct owner-local authoring in Obsidian + Git;
- the private owner-alpha wiki: browser editing from the owner's trusted devices, with one Save running the policy-bound exact pipeline;
- an account-required external proposal through GitHub's web editor.

**The persona Principle 3 exists for has no shipped path.** A domain expert with no GitHub account and no wish to make one cannot contribute today. [`OD-01`](/cyberbaser/research/owner-self-dogfood/) tested the same exact-proposal and local-review boundary once with the maintainer switching reader and owner contexts. The operator carried the submission through existing libraries by hand; it was not an anonymous endpoint, editor, automatic writer, forge integration, independent-reader result, or closure of Q09.

## Maintainer local path: Obsidian + Git

**Status: built. This is the maintainer's daily path.**

**Target user:** vault-native power user, comfortable with git or an Obsidian git plugin.

### Flow

1. **Clone**: clone `cybersader/cyberbase` as an Obsidian vault
2. **Edit locally**: full Obsidian affordances (wikilinks, callouts, graph view, templates)
3. **Commit & push**: either via obsidian-git or a terminal
4. **Build trigger**: `publish-site.yml` fires on push to `main` and runs the publish boundary, the projection, and the Quartz build, then deploys to GitHub Pages
5. **Live**: **3 to 5 minutes later** the change is on the published site

> [!info] The build time, measured
> Five successful end-to-end runs (push to bytes live) took **3m07s, 3m15s, 3m22s, 3m27s and 4m52s**. An earlier version of this page promised "~60-90 seconds"; that number was never measured and is 2-5x optimistic. The pipeline rebuilds 933 selected Markdown sources into 931 public page URLs every time — see [Q05](/cyberbaser/reference/open-questions/) on incremental builds.

### Constraints

- Must not require any cyberbaser-specific plugins or tooling inside Obsidian (holds: the vault repo carries only `publish.yml` and two workflow files)
- The vault must work as a plain Obsidian vault even if cyberbaser doesn't exist
- Pre-commit hooks (if any) must be optional, not required

### What is not enforced on this path

The maintainer pushes to `main` directly, and `ofm-check` and `trust-gate` are both `pull_request`-triggered. **A direct push is validated by nothing.** The contributor path has more checks than the maintainer path, not fewer. That asymmetry is deliberate for now (requiring PRs for all changes would break daily authoring from Obsidian), but it is a gap, not a design.

## Private owner-alpha wiki: one Save, policy-bound publication

**Status: built for private dogfood; the first real outward acceptance Save completed on 2026-08-02.**

**What this is in practice.** The owner's machine becomes a personal wiki server, the same self-hosting pattern as running Jellyfin or Home Assistant at home. The vault, Git, credentials, and publishing policy all stay on that one machine. Every other device the owner trusts (phone on the couch, laptop in another room) is just a browser pointed at the server's private address: browse and search the full wiki, tap **Edit** on the page with the mistake, fix the sentence, tap **Save and publish** once, and the server does the rest. Noticing a problem and fixing it become the same moment, from wherever the owner happens to be, and the phone never holds the vault or any secret. Nothing is exposed to the public Internet; readers of the *published* site are untouched by any of this.

The owner launches one Bun application bound to one owner-chosen private numeric IPv4 address (`127.0.0.1` by default, which keeps everything single-machine). Setting it to an RFC 1918 or RFC 6598 shared-address-space address instead lets an encrypted private overlay or trusted LAN carry the wiki to the owner's other devices; each additional device signs in through a one-time link the owner mints at the server console. The app is transport-neutral: it neither knows nor cares which private-network product or protocol carries the traffic, and it never binds a wildcard or public address. Startup verifies a clean canonical checkout against the actual remote branch, selects and projects the public corpus, builds pinned Quartz in owner mode, validates the rendered site, and serves browsing and search from an unprivileged reader origin with source editing and durable job status on a separate privileged origin. On WSL, the bare-metal launcher mirrors runtime code and derived state into a marked private ext4 cache so Quartz does not pay the measured many-small-file penalty of `/mnt/c`; the container path instead requires native Linux storage and does not run WSL mirroring code.

Opening **Edit** binds the exact tracked Markdown path, renderer slug, base commit, policy revision, source bytes and digest, Git mode and object ID, and live URL. The first milestone accepts one existing UTF-8 LF Markdown body edit, preserves YAML frontmatter bytes, derives one minimal contiguous UTF-8 operation, and rejects no-ops, stale source, creates, deletes, renames, assets, and multi-file changes.

### The deployment story: what runs where

Three machines participate, and each holds exactly what it needs:

| Place | What runs there | What it holds |
|---|---|---|
| **The server machine** (owner's desktop or a small home box) | The owner-alpha app: both wiki origins, the editor, the whole Save pipeline | The vault checkout, Git push credentials, the durable policy, job evidence |
| **Any trusted device** (phone, laptop) | Just a browser on the private network | A session cookie. Never the vault, Git, or any credential |
| **GitHub** (current dogfood infrastructure, not essence) | The vault repo, the `publish-site.yml` Actions workflow, Pages hosting | The canonical remote and the public site |

The wiki the owner browses is served locally by the server machine, rebuilt from the vault on startup and after every accepted change; it is not the public site. The public site only changes when the server pushes a commit and the vault's own CI deploys it, exactly as if the owner had pushed from Obsidian.

**What a Save looks like in time.** Sub-second to a few minutes of local checks (the render check builds the site twice to prove the edit lands cleanly), then the commit and push in seconds, then three to five minutes of GitHub Actions build-and-deploy that the server merely watches, then the live-page confirmation and local rebuild. The owner can close the browser after the redirect; the job is durable on the server and the status page shows where it is. If the server is stopped mid-job, the next launch resumes any state that is provably safe to resume and stops for the owner otherwise.

**Standing it up now has two documented shapes.** Bare metal remains: clone the repo, copy `owner-alpha.example.json` to a mode-`0600` local config, point it at the vault, and run the launcher. WP2 adds the [operator-first container path](/cyberbaser/development/owner-alpha-container-deployment/): build one immutable Linux/amd64 image locally, choose an explicit rootless or rootful Docker Engine profile, bind the exact vault and credential-free config, mount one profile-bound state volume and one narrowly scoped HTTPS credential socket, then validate, initialize, and start detached. Linux host networking is mandatory, Docker Desktop and bridge publishing are unsupported, and Bun still binds only the exact owner-selected private address. The operator attaches to the live TTY, enters `b`, consumes the one-time link, and detaches without stopping the server.

The OCI package is mechanically accepted, not published. A two-browser fixture Save reached a local bare Git remote and replacement recovery passed. The real 2026-08-02 Cyberbase Save used the bare-metal route; no physical-device Save, external-forge/live-site Save from the container, registry publication, or service installation is claimed.

### The Save pipeline in detail

Clicking **Save and publish** is the edit-specific owner authority event. There is no routine Apply, Commit, Push, Deploy, Approve, or Reject step. The durable local policy then:

1. reruns checkout, source, byte-identity, OFM, trust, publication, projection, render, and link-delta checks;
2. applies only the exact operation through an atomic same-directory replacement;
3. verifies and creates one single-parent, one-path commit atop the bound base;
4. pushes the exact commit normally and never force-pushes, merges, rebases, or guesses conflicts;
5. binds and monitors the exact GitHub Actions run and Pages deployment;
6. confirms the exact live page lost the old visible witness and gained the new witness once; and
7. rebuilds the local Quartz owner site at the confirmed commit.

This direct owner route is not an exception to the source-integrity rule. It is the owner's authority expressed through the same exact-change boundary. External tools still submit proposals and cannot acquire the owner policy, browser session, source path, Git command, remote, URL, or refspec from request data. The private app does not answer Q09 and does not select a generalized rich editor, hosted service, database, or adapter API.

## Shipped contributor path: Direct GitHub

**Status: built, and it is the only path an outside contributor can use.**

**Target user:** originally scoped as "developer, knows git, wants a quick fix." In practice it is now everyone who is not the maintainer.

### Flow

1. **Edit link**: every page carries an "✎ Edit this page" link. It sits under the article title next to the page metadata, not in the footer, and it is small grey text rather than a prominent button. 931 of 931 pages verified as carrying it
2. **GitHub web editor**: opens the raw markdown in GitHub's web UI. The contributor sees `[[wikilinks]]`, `> [!note]` and `%%comments%%` as plain text, with no rendering and no preview
3. **Auth**: GitHub prompts for an account. There is no way past this step without one
4. **Commit**: GitHub forks the repo behind the scenes, creates a branch, and opens a PR
5. **Checks**: `ofm-check` annotates any OFM damage; `trust-gate` applies a `trust:<route>` label. Both are advisory
6. **Merge**: the maintainer reads the diff on github.com and clicks Merge

### Constraints

- Contributor must NOT need to understand Obsidian syntax to make safe edits (partially met: the syntax is visible and unexplained, but `ofm-check` catches damage after the fact)
- Wikilinks and callouts should be visible as raw text but must not break when round-tripped (met by construction: GitHub's editor writes back only the bytes the contributor typed)
- The "Edit this page" link must go to the exact file that renders the current page (met: `EditThisPage.tsx` builds the link from the projection's verbatim path)

### Open questions

- Do we surface a syntax hint for Obsidian-specific constructs in the raw view?
- Should the PR template auto-fill with the page being edited?

## Trusted-contributor rich authoring: intended, unbuilt

**Status: architecturally allowed; no editor or adapter selected.** A trusted contributor may eventually use a browser WYSIWYG editor, hybrid Markdown/preview surface, CMS-like front end, or another specialized tool for larger section edits and new content. Cyberbaser should be able to replace that surface without replacing the source authority, review policy, renderer, or forge.

The stable boundary is conceptual today, not a shipped API. A conforming authoring spoke must:

1. read a known source path and pinned base representation;
2. return a bounded, human-reviewable proposal rather than write the authoritative source directly;
3. identify the intended old and new source content precisely enough to fail closed when the base is stale or mapping is ambiguous;
4. preserve every byte outside the declared change by construction;
5. carry rationale, source evidence, and author/trust claims without letting the spoke authorize itself; and
6. let the owner-controlled boundary run integrity, publication, link, trust, and rendered-candidate checks before application.

The current `@cyberbaser/correction` package proves only one existing file, one exact quote, and one splice. It does not yet define multi-splice, structural, new-page, frontmatter, asset, or generalized rich-editor operations. [Translation Layer](/cyberbaser/design/translation-layer/) tracks the remaining source-mapping and unsupported-construct questions.

## Account-free correction: one owner loop complete

**Status: bounded owner evidence complete, no product surface shipped.** The [owner self-dogfood result](/cyberbaser/research/owner-self-dogfood/) used the exact seven-field local instrument: page URL, exact quote, replacement, rationale, factual source, optional public credit name, and credit consent. Those fields are observation inputs. They are not the product form, a contribution API, the permanent minimum payload, or a decision about whether the eventual reader surface is inline, selection-based, raw, or rich.

In `OD-01`, one maintainer switched between reader and owner contexts. The operator converted the submission into one exact UTF-8 byte splice, proved every byte outside it unchanged, ran OFM/trust/render/link checks, and assembled a local review card. The owner accepted the candidate, then separately authorized application and publication. The harness did not apply or publish the change itself.

The original charter also assigned stale source and ambiguous quote to `OD-02`, and owner rejection to `OD-03`. Those attempts are **Not run — superseded** and blocked from initialization. Deterministic synthetic `ADV-*` scenarios now prove those mechanics; the rejection fixture is not a human owner rejection and creates no human-decision artifact. This evidence cannot establish ordinary-reader completion, independent-owner preference, or a zero-account product. The preserved [five-reader pilot](/cyberbaser/research/concierge-human-correction-pilot/) remains optional before making those stronger claims.

## Cross-path concerns

### Conflict resolution

> [!info] Concurrent edits
> Two contributors edit the same page at once. The outcome depends on the timing:
> - If both edits are sequential (first merges before second opens), git handles it fine.
> - If both land simultaneously as open PRs, the second gets a merge conflict and must rebase.
> - There is no realtime collaborative editing. That's fine — the contribution rate is low and async.

### Review model

The trust classifier computes a route for every PR. What happens next is entirely manual.

| PR type | Computed route | What actually happens |
|---|---|---|
| Typo fix from trusted contributor | `auto-merge` | Label applied. **Nothing merges.** The auto-merge step is commented out and no required check exists |
| Typo fix from unverified identity | `full-review` | Classifier behavior exists; no shipped account-free intake produces this route today |
| Content change from trusted | `quick-review` | Label applied, maintainer merges by hand |
| Content change from unverified identity | `full-review` | Classifier behavior exists; no shipped account-free intake produces this route today |
| Structural / navigation change | `full-review` | Label applied, maintainer merges by hand |

Trusted contributors are designated in **`.cyberbaser/trust.yml`** in the vault repo (not `.github/trusted-contributors.yml`; the file moved out of the forge's namespace deliberately, per [dissent §1.4](/cyberbaser/research/dissent/)). Moving someone onto that list is a conscious act, and the policy is read from the base ref, so a PR cannot promote its own author.

**Nothing has ever auto-merged, and nothing can.** Enabling it needs three things that do not exist: branch protection on `main`, the site build as a required check, and the commented-out step turned on. The first of those collides with the maintainer's direct-push workflow, which is why it has not happened.

### Decision recording after closure

The [decision ledger](/cyberbaser/design/decision-ledger/) now has an implemented two-stage GitHub adapter for recording what the maintainer actually did without giving the fork-triggered workflow write authority. Stage A runs on `pull_request: closed` with no repository permissions or checkout and uploads only a bounded routing hint. The hint is not evidence: it contains repository/run identity and the PR number, but no route, actor, decision, Git object, check, timestamp, path, command, or refspec.

Stage B runs through GitHub's [`workflow_run` trust boundary](https://docs.github.com/en/actions/reference/workflows-and-actions/events-that-trigger-workflows#workflow_run). It binds the exact source run and artifact, then reconstructs authority from the pull-request, labels, timeline, collaborator-permission, and check-runs APIs plus exact inert base/head Git objects. A closed-unmerged decision uses the unique timeline `closed` event matching `closed_at`; the actor must currently have `maintain` or `admin` permission. The resulting row is the first successfully published Stage B observation, so mutable labels, checks, and permission are observed at record time rather than claimed as a perfect closure-time snapshot.

The composition is hermetically tested for maintainer, fork, closed-unmerged, duplicate, and tampered-artifact scenarios. It is **not installed** in the live vault: the record template still carries a deliberate non-runnable immutable-tooling placeholder, no real fork run has occurred, and the live ledger has zero observations. Installation and the first outward write require separate explicit authorization.

### The policy, concretely (cyberbase's own)

This is the actual moderation policy for the dogfood vault, written out to prove the trust-curve story survives contact with specifics. Any maintainer using cyberbaser would write their own version of these two paragraphs, and the trust dial is exactly which parts they tighten or loosen.

> **Every shipped external proposal lands in the moderation queue; nothing proposed from outside goes live without the owner's policy route.** The owner's local Markdown authoring is a separate direct lane and is not a moderation client. In the current GitHub path, the maintainer reviews **the diff on the PR page**, plus the `ofm-check` annotations and the `trust:<route>` label, and aims to act within a few days; "act" means merge, request changes, or reject with a one-line reason. Accepted proposals make the content more true, current, or clear, and cite a source for factual claims that are not self-evident. The policy intends to welcome account-free corrections on the same editorial terms, but that intake has not shipped; today an outside contributor needs GitHub.
>
> **Held or rejected without debate:** spam and promotion, edits to the personal folders (out of scope for contribution), factual changes with no source, drive-by rewrites of a page's voice or structure, and anything the maintainer judges to be generated bulk content. Contributors earn the trusted list after roughly three merged, unproblematic edits, and drop off it on the first spam or bad-faith submission; repeat abuse gets blocked at the repo (and, if volumetric, handled at the edge, which is [a separate problem](/cyberbaser/concepts/problem/#contribution-on-your-terms)). The maintainer's call is final; there is no appeals process at this scale, and that's a feature, not a gap.

> [!warning] What this policy used to say, and why it changed
> It committed the maintainer to reviewing "the rendered preview (not just the diff)." No rendered preview exists anywhere in the pipeline, so that clause made the written policy uncheckable. It is amended above to describe what a reviewer can actually see today. If per-PR previews ship, amend it back.

### Preview / staging

**There is no preview deployment. No PR has ever been rendered before merge.**

Three separate claims in the earlier version of this section were false, and they are worth stating individually because each fails for a different reason:

| Claim | Why it is false |
|---|---|
| "Every PR gets a preview deployment from the same pipeline that builds the site" | `publish-site.yml` triggers only on `push` to `main` and `workflow_dispatch`. It deliberately refuses a `pull_request_target` trigger, because that would run fork-authored content in a job holding write scopes on the vault ([pwn-request](https://securitylab.github.com/resources/github-actions-preventing-pwn-requests/)). The refusal is a security decision, not an oversight |
| "The maintainer reviews the rendered preview before merging" | Nothing renders it. The maintainer reads a raw markdown diff on github.com |
| "This is the CI gate: if the preview fails to build, the PR can't merge" | `ofm-check.yml` is `continue-on-error: true`, `trust-gate.yml` is decision-only, and `main` has **no branch protection and no rulesets**. No check can block any merge |

**The commitment stands; the implementation does not exist.** The design is written and costed: two CI jobs split across a trust boundary, a `pull_request` build job with no secrets producing an artifact, and a `workflow_run` publish job running base-branch code that never checks out the contributor's branch, publishing into a subpath of a second Pages site on its own origin. See [Hub BOM · Per-PR rendered previews](/cyberbaser/research/proposal-hub-bom/#per-pr-rendered-previews) for the full shape and the reason GitHub Pages cannot do it in one repo (one site, one environment, one concurrency group).

A quarter-day interim exists too: have the PR job run the same projection and Quartz build and **upload the output as a workflow artifact**, which the maintainer downloads and serves locally. No second host, no policy exception. Written up in [renderer URLs · adjacent](/cyberbaser/research/proposal-renderer-urls/#adjacent-per-pr-previews-flagged-not-owned-here).

### Attribution

> [!warning] Unverified, and three pages depend on it
> The claim that "contributor names appear in git history automatically, so attribution is preserved without any special handling" has **never been observed working**. It was written about Decap's fork flow, which no longer exists in the write path.
>
> The mechanism today is GitHub's own edit-and-fork flow, and the expectation is that the fork's commit author is the contributor's account and survives the merge. That is an expectation, not a measurement. The two live contribution PRs run during [R17](/cyberbaser/getting-started/roadmap/) were both authored by the maintainer's own account, so they could not have tested it.
>
> This matters beyond UX: [Legal & Governance](/cyberbaser/design/legal-and-governance/) makes commit history the attribution record the content license points at. An untested claim is currently load-bearing for a licensing obligation.
>
> Tracked as an open question — see [Q08 · Does the fork flow actually attribute the contributor?](/cyberbaser/reference/open-questions/#q08--does-the-fork-flow-actually-attribute-the-contributor) and the reopened brief [07 · Contributor attribution](/cyberbaser/agent-context/zz-challenges/07-contributor-attribution/). The check is roughly ten minutes of work: one `git log --format='%an %ae'` over the merged contribution PRs, plus one PR opened from a second account.

**What a reader sees today: nothing.** The published site's page layout is breadcrumbs, title, date and reading time, tags, and the edit link. There is no author line, no contributor list, no avatar, and no contributors page. The vault vision's "show contributors at the top of each page with pic and contributors page" has not been designed, costed, scheduled, or explicitly declined.

### Licensing

Contribution only works legally if the vault has a content license with a contributor clause; without one, every accepted edit is owned by its contributor and readers can't reuse anything. The full treatment (license choice, mixed-vault carve-outs, the contributor clause) lives at [Legal & Governance](/cyberbaser/design/legal-and-governance/). Note the dependency flagged above: that page's attribution argument rests on the unverified claim.

### Abuse / spam

> [!warning]+ Abuse handling today is entirely GitHub's
> There is no OAuth proxy, no rate limiter, and no cyberbaser-operated intake endpoint. What actually protects the repo:
> - GitHub's own account requirement and anti-spam on fork PRs
> - The maintainer reading every PR, since nothing auto-merges
> - Repo-level blocking for a persistent bad actor
>
> The per-account rate limiting the earlier version credited to "Decap / the OAuth proxy" does not exist, because neither component does. Rate limiting becomes a real requirement the moment an anonymous intake endpoint ships, and it is part of that design rather than a separate control.

## Minimum viable contribution set

Based on prior art ([awesome-* repos](/cyberbaser/research/prior-art/#awesome--repos)), the floor was set as **"as easy as editing an awesome-list repo on GitHub"** — 3 clicks: Edit → type → Propose change.

That floor is met, and entirely by GitHub's editor rather than by anything cyberbaser built. It clears the bar for a contributor who already has a GitHub account, and it does not satisfy [Principle 3](/cyberbaser/getting-started/principles/) for someone who does not. `OD-01` completed one real owner loop and recorded the handoff and review burden; the remaining chartered obligations were superseded by synthetic mechanical coverage. This cannot earn an ordinary-reader product claim. If Cyberbaser later needs that claim, the deferred five-reader protocol still requires at least 3 of 5 unaided submissions in five minutes or less, two substantive accepted-and-live corrections, and independent-owner preference.
