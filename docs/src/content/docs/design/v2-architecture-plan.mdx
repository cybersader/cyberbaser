## The one-sentence architecture

Cyberbaser stays a **hub of no-authority libraries around an owner-controlled source**, and everything in this arc is about giving that hub **operational homes** (a container, a forge, an owner surface) without letting those homes become content or identity authorities: identity is delegated to the surface that carried the proposal, canonical content and policy plus portable governance history live in commits, owner-local create-once decisions may bind exact proposal evidence, and every intake lane converges on the same trust-curve-plus-owner-review boundary.

## Standing constraints (locked, non-negotiable in this arc)

1. No whole-file re-serialization in any source-application path (R12). External spokes emit exact base-bound proposals; only the owner-alpha route writes, under one-Save policy.
2. No Cyberbaser component becomes an identity source of record or persists browser-session credentials. An owner-operated local component may retain canonical create-once decisions bound to exact proposal evidence; those decisions grant no source-write or publication authority by themselves. Canonical content, policy, and portable governance history remain in commits. (Architecture boundaries table.)
3. Accounts are never the safety mechanism. Trust curve + moderation queue + owner review are. Anonymous is a supported trust-floor, not an error.
4. Renderer-, forge-, and transport-agnostic. GitHub, Quartz, and any overlay network are swappable dogfood infrastructure. No hyperscalers; numeric private addresses; no overlay-vendor coupling in product code.
5. The maintainer runs no hosted infrastructure for others. Deployable shapes are Forgejo-native and one-click container self-host. Docs are a first-class deliverable of every package.
6. Evidence before product claims; peer need before protocol work. The five-reader pilot and federation profile stay parked.

**Owner-decision storage amendment (2026-08-20).** The earlier “configure and delegate; never store moderation state” language was too broad. The selected Wave 1 boundary permits owner-alpha to retain one immutable Approve or Reject decision per exact proposal evidence object in its ignored owner-controlled local store. The queue remains proposal evidence only and keeps only `pending-review` and `expired`. A decision records owner intent, not source application authority: it cannot apply, write, commit, push, deploy, publish, or rebuild. The decision embeds the reviewed evidence so history survives queue expiry or purge. An exact retry returns the existing decision; a contradictory retry fails closed. Canonical Markdown and policy remain in Git commits, and any later portable governance history still belongs in commits. This does not relax the identity, browser-session, external-writer, federation, or disposable-spoke invariants.

## Work packages, in dependency order

### WP1 — Trusted ledger trigger (installed; first live row published)

**Problem addressed.** Public-fork `pull_request` runs get a read-only token, so a one-stage closed-PR job cannot push ledger entries for exactly the external-contributor case the ledger exists to record.

**Implemented design: two-stage `workflow_run`.** Stage A (`pull_request: closed`, `permissions: {}`) checks out nothing and uploads one small routing hint containing only repository identity, source run identity/attempt, and PR number. It carries no route, actor, decision, SHA, timestamp, check, OFM result, URL, path, command, ref, or refspec. Stage B (`workflow_run`, trusted base-repository code, narrow read scopes plus `contents: write`) binds that hint to the exact refetched source run and its single bounded artifact, then reconstructs every authority field from the pull-request, issue-label, timeline, collaborator-permission, and check-runs APIs plus exact inert Git objects. The artifact is non-authoritative.

Stage B records the first successfully published observation. Labels, checks, and current actor permission are observed during Stage B, not claimed as perfect closure-instant snapshots. Safe publication uses a fresh detached worktree, permits only `.cyberbaser/decision-ledger.jsonl`, creates one single-parent factual commit, verifies the exact destination and branch before and after a normal non-force push, and retries only a classified fast-forward branch-advance race. See [Decision Ledger](/cyberbaser/design/decision-ledger/) and GitHub's [`workflow_run` security guidance](https://docs.github.com/en/actions/reference/workflows-and-actions/events-that-trigger-workflows#workflow_run).

**Package acceptance passed.** Hermetic tests cover a maintainer PR, fork PR with contributor code kept inert, closed-unmerged actor reconstruction, duplicate delivery with no second mutation, and tampered artifact rejection before Git mutation. The record template deliberately contains a non-runnable all-zero Cyberbaser tooling placeholder so installation must substitute one reviewed immutable commit.

**Live installation and first publication are complete.** Cyberbase installed the two reviewed workflows. Two initial recorder attempts failed closed and exposed custom-run-name and artifact-download mismatches; reviewed repairs followed. Capture run `31648052403` and Record run `31648065388` then published one valid unclassified maintainer row through a single-parent ledger-only commit. The classified count remains zero. Real fork, closed-unmerged, duplicate-redelivery, and tamper live cases remain bounded follow-up evidence, not blockers for the owner-review wave.

### WP2 — Container packaging (implementation and mechanical acceptance complete)

**Problem addressed.** Owner-alpha needed an always-on owner-operated home and Q09's later self-host shape needed a reproducible package. The package had to preserve the exact private-address, source-authority, credential, bootstrap, and restart boundaries rather than hiding them behind a permissive container default.

**Implemented design.** One Linux/amd64 OCI image contains Bun, Node, Git, the six owner-alpha package dependencies, the renderer wrapper, and a verified read-only Quartz v4.5.2 seed. Two explicit Compose profiles avoid an ambiguous portable-identity claim: rootless Docker runs container `0:0`, mapped to the ordinary daemon user who owns the vault; rootful Docker runs the main process as the vault owner's exact nonzero UID/GID. A networkless one-shot initializer prepares only the profile-bound named state volume.

Linux host networking is mandatory for v1. Compose defines no `ports:` and no bridge alternative. The configured private numeric IPv4 address must exist in the Linux namespace Bun joins, and the app binds that exact address on the owner port and adjacent reader port. Docker Desktop is outside the supported contract. The image runs the existing server directly, never a bare-metal launcher, and does not execute WSL mirroring code.

The mount contract is explicit: `/vault` is the read-write exact worktree root and only writable host bind; the credential-free config is a read-only bind copied without symlink following into private `/run/owner-alpha` tmpfs; durable state lives in one profile-bound named volume; render scratch uses a size-bounded executable `/tmp` tmpfs; and an operator-supplied HTTPS credential broker is exposed through a read-only directory containing only `helper.sock`. SSH remotes and SSH-agent-only authentication are unsupported because schema version 1 requires the exact HTTPS remote. Credentials never enter config, environment, image layers, named state, or retained logs.

Detached startup allocates stdin and a TTY but disables engine logging. The operator explicitly attaches and enters `b` to mint a replacement one-time capability, then detaches without stopping the service. Startup waits for durable recovery before readiness; recovery failure stops both listeners and exits nonzero. The health check requires both the ready marker and an exact-Host reader response. Replacement revokes process-memory sessions while durable jobs survive according to the existing recovery classes. Ambiguous `applying` work still requires manual intervention.

**Acceptance passed.** Static structure, shell behavior, Compose expansion, both systemd examples, owner-alpha package tests, the two-browser local-bare-remote Save fixture, restart/replacement recovery, rootless runtime identity, numeric nonzero identity mechanics, image contents, offline Quartz materialization, exact mounts, bootstrap non-retention, and negative security cases passed. The final review used a real rootless Linux Docker Engine on native ext4-backed storage. An actual rootful-daemon run remains pending, although nonzero UID/GID, state ownership, marker mismatch, and replacement behavior passed inside the available user namespace.

**Evidence boundary.** The real 2026-08-02 Cyberbase Save used the bare-metal route, not the image. WP2 did not perform a physical-device Save, external-forge/live-site Save from the container, external-vault action, registry publication, service installation, Docker Desktop run, bridge publish, private-repository deployment observation, or public exposure. The image remains local-only. See [Owner-alpha container deployment](/cyberbaser/development/owner-alpha-container-deployment/) for the operator story and exact limits.

### WP3 — Forgejo migration (phase one complete; authority unchanged)

**Problem addressed.** GitHub was the only deployment-observation provider. The pipeline seam existed, but its default imported GitHub functions directly and configuration treated GitHub-only remote, Pages, workflow, environment, and ordered-job rules as universal.

**Implemented phase-one design.** Schema version 1 is now a strict provider-discriminated union. The GitHub branch is regression-pinned to the unchanged normalized policy JSON and revision. The Forgejo branch binds a canonical HTTPS remote, exact same-origin `/api/v1`, repository/owner/branch identity, `.forgejo/workflows/*.yml`, a job set, one terminal deployment job, and an independent owner-policy live URL. Self-hosted Forgejo may use one explicit non-default HTTPS port. A narrow dispatcher selects GitHub or Forgejo only from `workflow.provider` and rejects unsupported providers before fetch.

The Forgejo 16 adapter uses sequential read-only `GET` requests, one deadline, a 2 MiB streaming JSON ceiling, version preflight, exact one-run cardinality, candidate fixation, bounded `event_payload` parsing, and exact job ID/attempt/handle/dependency binding before durable `run-bound`. It uses Forgejo-native `commit_sha`, `workflow_id`, and terminal statuses; `needs: null` normalizes only to the explicit empty dependency set. Monitoring validates stored evidence before network access and never rediscovers or adopts a rerun. Publication evidence explicitly distinguishes the owner-policy destination from absent Forgejo environment attestation. The existing job graph, source application, Git publication, and live witness remain unchanged.

A separate disposable package implements the acceptance lifecycle around one unchanged authoritative bare repository, one private Forgejo fixture repository seeded once without mirror service, controlled PR checks using tracked shell-only workflows and copied Cyberbaser tools, one owner-alpha Save, explicit non-default loopback TLS endpoints, checksum-bound runner bytes, a 4 GiB combined storage ceiling, credential-file boundaries, and manifest-scoped cleanup. Private checkout uses Forgejo's automatic repository token through a temporary helper that disables ambient Git credential sources. Cleanup authorizes resource creation before Compose, reconciles interrupted double-labelled resources into the atomic manifest before removal, handles termination signals, and recovers stale locks only after the recorded owner is dead.

**Accepted runner boundary.** Adversarial review rejected the planned same-UID host runner because workflow code could read run-root credentials and reach ambient same-user container sockets. The replacement keeps the checksum-pinned runner daemon as trusted fixture infrastructure but executes every workflow job inside an unprivileged run-scoped container. Jobs join only the exact run network, receive only the read-only tools and writable publication handoff mounts, and receive no engine socket, host network, host PID, added capability, privileged mode, or unconfined seccomp. A dedicated `isolation-probe` fails if workflow code can observe host authority.

**Real-engine acceptance passed on 2026-08-10.** Forgejo 16.0.2 passed the isolation probe, `ofm-check`, `trust-gate`, controlled merge publication, one exact owner-alpha Save, fixed run/job binding, HTTPS live witness, unchanged authoritative seed, complete storage measurement, and exact manifest-bound cleanup. Peak combined temporary storage was 172,289,041 bytes against the 4 GiB ceiling. Cleanup stopped two exact processes, removed four exact Docker resources, skipped none, and left no labelled resources or run roots. See [Forgejo Actions phase one](/cyberbaser/development/forgejo-phase-1/).

**Later phasing remains unchanged:**
1. begin the WP4 shared proposal contract without moving production authority;
2. separately decide whether to run a persistent mirror/burn-in while edit links and PR authority remain elsewhere;
3. treat any authority cutover as its own explicit decision, including the render-hosting spoke.

**What this may buy later:** forge-delegated identity on an owner-controlled instance. Phase one proves only the deployment adapter and disposable hosted-Save path under a controlled local fixture. It does not select production identity, credentials, mirror, hosting, service installation, image publication, or authority.

### WP4 — Shared contract, local queue, and both adapter implementations complete; offered lanes pending

**Decision inherited (2026-08-02 direction):** support all lanes, each "super easy"; no maintainer-hosted relay. Two lanes, one contract.

**The shared contract is implemented.** Every intake lane must now produce the same canonical `@cyberbaser/proposal`: one pinned existing Markdown source, one fully prepared quote- or offset-bound splice via `@cyberbaser/correction`, caller-supplied submission metadata, evidence URLs, and an optional inert identity claim. The pure package validates canonical bytes, reapplies the exact candidate in memory, and converts a separately receiver-verified subject into the existing trust classifier input. It performs no queue, network, Git, identity verification, source write, or publication work. Lanes may differ only in transport and verified identity signal; they cannot fork the proposal shape. See [Proposal Contract](/cyberbaser/design/proposal-contract/).

- **Lane A, Forgejo-native (adapter implemented hermetically; offered lane unbuilt):** `@cyberbaser/forgejo-intake` reads one open pull request through four injected same-origin `GET` responses and exact inert Git objects, then emits the canonical proposal and a Forgejo-origin-plus-numeric-user-ID trust subject. It is tested against injected Forgejo metadata and real local Git only. No live Forgejo validation, installation, rendered edit link, contributor-usability result, merge/write action, or production authority exists.
- **Shared queue (implemented locally):** `@cyberbaser/proposal-queue` retains exact canonical proposal bytes plus bounded receipt, carrier, classification, and lifecycle artifacts in one private owner-controlled filesystem directory. It is carrier-neutral, finite, kernel-locked, crash-recoverable, and evidence-revalidating. V1 deliberately uses this local queue rather than bot pull requests. Its only states are `pending-review` and `expired`; it has no owner decision, accepted, rejected, merged, applied, or published state.
- **Lane B, account-free intake (implemented mechanically; offered lane unbuilt):** `@cyberbaser/account-free-intake` resolves an opaque retained publication binding and exact historical Git objects, then derives the canonical proposal at the anonymous trust floor. A separate optional Bun sibling service accepts strict credential-free intents and writes only the local queue. A Quartz form exists but is absent unless explicitly enabled at build time. The local-only OCI/Compose bundle runs the service separately from owner-alpha on an internal network, with read-only source evidence and one dedicated queue volume. No public reverse proxy, TLS endpoint, edge DDoS control, service installation, image publication, human result, source write, or production authority exists. See [Account-free intake Lane B](/cyberbaser/development/account-free-intake/).

**No-R-number implementation amendment (2026-08-10):** v1 selects the local filesystem queue and a sibling service, not an owner-alpha in-process endpoint. This keeps unauthenticated traffic and queue writes outside the owner-authority process. It implements the already ordered WP4 boundary without locking a permanent queue protocol, public exposure model, review product, or identity technology.

**Evidence boundary:** package, app, renderer-helper, queue, and deterministic deployment tests pass. Repository CI is read-only and is designed to build the local image and run the isolated container acceptance without publishing it. This is mechanical evidence only. The acceptance target of a real correction traversing each offered lane into one common queue has not happened: Lane A is not installed or live-validated, Lane B is not publicly deployed or human-tested, and neither lane is offered. Q09 closes only after the separately required product and human evidence; building these mechanics does not close it.

### WP5 — Owner review first; broader management later

**First slice implemented and mechanically accepted (2026-08-20): live queue review and durable decisions.** The first owner surface is narrower than a general management console. The running account-free intake process exposes bounded read-only `list` and `load` snapshots from its already-open queue over a private same-host Unix socket. Owner-alpha independently revalidates the exact proposal, branch-reachable source blob, candidate, policy, classification, queue binding, and expiry before presenting it. The owner may record one immutable, exactly-once **Approve** or **Reject** decision in the ignored owner-controlled local store. Both are decision-only and have zero source, Git, rebuild, deployment, publication, queue-lifecycle, or owner-job effects. The queue keeps no decision state and remains `pending-review` or `expired` only.

The real same-host acceptance retains the intake writer's lifetime lock, records one rejection and one approval intent through the privileged owner HTTP boundary, reconstructs both after owner restart, preserves history after one queue copy is purged, and accepts a later submission while source, Git, remote, queue evidence, deployment state, and owner job storage remain unchanged. The review surface may persist canonical decision evidence because it is the selected owner-local decision authority, but it never stores identity or browser-session credentials as durable authority. Anonymous Lane B evidence remains anonymous and full-review; the decision records separate `decisionAuthority` rather than replacing the contributor trust subject. Shared-socket OCI wiring, cross-container UID/group authorization, outward exposure, and approval-to-source application remain separate later work.

**Broader vision retained:** one owner place may later configure authentication integrations and network setup, edit policy files through the same exact-change boundary, show proposal and deployment status, and link to delegated systems rather than reimplementing them. That broader surface is not selected by momentum and does not expand this wave.

#### Required gate before the approved-proposal adapter

The first review implementation proved the same-host decision boundary mechanically, but two maintainer reviews rejected its product model. The next work is the coordinated [proposal operating model](/cyberbaser/research/proposal-operating-model/), not another CSS pass and not the application adapter in isolation.

The gate requires:

1. immutable submitted intent separated from exact change mechanics;
2. a versioned editorial taxonomy and declared scope treated as advisory claims;
3. a measured single-file multi-operation contract proposal that preserves version 1 bytes and digests;
4. realistic executable and conceptual fixtures with explicit evidence labels;
5. wide-screen side-by-side and mobile stacked comparison mockups with a persistent but deliberate decision affordance;
6. a clear same-host-now, shared-socket-OCI-later deployment model; and
7. one focused maintainer comprehension checkpoint.

Items 1 through 6 now exist as working research, typed fixtures, and a separate loopback-only static/no-effect surface. They do not constitute a selected v2 schema or real owner-review product implementation. Two adversarial reviews forced corrections to inbox truth, conceptual attention, operation semantics, complete atomic scope, above-the-fold evidence, mobile dismissal, keyboard focus, authority copy, lane representability, bidi display, system selection, launcher ownership, and test reliability. Item 7 remains pending and must be judged by the maintainer without coaching.

Only after that checkpoint does richer-contract selection and real owner-review implementation begin, followed by the approved-proposal adapter. Approval remains decision-only, and the later adapter still requires a separately selected owner application-authority event or durable policy.

### WP6 — Identity seam (kept explicitly open)

The [federated identity](/cyberbaser/research/federated-identity/) research page holds the imagination: forge OIDC, signed commits/keys, DID/VCs, ActivityPub actors, IndieAuth — all optional trust *signals* above the anonymous floor. The implemented proposal contract keeps the seam narrow: it may carry one inert `{ type, issuer, subject }` claim, but that claim never promotes itself into trust. A receiving lane must supply a separately verified subject to the unchanged classifier; absent verification stays anonymous. No technology is selected, and nothing outside a future verifier/classifier adapter may branch on identity kind.

## Cross-cutting deliverables every package owes

Amazing docs (operator story first, spec second), same-session `.claude/` alignment, honest status lines (built ≠ installed ≠ validated), tests at the package's own layer, no durable identity or browser-session authority, and no local decision artifact that silently acquires source-write or publication power.
