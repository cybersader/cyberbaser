**Status: design, 2026-11-23. Build steps 1 (Iroh in the node, agent pairing) and 2 (the Obsidian plugin) are built and tested on synthetic vaults; step 2 has not been tried on a real phone; step 4 (one program, Linux install with two accounts) is built and tested in disposable containers only; the rest is not built.** It answers the owner's decision that the first real install waits for Iroh reach and a one-app setup ([decision log](https://github.com/cybersader/cyberbaser/blob/main/.claude/41-QUESTIONS-RESOLVED.md)). Settled matters are linked, not repeated: the five layers and Iroh-via-n0-relay choice are in the [editing roadmap](/cyberbaser/design/editing-and-trust-roadmap/), the passkey-over-Iroh evidence is in the [Iroh carrier research](/cyberbaser/research/iroh-editor-carrier/), and the container identities are in the [container deployment guide](/cyberbaser/development/owner-alpha-container-deployment/).

## The recommendation

1. **Iroh lives inside the owner node.** n0's official JavaScript bindings (`@number0/iroh`) load under Bun and connected both directly and through n0's relay in a check on this machine, and they compile into a single executable. No Rust sidecar is needed for phones and agents.
2. **Pairing is a QR code that holds a five-minute, one-use enrollment secret.** The phone or agent proves it holds that secret and its own new key, both screens show the same short code, and the owner taps Confirm. The device then lands in the existing device-key registry with exactly the grants picked on screen. Revoke is one tap.
3. **GitHub access is given once, through a Cyberbaser GitHub App with device sign-in,** installed on one repository with only "Contents: write". The token lives only with the publisher. A pasted fine-grained token remains the fallback, and Forgejo uses the same slot.
4. **The app is one compiled program** that runs as a background service, opens its setup page in the browser, and starts its publisher half as a separate process under a separate account. A container image covers home servers. A tray icon comes later.

## What a regular person does

1. Download and open Cyberbaser on the machine that stays on (a desktop, a mini PC, a NAS).
2. **Sign in to GitHub:** the app shows an eight-character code; enter it on github.com and choose the one repository holding the vault.
3. **Pick the vault:** the app lists that repository's folders that look like vaults and its live site address; confirm.
4. **Pair a phone:** pick what this phone may do, scan the QR code with the phone camera, check the two short codes match, tap Confirm.
5. **Pair an agent:** same screen, kind "agent" (propose only), and paste the pairing line into the agent's setup or run `cyberbaser pair <code>`.

No port forwarding, domain, certificate, account on a Cyberbaser server, or password. The mockups are in `.workspace/deploy-design/setup-flow.html` (owner review copy, shown in the chat thread).

## 1. Giving the node an Iroh endpoint

| Option | State today | Verdict |
|---|---|---|
| **Official N-API bindings `@number0/iroh`** in the Bun process | v1.2.0, released 2026-10-22, from [n0-computer/iroh-ffi](https://github.com/n0-computer/iroh-ffi) (not archived; 1.0.0 in June, 1.1.0 in July). Prebuilt binaries for Linux x64/arm64 (glibc and musl), macOS arm64 only (no Intel), Windows x64/arm64, Android ([iroh JavaScript docs](https://docs.iroh.computer/languages/javascript)). The docs name Node 20.3+, not Bun. | **Recommended.** Checked here: under Bun 1.3.14 and Node 22, a loopback connection exchanged a stream with the authenticated peer ID; under Bun, a dial by endpoint ID plus n0 relay URL connected in about 350 ms and then upgraded to a direct path. `bun build --compile` embedded the addon: the 131 MB binary ran from an empty directory. |
| Small Rust sidecar on a local socket | Rust `iroh` is at 1.5.0 ([docs.rs](https://docs.rs/iroh/1.5.0/iroh/)); the spike already wraps 1.0.3. | Keep as the fallback. It adds a second binary, a second build toolchain per platform, and a local socket that must itself be authenticated. Worth it only if the bindings stall or a missing feature becomes required. |
| Rewrite the node in Rust | | No. The command core, publisher and tests are JavaScript and work. |

**One gap in the bindings:** the JavaScript `Connection` exposes the authenticated remote ID but not `export_keying_material` (checked in the 1.2.0 type definitions). The TLS exporter is what the [research fixture](/cyberbaser/research/iroh-editor-carrier/#c-authenticate-the-person-on-this-connection) used to bind a passkey to the connection. The design below does not need it, because a signed request is bound to the peer's authenticated endpoint ID plus a fresh node nonce. If the exporter is wanted later, it is a small upstream addition to iroh-ffi or the sidecar fallback.

**Endpoint settings.** Start from the minimal preset, set the relay explicitly to the configured n0 relay URL (`RelayMode.customFromUrls`), no discovery publishing, one stable node secret key stored owner-only in the node's state. The relay URL is configuration, as already decided; nothing silently falls back. Native clients may upgrade to a direct path (both peers then learn each other's address; they are the owner's own devices). Browser and Obsidian-mobile clients use the WASM build, which only ever goes through the relay ([Iroh WASM support](https://docs.iroh.computer/deployment/wasm-browser-support)).

**How the existing envelopes ride on it unchanged.** Two ALPNs: `cyberbaser/pair/1` (enrollment, below) and `cyberbaser/cmd/1`.

- On each new command connection the node sends a 32-byte random nonce on the first stream.
- The client sets `channelBinding = SHA-256("cyberbaser.iroh-binding.v1" ‖ nodeId ‖ clientEndpointId ‖ nonce)` in the [signed request](https://github.com/cybersader/cyberbaser/blob/main/apps/owner-alpha/src/core/signed-request.js) it already builds. The audience becomes `cyberbaser.owner.iroh.v1:<nodeId>`.
- The node computes the same value from `connection.remoteId()` (authenticated by Iroh's TLS, never read from JSON) and calls the existing `verifier.forChannel(binding)` with `requireChannelBinding: true`. Replay window, nonce cache, revocation and expiry checks are the same code.
- One bidirectional stream per request, canonical JSON, the same 512 KiB cap, five-second read deadline and command allowlist as the [local signed socket](https://github.com/cybersader/cyberbaser/blob/main/apps/owner-alpha/src/signed-request-socket.js). A conformance test runs the same traces over the Unix socket and Iroh and compares outcomes.

A replayed envelope fails on another connection because the nonce differs, and on another endpoint because the peer ID differs. The device signing key and the Iroh endpoint key stay separate keys: the endpoint key may be per-session; the device key is the enrolled identity.

**Phone and browser side.** The Obsidian plugin (and any browser client) bundles the Iroh WASM build from the spike and talks only through the relay. Obsidian plugins can register an `obsidian://` handler ([`registerObsidianProtocolHandler`](https://docs.obsidian.md/Reference/TypeScript+API/Plugin/registerObsidianProtocolHandler)), so a QR code scanned by the phone camera can open Obsidian straight into pairing. Per the roadmap's [workspace findings](/cyberbaser/design/editing-and-trust-roadmap/#publish-from-where-you-write), the device key must not live in synced plugin settings; keep it in per-device app storage and treat this custody as the item to test on a real phone.

## 2. Pairing by QR

Built on the existing [device-key registry](https://github.com/cybersader/cyberbaser/blob/main/apps/owner-alpha/src/core/device-keys.js) (Ed25519 keys, actor kind `owner-device` or `agent`, grants from `read, save, review, apply, publication, publish, propose`, agents limited to `propose`, `notBefore`/`notAfter`, `revoked`).

**Owner starts it.** On the node's setup page (or an already paired owner phone holding `review`), the owner picks the kind, a name and the grants. The node creates an enrollment record `{enrollmentId, secretHash, kind, label, grants, expiresAt = now + 5 min, used: false}`.

**The QR contains** `cb1:<nodeId>:<relayUrl>:<enrollmentId>:<secret>` (32-byte secret, base32), wrapped as `obsidian://cyberbaser-pair?c=…` for phones. Nothing in it is a password or account; the node ID is not secret but should not be published.

**The device enrolls.**
1. It creates its device key (Ed25519) and a fresh Iroh endpoint key, and dials the node ID through the given relay with ALPN `cyberbaser/pair/1`.
2. It sends `{enrollmentId, devicePublicKey, label, mac, signature}` where `mac = HMAC(secret, transcript)` and `signature` is the device key over the same transcript. The transcript includes the node ID, the authenticated client endpoint ID, the enrollment ID and the device public key. The secret itself never crosses the wire.
3. The node marks the enrollment used on the first attempt, valid or not, checks the MAC and signature, and derives a short comparison code (four words) from the transcript hash. Both screens show it.
4. The owner taps **Confirm** on the node's screen. Only then does the registry gain `{keyId, publicKey, actor, grants: exactly those picked, notBefore: now, notAfter: now + 1 year, revoked: false}`. The device receives its key ID and starts using `cyberbaser/cmd/1`.

**Revocation.** The devices list shows each key's name, kind, grants and last use. Revoke sets `revoked: true`, persists it, reloads the registry and closes that key's open connections; the verifier already refuses revoked keys on every request. Rotating the node key invalidates every pairing (re-pair). Lost phone: revoke that one key; keys are per device, never synced.

**Someone photographs the QR.** For at most five minutes, and only until the real device uses it, they can attempt a pairing. They cannot finish without the owner's Confirm, and a mismatched or unexpected comparison code tells the owner to cancel. After use or expiry the photo is worthless. The node ID and relay it reveals let them try to connect, which the node refuses; the relay operator already sees connection metadata, as decided.

**Code change this needs:** the registry is built once from config today. It needs a small persisted store the node can append to and revoke from, with an atomic write and reload. The verification path stays as is.

## 3. GitHub access, once

| Option | Steps for a non-developer | Scope | Expiry, revocation | Fit |
|---|---|---|---|---|
| **Cyberbaser GitHub App, device sign-in** | Enter a code on github.com, install the app on one repository | Contents: write (plus the mandatory metadata read); user token limited to repos where the app is installed *and* the user has access ([GitHub](https://docs.github.com/en/apps/creating-github-apps/authenticating-with-a-github-app/generating-a-user-access-token-for-a-github-app)) | 8-hour token, 6-month refresh token, refreshed by the publisher; revoke by uninstalling or revoking in GitHub settings | **Recommended.** No copy-paste of secrets; device flow needs no client secret, so no Cyberbaser server. Without the Workflows permission the token should not be able to change `.github/workflows` (to test). |
| Fine-grained personal access token | Open a pre-filled GitHub link, pick the repo, copy, paste | One repo, Contents read/write ([GitHub](https://docs.github.com/en/authentication/keeping-your-account-and-data-secure/managing-your-personal-access-tokens)) | Default 30 days, up to 366 or none; delete in settings | **Fallback**, and the model for Forgejo tokens. |
| Deploy key | Create SSH key, paste it in repo settings, tick write | One repo | Never expires | No: more steps, SSH handling, no expiry. |
| Self-registered app (manifest flow) | Create a private app per user | One repo | Long-lived app private key | No: more steps, a private key to guard. |

**Where it lives.** Only the publisher process stores the refresh token, owner-only in publisher state, and hands Git a short-lived token through its existing credential helper. The web-facing node never sees it. Behind a vendor-neutral `ForgeAccess` provider interface (`github-app`, `token`, later `forgejo`) with a conformance test: can push to the one repo, cannot read another, refresh works, revocation is noticed. This follows the project's [protocol-driven controls](/cyberbaser/getting-started/principles/) preference.

**Cost of the recommended option:** the project registers and keeps one public GitHub App. If the registration disappeared, users would switch to the token path; no user data sits with the app.

**First run** is the five steps above, served on loopback (`127.0.0.1`) with a one-time setup token opened automatically, which is how the [bootstrap console](https://github.com/cybersader/cyberbaser/blob/main/apps/owner-alpha/src/bootstrap-console.js) already works. On a NAS the setup link comes from the container log.

### First-run setup, as built (2026-11-23)

A short guided flow in the owner app, shown only until setup is finished. It opens from a one-time link the app prints when it starts (`127.0.0.1` only, works once, for 15 minutes; a restart prints a new one). After setup, the normal owner sign-in applies.

1. **Welcome:** one sentence on what Cyberbaser does, and Start.
2. **Connect GitHub:** the same sign-in code and searchable repository list as the Publishing to GitHub page. During setup the publisher can sign in, list and pick a repository, but it cannot push.
3. **Your notes:** the node makes its private copy of the repository, shows a calm progress line, then how many notes it copied. If the repository has no `publish.yml`, it says nothing will be published without one and offers **Publish nothing yet** or **Write a starter file**, where the owner picks the public folders (none are picked for them). A starter file stays on this machine until the owner publishes it. If this machine cannot build the private preview, it says so and continues.
4. **Your website:** found from the repository's own Pages workflow or `CNAME` file when they exist; otherwise one address field and **Skip for now**.
5. **Pair your phone:** the Devices pairing with QR code and matching words, or **Pair later**.
6. **Pair an agent:** optional; shows the one-line `cyberbaser pair` command, or **Skip**.
7. **Done:** "Changes your agents and visitors suggest will appear in Proposals", with links to Proposals and Devices.

Each step is saved to an owner-only file, so a restart resumes at the same step. Every action needs the setup session and its CSRF token and names the step on screen, so a stale click does nothing. Nothing is published during setup. An installer that starts the node in the same process can hand over the setup session, so the owner is still signed in at Done.

**Not yet:** copying a private repository needs the publisher to fetch it (today the node clones without credentials, so only public repositories, or the test fake, copy). Adding a confirmed starter `publish.yml` to the repository is not wired. A custom website address is recorded, but live checks still use the GitHub Pages address. Pairing during setup has not run against a real Iroh endpoint.

**Cross-builds.** Bun cross-compiles with `--target` and can embed `.node` addons, but each target needs that platform's addon package installed ([Bun executables](https://bun.com/docs/compiler/executables)), so build per platform in CI. No macOS Intel binding exists.

### One program and the Linux install, as built (2026-11-23)

**What a Linux user runs:** download one file and run `cyberbaser install --quartz-seed quartz-seed-v4.5.2.tar.zst`. It asks for the admin password once (pkexec on a desktop, sudo in a terminal, and says which), installs a background service, and prints one line: the local setup address with its one-time token. `cyberbaser status` shows what runs; `cyberbaser uninstall` removes the program and services and keeps the notes and keys unless `--purge`. Running install again updates in place; it refuses to touch a setup it did not make.

**The program.** `packaging/build.js` compiles one 130 MB Linux x64 executable with `bun build --compile`. The Iroh addon is inside it: pairing loads it from an empty folder with no network. It starts in about 0.1 s. Its modes wrap the existing entry points unchanged: `node`, `publisher`, `intake` (the node starts it through the same program), `pair`, `install`, `uninstall`, `status`. Each refuses root, and on an installed machine refuses any account but its own. The web pages, renderer files and the sources the site-identity check hashes (2.7 MB) are embedded and written to `/opt/cyberbaser` at install.

**The site builder.** The pinned Quartz runs on the program's own runtime: `node` and `bun` in the install are two-line scripts that start the same program as Bun. No Node.js is needed. With no network at all, a private build of a small vault took 1.1 s under Bun against 1.5 s under Node 22; the pages differ only in whitespace inside serialized functions and a source-map path. Quartz and its locked dependencies (465 MB installed) ship as one archive, 107 MB with zstd, whose SHA-256 the program pins; install checks the digest, unpacks it, and the renderer's own setup checks origin, tag, commit and lockfile again.

**Two accounts.** `cyberbaser` runs the node and the intake; `cyberbaser-publisher` runs the publisher; both have the group `cyberbaser-share` as their primary group.

| Place | Owner, mode | Who can read it |
|---|---|---|
| `/var/lib/cyberbaser` (config, Iroh keys, setup state) | `cyberbaser`, 0700 | the node only |
| `/var/lib/cyberbaser-publisher` (forge key, push repository, its copy of the config) | `cyberbaser-publisher`, 0700 | the publisher only |
| `/var/lib/cyberbaser-shared/workspace` (job store, seen at `/opt/cyberbaser/.workspace`) | node, group share, 0770; job records 0640 | both; the publisher adds its push receipt |
| `/var/lib/cyberbaser-shared/notes` (the notes copy) | node, group share, 0770 | both; the publisher reads commits |
| `/run/cyberbaser-publisher` (publisher sockets) | publisher, group share, 0710; sockets 0660 | the node may connect, not list or write |

The units use `ProtectSystem=strict`, `NoNewPrivileges`, `PrivateTmp`, `ProtectHome`, `ProtectProc=invisible`, no capabilities, and only the paths above as writable; each unit cannot see the other's private folder at all. Before the publisher starts, root copies the node's config into the publisher's own 0600 file (refusing links and any file not the node's own), and a path unit restarts the publisher when that config changes.

**Two small code changes made this possible, both off unless the installed service turns them on.** The publisher was written as a separate process under the same user: its sockets accepted only its own account, and the job store was owner-only. Now the publisher takes a socket group (`--socket-group`: directory 0710, sockets 0660), and `CYBERBASER_SHARED_STORE=group` makes only the job records under `jobs/` group-shared (directories 0770, files 0640; the store root 0710). Everything else in the store stays owner-only; the node's other checks require that.

**Evidence** (`packaging/test/container/run.sh`, a disposable Fedora 44 container running systemd under rootless Podman, 61 checks, all pass): install in about 2 s and the setup link printed; the node cannot list the publisher's folder, read a stand-in forge key or the publisher's config, read the publisher's environment or memory maps, or list or write the socket folder, but can connect to the socket; an unrelated user cannot connect or read the shared store; the publisher cannot read the node's keys or config; inside the running node service the publisher folder is an empty locked stub and the program files are read-only even for root. One synthetic job ran end to end across accounts: the node applied and committed, the publisher pushed that exact commit to a local bare repository, and its receipt was group-readable only. Uninstall kept data, reinstall and update reused the same accounts, and install refused an unknown `/opt/cyberbaser` and an unknown `cyberbaser-publisher` account. `systemd-analyze security` rates both units 2.9 ("OK"). A separate test runs the program with no network in a private namespace: the node built its private site, started the intake and Iroh, and answered its health check in 3.5 to 5.5 s.

**Home server.** `deploy/owner-alpha/one-app/` builds a local image from the same program (1.07 GB: Fedora base, program, renderer bundle) with the same layout as two containers: node as uid 65532 and publisher as 65533, sharing group 65530; only the publisher container mounts the publisher volume. Checked: the node container prints the setup link, refuses to run as the publisher, and cannot list the publisher volume. Not yet run end to end with a push; the earlier image and its guide are unchanged.

**What still does not hold up.**
- The node's startup asks the forge for the branch head (`git ls-remote`), so it cannot start with no network, and the tests stand a local repository in for GitHub.
- First-run setup needs the publisher for GitHub sign-in, but the publisher only starts once a config exists. Setup also keeps its state owner-only and clones the notes inside it, where the publisher cannot read them; the install writes `checkout: /var/lib/cyberbaser-shared/notes/notes` into the setup layout for setup to use.
- A compromised node still owns the job store, so it can ask the publisher to push any commit to the one repository. What the split protects is the key itself: the node can never read or copy it, and revoking it is immediate.
- The renderer bundle is a separate 107 MB download; the program does not fetch it yet.

### Other platforms (evaluation, 2026-11-23)

**Cross-compiling, checked here.** `bun build --compile --target` produced a Windows x64 `.exe`, a macOS arm64 executable and a Linux arm64 executable from this machine in about 1.5 s each. n0 publishes the Iroh addon for win32-x64, win32-arm64 and darwin-arm64 (version 1.2.0; darwin-x64 does not exist, npm returns 404). With the target's addon package unpacked beside the others, the builds embed it (Windows 120 MB, macOS 77 MB); without it they build but carry no Iroh. None of these was run: there is no Windows or Mac here. Running is not enough anyway: the publisher's repository import refuses any platform but Linux (it reads objects through `/proc/self/fd`), and the node and publisher call `flock`, which Windows lacks. Those two need a port before Windows works; macOS has neither `/proc` nor `flock(1)` by default either.

|---|---|---|---|---|

| Tauri 2 | Yes: a webview showing the local page | `.msi`/NSIS `.exe`, `.dmg`/`.app`, `.deb`/`.rpm`/AppImage from one config; ships our program as a sidecar | Rust toolchain and signing per platform; the webview differs by OS | **Later**, as the tray and installer wrapper around the same program. |

The Tauri row is from its documentation, not built here.

**The publisher's own account on each OS** (design, not built).
- **Windows:** two Windows services, each under its own virtual service account (`NT SERVICE\CyberbaserNode`, `NT SERVICE\CyberbaserPublisher`). The publisher's folder under `ProgramData` gets an ACL for the publisher service only; the socket becomes a named pipe whose ACL admits only the node service. Admin once: the MSI asks through UAC. Not equivalent: administrators can still take ownership of anything, and the code's Unix checks (owner, mode bits, `flock`, `/proc`) need Windows versions.
- **macOS:** two launchd daemons in `/Library/LaunchDaemons` with `UserName` set to two hidden role accounts the installer creates, state under `/Library/Application Support/Cyberbaser` with the same modes; Unix sockets work as on Linux. Admin once: the `.pkg` installer's password prompt. The Keychain is not a better home for the key: the publisher daemon has no login keychain, and the System keychain is shared with root processes. Same strength as Linux except `/proc`-based code, which needs a macOS path.
- **Without admin rights** on any OS: two processes under one user, not credential isolation, and labelled so.

**Sockets on Windows.** Today: Unix sockets with owner and mode checks, `chmod`/`chown`, a `flock` ownership lock, and `lstat` inode fingerprints. On Windows: named pipes (`\\.\pipe\…`, which Bun's `net` supports) with an ACL instead of modes, a lock file opened exclusively instead of `flock`, and no inode fingerprint. These checks should sit behind one small socket interface per platform; Linux keeps today's code.

## 5. What is genuinely hard or risky

- **The private-site renderer is not a single file.** Review renders the vault with the pinned Quartz toolchain (Node packages and an esbuild binary). The binary must either download a pinned, digest-checked renderer bundle on first run or ship beside it. This is the largest packaging item.
- **External programs.** The node calls `git` and `flock`. Linux has both; macOS needs Git (Xcode tools prompt); Windows has no `flock`. Linux first, macOS next, Windows after a port.
- **Isolation on desktops** needs an admin install. A no-admin install is weaker and must say so.
- **Phone key custody and background limits** in Obsidian mobile are untested. A phone app that is closed cannot hold a connection; every command must be a single request with a receipt to look up later, which the command core already supports.
- **n0's public relay** is development infrastructure with no uptime promise (accepted); the relay URL must stay one setting.
- **The bindings are young** (1.x since June 2026) and not documented for Bun. Pin the version, keep the loopback and relay checks as tests, keep the sidecar as the fallback.
- **The GitHub App** is a registration the project must maintain, and its exact refusal of workflow-file pushes needs a real test.

## Build order

1. **Iroh carrier in the node, agent on this machine.** `@number0/iroh` pinned, `cyberbaser/cmd/1` with the nonce binding, the persisted device store, `cyberbaser/pair/1` with the QR screen and Confirm, and a `cyberbaser pair` command for an agent. Test: an agent on this machine pairs by code, submits a proposal over Iroh through the n0 relay, and is refused after revoke. Same conformance traces as the Unix socket. Synthetic vault only. Roughly a few focused days.

   **Built (2026-11-23).** Off unless the config's `iroh` section enables it. `@number0/iroh` 1.2.0 pinned; `cyberbaser/cmd/1` accepts only signed proposal submission, bound to the authenticated client endpoint plus a one-use node challenge; paired keys name their Iroh endpoint; enrolments and revocations are private create-once files that take effect at once; a Devices and agents page in the owner app starts pairing, shows the four words and Confirm, and revokes; `bin/cyberbaser-pair.js` pairs an agent and `agent-propose.js ... iroh` submits. A loopback test runs pair, submit, revoke, refuse with the real CLI; an opt-in test did the same once through n0's public relay (about 1.4 s to words, 0.6 s per submission). **Limits:** the code is shown as text, not a QR image (a QR encoder would add a dependency); each agent keeps one stable Iroh endpoint key named in its record, not a per-session one; proposal rate limits are counted per carrier; the Unix socket and Iroh share behaviour through matching tests, not one shared trace file; nothing ran against the real vault.
2. **Phone.** Thin Obsidian plugin with the WASM build: scan, confirm, status, propose or publish within its grants. Test on the owner's real phone.

   **Built (2026-11-23), tested in a disposable browser only.** `apps/obsidian-cyberbaser` is a plain JavaScript Obsidian plugin with Iroh compiled to WebAssembly from the `iroh` 1.2.0 crate (n0 publishes no ready-made browser package). The WASM is 2.6 MB (0.95 MB gzipped) and is embedded in the 3.5 MB `main.js`, loaded only when the plugin first connects. It ran inside Obsidian 1.12.7's own page and content security policy in the OpenClast harness.
   - **Pair:** a command, a settings button and an `obsidian://cyberbaser-pair?code=…` link (so a QR code can open it later). The owner pastes the code from the Devices page; the plugin shows the four words; the owner confirms on the node. The signing key is a non-extractable WebCrypto key and the Iroh secret is 32 random bytes, both kept in the app's own IndexedDB on that device, one record per vault. Nothing goes into `data.json`, which lives in the vault and syncs. Unpair deletes the record (revoke on the node as well).

## Decisions for the owner

1. **GitHub access:** a Cyberbaser GitHub App with device sign-in (recommended: nothing to copy, short-lived tokens, but the project maintains one app registration) or a pasted fine-grained token (no registration, but copy-paste and expiry within a year).
2. **Install on a desktop:** a system service that asks for the admin password once and keeps the publishing key under a separate account (recommended) or a no-admin app with weaker, labelled isolation.
3. **Pairing confirmation:** every pairing needs the matching short code and a Confirm tap (recommended; stops a photographed QR) or agents limited to proposing may pair from the QR alone.
4. **Platforms first:** Linux desktop and home-server container first, then macOS, Windows later (recommended) or all three before the first install.

## Decisions taken (2026-11-23)

The owner chose: the Cyberbaser GitHub App for publishing access; a background service installed with the admin password once, with the publisher under its own account; matching words plus a Confirm tap for every pairing; Linux desktop and a home-server container first. On the setup screens they asked for a searchable, polished repository picker: the mocked checkboxes "look really crappy", while the approach itself is right. See `.claude/41-QUESTIONS-RESOLVED.md`.
