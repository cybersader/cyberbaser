**Status: adopted in principle, 2026-11-21 (R25). Mostly not built.** It began as a finding from the first live workspace rehearsal: an edit that changed one property was refused, and tools in a writing workspace change properties constantly. A first draft proposed a fixed table of property names. An independent review kept the idea and rejected the table, and the owner adopted the reviewed shape below.

## Where properties sit

The same block of properties means something different at each stage, and a different component owns that meaning.

| Stage | What properties are there | Who owns the meaning | Must never happen |
|---|---|---|---|
| Authoring tools | The writer's fields, plus tool bookkeeping | The owner and their tools | Cyberbaser requiring or adding fields |
| Source of truth | Plain bytes in the note | The owner | Rewriting or reformatting the block |
| Publication selection | A signal that a note may be public | The selector and the vault's publication settings | A grant arriving inside an edit or proposal |
| Projection | Checked for readability and path safety, copied unchanged | Projection | Changing source bytes |
| Renderer | Address, redirects, tag pages, drafts, dates, title | The renderer adapter, which is replaceable | Its key names becoming core rules |
| Public site | Pages and addresses people rely on | The emitted site (R23) | A published address vanishing |
| Proposal, review, application | Exact bytes against pinned source; old and new values shown | The proposer has no authority; the owner decides | Carrying a public-set or address change; auto-apply |

## The model

**Simplified on 2026-11-21 at the owner's direction: first principles, no more machinery than the guarantees need.** Plugins and tools write properties constantly and unpredictably, so any scheme that depends on knowing what each key means will be wrong for the next plugin. The rule therefore knows no key names and asks nobody to declare any.

Only two things about a property can hurt, and both are already computed for every change, body or properties alike:

1. **Does it change what is public?** Publication selection is run before and after and the public set compared, assets included.
2. **Does it change or remove an address?** The address map is compared the same way.

Either one is refused as part of an edit. It needs the owner's own separate decision, with a preview. No tier, tool or agent can carry it.

**Everything else in the properties block is just text in the note.** A property edit that passes both checks is an ordinary exact change, reviewed like a change to the body. It does not matter which key changed or which plugin changed it.

One structural condition keeps the two checks trustworthy: the block must be there, closed and readable both before and after. A block that is added, removed, duplicated, left unclosed or made unparseable is refused with a readable reason.

## Rules

- **Parse to judge, never to write.** The change applied to the vault is still an exact byte operation. Cyberbaser never re-serializes the block and never authors a field. When the owner makes a note public, the change is the owner's own exact edit.
- **One finder, everywhere.** A single shared routine decides where the block is, used by selection, projection, trust classification, review and every guard.
- **The two checks cannot be turned off or lightened** by any policy, tier or grant.
- **Fail closed.** If before or after cannot be read, or the checks cannot be run, the change is refused.
- **Scope.** This governs changes that pass through Cyberbaser. The owner editing the vault directly with their own editor and Git is outside it, as always.

## When nothing visible changes

A save normally counts as live once the new text is seen on the public page. Some property edits change nothing a reader can see. For an edit that lies entirely inside the properties block and renders identically before and after, live means: the deployment for that exact commit succeeded, and the page still shows a witness recorded before the change. It is reported as **"Published, nothing visible changed"**, a distinct kind of evidence, never as a text confirmation. A visible change can never use it, and a body edit with no visible change is still refused.

## What was dropped, and why

An earlier version had renderer adapters declare the keys they use, a separate "unclaimed property" class held for full review, a vault policy mapping keys to effects, and a conformance test tying it together. None of it protected anything the two checks do not already protect. It would have held up every plugin-written key until someone classified it. The existing trust classifier's allowlist for agent-written keys is untouched and remains the one place a vault can ask for stricter review of property edits from others.

## Build order

1. The single shared finder. *(Built 2026-11-21; not yet checked against the real vault.)*
2. Address-map comparison beside the selected-set comparison. *(Built 2026-11-21.)*
3. Let a property edit through on the owner's own paths when the block stays intact and both checks pass. Off unless the owner turns it on. Proposals from others keep today's refusal until the owner has used this. *(Built 2026-11-21 as `owner.allowProperties`; synthetic tests only.)*
4. Review display that shows the old and new property text plainly.
