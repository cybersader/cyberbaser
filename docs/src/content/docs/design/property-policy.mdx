**Status: proposal, 2026-11-21. Nothing here is decided or built.** It answers a finding from the first live workspace rehearsal: an edit that changed one property was refused, and tools in a writing workspace change properties constantly. The owner asked for a principled structure, not a thin special case.

## What exists today

A code survey found the treatment is ad hoc. Five places give properties meaning, each with its own way of finding the block and reading it:

| Where | What it does with properties |
|---|---|
| Publication selection | Parses values. `cb-publish` is the only key that can grant publication; `slug` sets the address. |
| Renderer | Parses values for dates, drafts and the page address. |
| Trust classifier | Parses values. For agents only, any changed key outside an allowlist forces full review. |
| Owner write paths | Does not parse. Refuses any edit that touches the block's bytes at all. |
| Review display | Reads flat `key: value` lines only. |

Two consequences. The blanket byte refusal is the *only* thing stopping an edit from flipping a note public or changing its address, which is the right outcome reached by accident. And the same refusal blocks every harmless change, such as a tag, on every owner path.

## The proposal: classify a property change by what it does

One shared module finds the block and parses it, used by every path. A change is described as the set of top-level keys whose **parsed value** changed, and each key belongs to an effect class. The strictest class present decides what the change needs.

| Class | Keys (built-in defaults) | What a change needs |
|---|---|---|
| **Authority**: changes what is public | `cb-publish`, `publish`, `draft` | Never part of an edit or proposal. Only a separate owner selection decision, with a preview of what becomes public. No tier, tool or agent can carry it. |
| **Route**: changes the address or how the note is found | `slug`, `permalink`, `aliases` | Owner only, as its own reviewed step showing old and new address and the redirect that results. |
| **Descriptive**: says something about the note | `title`, `tags`, date keys | An ordinary exact change, shown in review. Eligible for lighter review by tier where the owner's policy says so. |
| **Unknown**: any key with no declared class | everything else, including tool bookkeeping | Full owner review by default. The owner may declare a key descriptive; nothing becomes lighter by default. |
| **Structural** | block added or removed, duplicate key, second block, unparseable YAML | Refused with a readable reason. |

Bytes that change without changing any parsed value (spacing, quoting, key order, comments) count as a descriptive change.

## Rules that keep this principled

- **Parse to classify, never to write.** Classification reads values. The change applied to the vault is still an exact byte operation, and Cyberbaser never re-serializes YAML or writes a field of its own into a note. Both existing principles hold.
- **One reading, everywhere.** The same module and the same class table serve owner Save, workspace publication, visitor suggestions, forge intake, trust classification and review display. A class cannot mean different things on different paths.
- **Authority and route keys cannot be demoted.** The owner's policy can move unknown keys into descriptive, and can make descriptive keys stricter. It cannot make a public-set or address change lighter.
- **Declared in the vault, part of the policy revision.** The existing `frontmatterAllowlist` in the vault's trust settings becomes a `properties` map by class, so the rule is visible, versioned and changes the pinned policy when it changes.
- **Fail closed.** If the before or after block cannot be parsed, or two readings would disagree about where it ends, the change is structural and refused.

## What it means per actor

| Actor | Descriptive | Unknown | Route | Authority |
|---|---|---|---|---|
| Owner, from the writing tool or the site | Publishes after review | Publishes after review | Separate reviewed step | Separate selection decision |
| Agent | May propose | May propose; full review | May not propose | May not propose |
| Visitor, account, trusted contributor | May propose; review by tier | May propose; full review | May not propose | May not propose |

## Evidence to gather before building

1. Which keys exist in the real vault and how often each changes, as counts only.
2. Which keys the workspace's own tools and plugins write without the person asking, since those would otherwise flood review as unknown.
3. Whether any real note relies on duplicate keys or YAML the parser rejects.

## The decision this needs

Whether to adopt effect classes as the one model for property changes. If yes, the first build is the shared module and the class table behind the existing refusal, changing behavior only for descriptive keys on the owner's own paths.
