## Independent foundations and optional integration

**Owner constraint (2026-10-07):** neither architecture should overscope its vision. Cyberbaser is not tied to one particular host; the host must not acquire Cyberbaser/Cyberbase-specific internal product logic. Independent foundations should interface well. This reinforces existing independently replaceable spokes, not a new universal framework.

The planned host tools, policy, bound hash-only handles, audit, transport and context enforce a **generic host snapshot capability**. Its capability records describe host identity, grant, room, expiry and capture only, with no publication, Quartz, proposal or content-layout semantics. Publication selection and proposal meaning remain Cyberbaser concerns. Frozen r3 descriptor/pages/chunks semantics are unchanged. The host must have **no reverse runtime dependency on Cyberbaser**; a test-only interoperability harness is distinct from runtime dependency.

Removal/substitution acceptance targets are:

1. The host remains useful without Cyberbaser.
2. Another client can use unchanged host APIs without a host special case.
3. Swapping the host does not reshape Cyberbaser's publication/proposal domain.

These are **acceptance targets, not demonstrated code properties**. Another-client acceptance is unproven, and this documentation wave performs no code-level architectural audit. The verifier being pure does not prove architectural independence.

Future-facing means independent evolution through bounded versioned contracts and minimal changes. It does not authorize speculative providers, framework extraction or automatic package renaming/refactoring. See the [dated clarification](/cyberbaser/agent-context/zz-log/2026-10-07-snapshot-product-independence/).

## Recommended ownership

### Host owns producer implementation

The reviewed contract requires one coherent synchronous in-memory CRDT capture, not per-entry disk reads. Readiness requires initial synchronization on the current connection and no pending CRDT updates; unsupported formats fail closed. The producer must verify referenced blob bytes and retain immutable verified copies **outside the canonical vault, in subject-private state**. This replaces the earlier shared-folder pinning/garbage-collection proposal.

Filter scope **before** counts, hashes, or completeness reporting; disclose no outside-grant names/metadata. The canonical line manifest and capture identity use SHA-256. Capture identity binds issuer, tenant, room, scope, capture, time, manifest, entry count, exclusion counts, and status. Text is UTF-8 with BOM and newline bytes preserved as stored; attachment digests use SHA-256 or BLAKE3. Neither representation proves original desktop-byte fidelity. Declared exclusions differ from failed eligible rows; a complete result requires every row to be successful.

Current grant, scope and revocation checks belong to the host at capture and on every manifest-page or blob-chunk request. Retrieval is bound to snapshot handle and path, never bare digest. Grant identity is host-local context, not a wire binding that the consumer can remotely verify. Handles and hashes are identity, not authorization; export permission must remain separate from ordinary note reads.

The owner approved the recommended private-copy implementation policies on 2026-10-07:

| Policy | Approved implementation boundary |
| --- | --- |
| Capture/store budgets | 16 GiB of blobs per capture; 32 GiB per daemon capture store; approximately 25% of the state filesystem as a hostwide cap. |
| Member removal | Revoke access immediately. If a daemon is stopped or unreachable, physical cleanup is durably queued and must complete before future serving. |
| Retention | Default one hour for complete captures and 15 minutes for incomplete captures; caller requests at most 24 hours; operator maximum seven days. |

Existing r3 floor/reservation and other unchanged requirements remain design obligations, not newly invented owner choices. Approval does **not** activate or change live settings.

The first-slice repair re-review resolved the original blob-ancestor race, durability-failure cleanup gap and decoded-trash classification findings, with no confirmed residual repair defect in its bounded scope. The coordinating session read the same independent reviewer's full report; host repair-test evidence was not rerun here. Linux `/proc/self/fd` is deliberately required and fails closed when unavailable; no cross-platform claim follows. That review permitted daemon-only slice two. Its later repair/test receipts now reconcile, but authenticated context and durable erasure/subject-store integration remain absent from production; it stays NON-SERVING pending the unchanged review and authority gates.

The independently verified artifact-r2 has separate repaired source/provenance even though eight A/B descriptor, serialized-input, manifest and identity files are byte-identical to r1. Its authoritative preserved source snapshot, not a potentially advancing working tree, binds this result. Preserve all initial r1 artifact/source/harness/receipt evidence. The six-slice plan and all **27 producer acceptance cases**, routes/authority/audit, host reservations/budgets, queued erasure, lifecycle, read-only binding, capacity and live gates remain deferred. Separate live-deployment preflight remains paused, not a prerequisite; no deployment or live acceptance follows. An ordered change feed remains deferred.

### Pure consumer foundation in the optional host integration

**Intended domain boundary (owner clarification, 2026-10-07):** the host-prefixed r3 protocol and its verifier belong in an **optional host-specific integration adapter**, not the generic Cyberbaser publication/proposal domain. The existing `@cyberbaser/snapshot-verifier` package name, API and prior evidence remain unchanged. This records intended architectural placement, not a performed package move, rename or code-level independence audit.

The authorized slice is a synchronous, pure in-memory verifier of supplied untrusted snapshot artifacts against independently supplied expected source and scope, with optional pinned digests, caller-owned budgets and time. It validates supported format, canonical manifest and identity, paths, lengths, digests, counts, expiry, and supplied page/chunk observations. Paths require canonical base64url, valid UTF-8, a 4,096-byte bound and exact byte ordering. Pages/chunks must be contiguous, terminate explicitly and keep identity constant.

BLAKE3 attachments require an explicitly trusted injected provider; without it verification fails closed. No installation, download or hand-written cryptography is authorized. Collision statuses are producer verdicts because Unicode versions can differ; consumer hashing cannot prove producer collision logic, completeness, capture coherence, authentication or current authorization.

`@cyberbaser/snapshot-verifier` exposes `verifySnapshot({ input, expected, limits, now, hashes })`. It accepts serialized descriptor and page/chunk observations, reconstructs manifest/identity/status and enforces local limits; an optional raw manifest must corroborate the reconstructed bytes exactly. Accepted evidence is frozen; retained validated bytes remain private, with fresh copies available through `readBytes(path)` and no usable partial success. Package/API reference: `packages/snapshot-verifier/README.md`, with public exports in `packages/snapshot-verifier/src/index.js`. These repository paths do not imply a merged or published package.

Independent final runs reported 186 passed, five explicit optional-provider skips and zero failures by default; with an explicitly selected vetted BLAKE3 test adapter, 191 passed with no skips or failures. A focused 12-test regression suite passed across Bun and Node after the async-provider repair. The [dated log](/cyberbaser/agent-context/zz-log/2026-10-06-snapshot-consumer-foundation/) records exact counts and review limits. Synthetic contract vectors are neither producer output nor interoperability evidence.

This slice has **no filesystem materializer, production network client, publication-policy selection/pinning, renderer, job or UI**. Later S2 work must verify the input before secure materialization and keep input, projection, reports, renderer and output separate. Existing path guards are not proof of symlink-safe sandboxing.

The trusted selection surface/location is **absent and unselected, a first-preview gate**. Neither room `publish.yml`, plugin settings, nor a grant authorizes policy. No GUI, signed approval, or CLI implementation is selected. Snapshot provenance is not proposal approval. Evaluate references over authorized input, not preselection hiding excluded embeds; refuse or report outside-scope references without leaking private names.

Join component reports into an evidence envelope. Consistent snapshots do not supply trusted execution or result UI; read-only mounts do not contain untrusted HTML/SVG/network behavior. Preview requires a **separate registrable domain**, not a sibling subdomain, outside host agent-MCP allowed origins. This is necessary for sibling cookie-interference isolation, not sufficient security. No inherited credentials/cookies. Preview authentication/access/revocation, content sandboxing, network/credential handling, navigation/messaging, and lifetime remain unselected S2 gates. No domain acquisition/configuration or browser authorization follows.

### Proposed request/result contract — ownership uncommitted

The host has committed to none of this job/UI flow; S1 does not deliver it. A future integrated preview requires a request binding actor/authorization, snapshot/scope, policy, renderer/configuration, URL baseline, preview-only action, limits, and identity. Dispatch, status, cancellation, expiry, recovery, and ownership remain unresolved.

A separate scoped execution worker is possible initially; no general native scheduler is required. But its narrow authenticated host handoff is missing today. The agent-MCP dispatcher is not a general job runner and deliberately excludes the browser tab origin. A plugin button must not bypass that exclusion, broaden origin access, or store backend bearer credentials. Plugins share tab privilege; no established sandbox or least-privilege task channel can be assumed.

A proposed result binds the same request/input identities to output digest/private preview handle, selected corpus, warnings, failures and failure stage, continuity/asset/anchor evidence, and cleanup/lifetime status. Cached output must not masquerade as a new live revision. Do not insert results into canonical notes or create public share links by default; shared plugin settings are not private per-user job state.
