This page answers the one authority question the operating model had left open: **what act puts an approved suggestion on the page?** The answer was proposed, accepted by the maintainer, and built on 2026-09-27. The working guide for the owner is [Applying an approved suggestion](/cyberbaser/development/applying-approved-suggestion/).

:::note[What was decided]
The maintainer accepted the core shape as proposed and made two corrections to the first draft: nobody runs commands, so the act is a button on the receipt in the owner's private app, not a terminal script; and the backend under it stays resilient and machine-callable, which the same privileged API provides. On the three follow-up questions the maintainer expressed no preference, so the recommended answers were taken and are recorded below.
:::

## The shape in one paragraph

Applying is a **second, separate owner act**, not a consequence of approving. On the receipt of an approved suggestion the owner sees whether the page is still exactly as reviewed and, if so, one button: **Apply to page**. Confirming it records one create-once **application event** and starts one ordinary owner-alpha Save job carrying the suggestion's exact operation. Everything after that is the existing pipeline: preflight, checks, atomic exact apply, one-path commit, normal push, deployment monitoring, live witness, local rebuild, and durable restart recovery. There is no new writer, no second application path, and no automatic step between the approval and the act.

## Why a second act, and why not a policy

Approve and Apply answer different questions, and the owner asks them at different times.

- **Approve** asks: is this a good change? It is answered while reading, often on a phone, sometimes weeks before anything happens. It should be cheap and recordable even when the page has since moved on.
- **Apply** asks: put this on the page now? It is answered when the owner is ready for a commit, a push, and a public change. It needs the current page, the current policy, and a moment of attention.

Letting a policy answer the second question from the first would make reading dangerous: the owner would hesitate to approve because approval publishes. The operating model already rules out automatic application from approval, category, identity claim, or trust route. This design keeps that rule and adds only the explicit act.

The act mirrors how the owner's own edits already work. **Save and publish** is the authority event for a direct owner edit. **Apply to page** is the same kind of event for a change that arrived from outside. Same boundary, same pipeline, same evidence.

## What the owner sees

1. **Approve.** The receipt says the page has not changed and that putting it on the page is the separate step below.
2. **Below that, one of four things.** *Put it on the page*, with the button, when the page is still exactly as reviewed. *Cannot be applied as it is*, with the reason in plain words, when the page moved since the review. *The page pipeline cannot apply this yet*, with the reason, when the change is one the owner's own Save path would refuse. *On its way to the page*, with the stage in plain words and a link to follow it, once the act has been taken.
3. **Confirm.** The sheet names the change and the page and says once what will happen: the page changes and is published, in the background, and the next screen follows it step by step.
4. **Follow it.** The job page shows the durable pipeline state, exactly as for a Save. The receipt keeps showing the stage afterwards, and the inbox's decided list can tell approved from applied.

The button appears only in the eligible state. Nothing on the review page itself changes: Approve stays decision-only, and the checkpoint question about that stays a hard gate.

## What the act checks before anything happens

In this order, refusing without effect at the first failure:

1. An Approve decision exists for the suggestion.
2. No earlier attempt reached the page. An attempt that never started or stopped before any source effect does not count, so the owner can try again; one that changed the page blocks any further attempt forever.
3. The prepared input exists or can be prepared: the pinned revision is still reachable, the blob at the branch tip is the exact reviewed object, base and candidate digests reproduce, the trust policy is unchanged.
4. The rendered owner site carries the page, so it has a slug and a live URL to verify against.
5. The owner pipeline's own rules hold: the path is inside the edit policy, the source is LF-only UTF-8, the change is within the owner's size limits, and it does not touch YAML frontmatter.
6. The checkout is clean and its HEAD equals the branch tip that was just checked.

Only then is the event recorded and the job started. The job re-runs its own checks against the supplied session and operation, including the HEAD equality gate immediately before apply.

## The event artifact

Create-once under `proposal-applications/<queueId>.<attempt>.json` in the private owner store, mode 0600, with the same hard-link create-once, child-held lock, and private directory checks the decision and input stores use.

```text
schemaVersion, artifactType: owner-alpha-proposal-application-event, queueId, attempt, appliedAt
authority        type: owner-alpha-local, identity (the configured owner identity)
input            digest of the prepared input artifact, preparedAt
decision         digest, decidedAt, reviewEvidenceDigest
source           repository, path, revision, branch, branchTip, gitObjectId, gitMode, baseDigest, slug, liveUrl
candidate        byteLength, digest
policyRevision   the durable owner policy revision the job is bound to
job              jobId of the Save job this event started
```

The event does not repeat the operation bytes; the input and the job's own immutable operation artifact carry them with digests that must match. The input artifact stays untouched and its gate stays `not-authorized`, because the input itself never authorizes anything. Authority lives in the act, the act is recorded by the event, and the event references the input.

## How the job binds to the existing pipeline

The pipeline accepts a supplied session and operation instead of deriving them from editor text. The act fills both from the input and the blob it re-read.

| Job artifact | Filled from |
|---|---|
| Edit session source bytes, digest, Git mode and object ID, frontmatter range | The exact blob re-read at the branch tip |
| Edit session `baseCommit`, `policyRevision` | Checkout HEAD at the moment of the act; the current durable policy |
| Edit session `slug`, `liveUrl` | The owner edit link the rendered owner site carries for that path |
| Edit session `origin` | `approved-proposal`, with the queue ID, proposal ID, and input digest |
| Source operation span and bytes, base and candidate digests | The proposal's operation, unchanged |

The commit message is the owner's configured prefix plus the path, exactly as for a Save. A provenance trailer was considered and deferred: the pipeline reconstructs the expected message from policy when it recovers a commit after a crash, so a custom message would break that recovery path. Provenance is durable in the event and in the job's session artifact instead.

## Findings recorded with the build

1. **Frontmatter changes cannot be applied by the current pipeline.** The owner Save path refuses any operation that intersects YAML frontmatter. Checkpoint proposal 5 can be approved but not applied; the receipt says so. Kept as measured friction.
2. **Only rendered pages can be applied.** The live witness needs a page URL. A path the owner site does not carry is refused with a plain reason. No witness-free mode was added.
3. **Owner limits govern.** The intake's limits and the owner pipeline's limits differ; the pipeline that writes is the one whose limits apply, and the receipt names the limit when it refuses.
4. **Authorship and credit.** The commit is the owner's, on the owner's machine. The contributor's note and the owner's decision note stay private. Visible contributor credit stays open under challenge 07.
5. **Approve stays recordable for a stale suggestion.** Eligibility is checked at each later act, never at approval.
6. **No separate policy switch.** A first draft proposed a new off-by-default config block. It was dropped: the act already runs only under the durable policy that lets a Save commit and push, and a second switch for the same effect would be a knob without a boundary behind it.

## What stays out

- No application from approval, category, identity claim, trust route, or timer.
- No queue lifecycle change; the intake never learns that a suggestion was applied.
- No rebase, re-resolution of a moved quote, three-way merge, or partial application.
- No multi-file or new-file application; the input contract is one file, one splice.
- No contributor notification; nothing leaves the owner host.
- No change to Lane A or Lane B exposure, which remain separately authorized.

## Evidence

Mechanical, recorded on 2026-09-27 and described on [Applying an approved suggestion](/cyberbaser/development/applying-approved-suggestion/): real intake, real decisions, a real local bare remote, and the real pipeline changing exact bytes, committing once, pushing once, refusing a second act, allowing a retry after a job that never started, and refusing frontmatter and stale suggestions with nothing written. No real Cyberbase application has been run; that is a separately authorized owner run and the first contributor-to-live evidence when it happens.

## Decisions recorded

| # | Decision | Outcome |
|---|---|---|
| 1 | Applying is a separate explicit owner act, with no auto-apply policy | Accepted |
| 2 | The act reuses the owner Save pipeline through a supplied session and operation, adding no second writer | Accepted |
| 3 | The act is taken from the receipt in the owner's app, over a privileged API a machine can also call | Maintainer's correction; built |
| 4 | Events are create-once per suggestion, attempt-numbered only after a failure with no source effect | Accepted |
| 5 | Frontmatter suggestions stay unapplicable, with an honest receipt | No preference stated; recommended answer taken |
