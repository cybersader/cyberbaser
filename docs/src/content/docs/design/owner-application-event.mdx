This page proposes the answer to the one authority question the operating model left open: **what exact event grants source-application authority after an owner approves a suggestion?** It is written for the maintainer to accept, amend, or reject before any code is written.

:::caution[Proposal, not a decision]
Nothing on this page is implemented, selected, or locked. Approve remains decision-only. The [approved proposal input](/cyberbaser/development/approved-proposal-input/) remains a never-consumed artifact with an unfilled gate. The decisions this page asks for are listed at the end.
:::

## The shape in one paragraph

Applying an approved suggestion is a **second, separate owner act**, not a consequence of approving it. The owner names one prepared input. The system checks that the page is still the exact object the owner reviewed and that the owner's durable policy allows applications at all. It then records one create-once **application event** and starts one ordinary owner-alpha Save job carrying the proposal's exact operation. Everything after that is the existing pipeline: preflight, checks, atomic exact apply, one-path commit, normal push, deployment monitoring, live witness, local rebuild, and durable restart recovery. There is no new writer, no second application path, and no automatic step between the approval and the event.

## Why a second act, and why not a policy

Approve and Apply answer different questions, and the owner asks them at different times.

- **Approve** asks: is this a good change? It is answered while reading, often on a phone, sometimes weeks before anything happens. It should be cheap, reversible in spirit, and recordable even when the page has since moved on.
- **Apply** asks: put this on the page now? It is answered when the owner is ready for a commit, a push, and a public change. It needs the current page, the current policy, and a moment of attention.

Folding the two together, or letting a policy answer the second question from the first, would make reading dangerous. The owner would hesitate to approve because approval publishes. The operating model already rules out automatic application from approval, category, identity claim, or trust route. This proposal keeps that rule and adds only one thing: the explicit act.

The event also mirrors how the owner's own edits already work. Clicking **Save and publish** is the edit-specific authority event for a direct owner edit. Applying an approved suggestion is the same kind of event for a change that arrived from outside. Same boundary, same pipeline, same evidence.

## The steps

What the owner does, and what the system does in response.

1. **The owner approves a suggestion.** Exists today. An immutable decision is recorded. Source is unchanged.
2. **An input is prepared.** Exists today, by local script. The input pins the decision digest, the reviewed evidence digest, the exact blob, and the branch tip. It grants nothing.
3. **The owner applies it.** Proposed. From the server machine, as the owner user:

   ```bash
   bun apps/owner-alpha/bin/apply-approved-proposal.js <owner-alpha config> <queueId>
   ```

   The script loads the prepared input and re-runs the same strict eligibility check at this moment: the pinned revision is still reachable, the blob at the branch tip is the exact reviewed object, the base and candidate digests reproduce, and the trust policy is unchanged. It also requires that the checkout is clean, that its HEAD is that branch tip, and that the durable policy has applications enabled. If any of that fails, nothing is written and the reason is printed.
4. **One event is recorded, create-once.** The event names the input by digest, the branch tip it saw, and the job it is about to start. A second event for the same suggestion is refused unless the earlier job failed before any source effect (see retries below).
5. **One Save job runs.** The event supplies the job's edit session and source operation directly, derived from the input rather than from an editor. The pipeline treats it exactly like an owner Save. At `ready-to-apply` it still requires HEAD to equal the bound base. Only the declared bytes change.
6. **The receipt shows what happened.** The approved suggestion's receipt gains one line: not yet applied and eligible now, not yet applied and no longer eligible, or applied in job so-and-so with the job's current state. The inbox's decided list distinguishes approved from applied. No button appears in this first version.

## The event artifact

Create-once under `proposal-applications/<queueId>.<attempt>.json` in the private owner store, mode 0600, with the same hard-link create-once, child-held lock, and private directory checks the decision and input stores use.

```text
schemaVersion, artifactType: owner-alpha-application-event, queueId, attempt, appliedAt
authority        type: owner-alpha-local, identity (the same owner identity the decision carries)
input            digest of the prepared input artifact, preparedAt
decision         digest, decidedAt, reviewEvidenceDigest
source           repository, path, revision, branch, branchTip (must equal checkout HEAD), gitObjectId, gitMode, baseDigest
candidate        byteLength, digest
policyRevision   the durable owner policy revision the job is bound to
job              jobId of the Save job this event started
```

The event does not repeat the operation bytes. They live in the input, and the job's own immutable operation artifact repeats them at bind time with digests that must match. The input artifact stays untouched: its `applicationGate.state` remains `not-authorized` because the input itself never authorizes anything. Authority lives in the event, and the event references the input.

## How the job binds to the existing pipeline

The pipeline already accepts a supplied `session` and `operation` instead of deriving them from editor text. The event fills both from the input and the blob it re-read.

| Job artifact | Filled from |
|---|---|
| Edit session `relativePath`, `source.bytesBase64`, `digest`, `gitMode`, `gitObjectId`, `frontmatter` | The exact blob re-read at the branch tip |
| Edit session `baseCommit`, `policyRevision` | Checkout HEAD at event time; current durable policy |
| Edit session `slug`, `liveUrl` | Resolved read-only from the local rendered site's content index for that path (see findings) |
| Source operation `start`, `end`, `expectedOldBytesBase64`, `replacementBytesBase64`, `baseDigest`, `candidateDigest` | The proposal's operation, unchanged |
| Commit message | Owner prefix plus path, with a `Cyberbaser-Proposal` trailer carrying the proposal ID and queue ID |

The pipeline then reruns its own checks against these inputs: candidate reproduction, LF-only candidate, unchanged bytes outside the operation, OFM classification, render check, link delta, and the HEAD equality gate before apply. The job's session artifact additionally records `origin: approved-proposal` with the event digest, so a job started from a suggestion is distinguishable from a direct owner edit in the durable evidence. That is a small, optional addition to the session schema.

## The durable policy gate

A new owner-alpha config block, off by default:

```json
"applications": { "enabled": false }
```

Turning it on changes the policy revision, exactly as activating automatic commit and push did before the first real Save on 2026-08-02. The event script refuses while it is off. This is the only policy this proposal adds. It gates whether the act is possible; it never performs the act.

## Retries and failure

The pipeline is durable. If the job fails in a restart-safe state, the owner resumes it through the existing resume path, and the event stays the single record. If the job fails terminally **before** durable source-applied evidence exists, the owner may record a new attempt for the same suggestion; the script refuses otherwise. Once any attempt has source-applied evidence, no further attempt is ever accepted for that suggestion: the change is on the page, and push or deployment recovery belongs to the job.

Undoing an applied suggestion is a normal owner edit, not a proposal operation.

## Findings that need a decision

These came out of reading the pipeline against the proposal corpus, and each one changes what the first version can promise.

1. **Frontmatter changes cannot be applied by the current pipeline.** The owner Save path refuses any operation that intersects YAML frontmatter. Checkpoint proposal 5, the `reviewed` date change, can be approved but not applied. Options: keep the rule and show "this pipeline cannot apply frontmatter changes" on the receipt, or relax the rule for approved proposals under the same byte-exact checks. Recommendation: keep the rule in the first version and record the case as measured friction.
2. **Only published pages have a live witness.** The pipeline confirms the change on the live page, so the target must have a slug in the rendered site. A proposal against an unpublished or unrendered path would fail at slug resolution before any effect. Recommendation: fail closed with a clear reason; do not add a witness-free mode.
3. **Owner limits and intake limits differ.** The owner Save path caps changed bytes and lines through its own config; the intake caps proposals through its own. A proposal within intake limits could exceed owner limits. Recommendation: the event applies the owner limits, since the owner pipeline is the one writing, and the receipt names the limit when it refuses.
4. **Authorship and credit.** The commit is made by the owner on the owner's machine. The proposal ID and queue ID go in a trailer. The contributor's note and the owner's decision note stay private. Visible credit for anonymous or pseudonymous contributors remains open under challenge 07 and is not settled here.
5. **Approve for a no-longer-eligible suggestion stays recordable.** Today the owner can approve a suggestion whose page has since changed; the input adapter then reports stale. This proposal keeps that: approval is intent, eligibility is checked at each later act. The receipt should say plainly that the page changed since the review.
6. **Script first, button later.** The privileged owner origin already holds Save authority, so an **Apply** control on the receipt would not be new authority in principle. It would, however, put the second act one tap from the first, on the same screen where the maintainer just decided that Approve must read as decision-only. Recommendation: first version is script-only, like the input adapter; a receipt control is a separate later decision after one real application and after the review checkpoint has been run.

## What stays out

- No application from approval, category, identity claim, trust route, or timer.
- No HTTP route, no button, and no queue lifecycle change in the first version.
- No rebase, re-resolution of a moved quote, three-way merge, or partial application.
- No multi-file or new-file application; the input contract is one file, one splice.
- No contributor notification; nothing leaves the owner host.
- No change to Lane A or Lane B exposure, which remain separately authorized.

## Evidence plan, if accepted

1. Adapter tests at the store layer: refuses while the policy gate is off; refuses when stale, dirty, or HEAD differs from the tip; event is create-once and attempt-numbered; session and operation reproduce the reviewed candidate digest; the checkout is byte-identical after every refusal.
2. One fixture application end to end, the way the two-browser fixture Save was proved: temporary repository, bare remote, real intake, real decision, real event, real job through push, with the local rebuild in place of deployment and live witness where those adapters need a provider.
3. One real Cyberbase application as a separately authorized owner run, recorded in a dated log with the job ID, commit, deployment, and live witness. That run is the first contributor-to-live evidence and must be labelled as a maintainer-operated run, not independent evidence.
