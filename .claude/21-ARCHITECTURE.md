## Current truth (summary, 2026-08-03)

- **Mental model:** replaceable external authoring spokes → pinned, bounded proposals → owner-controlled publication/exact-change/integrity/trust boundary → one authoritative Markdown source → replaceable rendering and publication spokes.
- **Owner lanes:** the owner may author directly in a preferred local Markdown tool or use the private owner-alpha wiki. In owner-alpha, one Save is the authority event and a durable policy controls the exact source-to-live operation. Mental model: the owner's machine is a small personal wiki server (self-hosting pattern); their other trusted devices are just browsers on a private network — edit from the phone, the server holds the vault/Git/credentials and does the work.
- **External lanes:** reader controls, rich browser/WYSIWYG/CMS-like tools, forge editors, and agents may use arbitrary presentation or transient models, but their adapters cannot directly write canonical files, become a second authority, authorize themselves, or hide stale/ambiguous source mapping.
- **As built:** six no-authority boundary packages (`correction`, `ofm`, `publish`, `projection`, `linkcheck`, `trust`), the append-only `ledger` package, the private `owner-alpha` application, GitHub and Forgejo deployment-observation providers, and dogfood CI jobs. `correction` remains a pure no-I/O primitive; only the separately selected owner-local route performs policy-bound source application. The ledger's two-stage GitHub adapter is implemented and hermetically tested: Stage A carries only a non-authoritative routing hint, and trusted Stage B reconstructs authority from GitHub APIs and exact inert Git objects before one ledger-only non-force publication. It is not installed in the live vault, has had no real fork run, and has zero live observations. The Forgejo 16 provider and disposable one-time-mirrored fixture are implemented and hermetically tested. Adversarial review showed that the planned same-UID host runner is not an isolation boundary: it can read run-root credentials and reach ambient same-user container sockets. The harness now blocks the opt-in gate before resource creation pending a separately reviewed runner boundary.
- **Ledger installation boundary:** the trusted record template carries a deliberate all-zero Cyberbaser tooling placeholder and never falls back to a mutable ref. Replacing it with one reviewed commit and installing both workflows in the external vault requires separate explicit authorization.
- **Owner-alpha isolation:** privileged editor/API and unprivileged Quartz reader run on separate origins of one owner-chosen private numeric IPv4 address (loopback default; RFC 1918 and RFC 6598 accepted; transport-neutral, no overlay-vendor coupling). Per-device bootstrap sessions, durable-before-acknowledgement Saves, fail-closed restart recovery, and an immutable pinned renderer commit.
- **WP2 deployment:** one local-only Linux/amd64 OCI image, explicit rootless `0:0` and rootful exact-UID/GID Docker Engine profiles, mandatory Linux host networking, no `ports:`, `/vault` as the only writable host bind, read-only config staged into private tmpfs, profile-bound state volume, operator-supplied HTTPS credential socket, offline Quartz seed, disabled engine logging, attached `b` bootstrap re-arm, and readiness after recovery. Mechanical acceptance passed on a real rootless daemon plus numeric nonzero identity fixtures; actual rootful-daemon, physical-device, external-live, registry, and service-install evidence remains pending.
- Renderers and hosts are swappable commodity spokes; never couple the hub to one SSG or forge. GitHub Pages is current, Cloudflare stays edge-only, and self-hosted Forgejo remains preferred for identity/hosting. WP3 phase 1 now has a strict Forgejo 16 provider branch and disposable one-time-mirrored acceptance package without authority cutover; it remains incomplete until a reviewed runner-isolation boundary exists and the opt-in real engine gate obtains complete storage measurements and passes.
